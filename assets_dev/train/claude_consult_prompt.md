# [진단 의뢰] 캔버스 라벨링 도구 — 그린 박스가 저장 시 축소·치우침되는 좌표 버그 (dpr≠1 환경 추정)

## 배경
혈당계 사진에서 LCD 화면 위치를 라벨링하는 자체 웹 도구를 쓰고 있다.
- 서버: `assets_dev/train/webtool.py` (표준 라이브러리 HTTP 서버)
- 프론트: `assets_dev/train/webtool.html` (단일 파일 SPA, canvas 1개 라벨러)
- 데이터: `screen_boxes.jsonl` = {"id", "quad": [[x,y]×4 TL,TR,BR,BL], "source"} — 좌표는 **EXIF 적용(표시) 이미지의 원본 픽셀** 공간
- 이미지 세트: Datumo 2,512장. **83.5%(2,098장)가 EXIF orientation=6**(저장은 가로 4032×3024류, 표시는 세로), 그 외 ori=1/3. **장마다 원본 크기가 제각각**(3096×4128, 2414×3218, 1118×1491, 1934×2578 등 혼재)
- 사용자 환경: Windows 11, Chrome, 디스플레이 배율 125~150%(dpr 1.25~1.5 추정), 캔버스 휠 줌은 항상 100%(fit 상태) 유지

## 현재 증상 (최신 빌드 + 브라우저 F5 이후에도 지속)
1. 라벨러 캔버스에서 노란 박스가 유리를 정확히 덮는 것으로 보인다(스크린샷 1: glucose_batch1/1005, CareSens N "106").
2. Space 저장 후 검증(E)을 하면: SRC 크롭(저장 박스 영역)과 4방향 펼치기가 노란 박스가 덮은 영역과 **어긋나 있다**. 저장 쿼드를 표시 이미지에 다시 그려보면 **그린 영역의 좌상단 일부만, 작게 저장돼 있다**(스크린샷 2: 청색선=저장 라벨, 초록선=자동 유리 쿼드).
3. 실측(glucose_batch1/1005, 표시 3096×4128): 사용자가 그린 영역(스크린샷 재구성, 근사치) ≈ (764,440)-(2321,2085), 저장 쿼드 = (558.6,345.4)-(1880.7,1778.6). 폭은 거의 보존(1322 vs 1357)되나 **위치가 좌상단으로 이동**(x0 -205, y0 -95)하고 높이는 ~0.80배로 단축 — 순수 균일 스케일이라기보다 이동+비등비 스케일 혼합. (그린 영역 재구성치는 스크린샷 측정이라 ±오차 있음)
4. 파란 모델예측 힌트 박스도 같은 캔버스에서 실제 화면과 어긋나 보인다. 이 힌트 좌표 파일은 별도 스크립트로 표시 좌표계 변환 후 눈검증(다른 이미지에서 유리에 정확히 일치 확인)을 마쳤기 때문에, **데이터가 아니라 캔버스 표시/저장 경로**가 의심된다.
5. 이전 증상: 줌 100%에서 아랫변 리사이즈 핸들이 그려진 위치보다 아래쪽에서만 호버된다.
6. 중요: 내 검증 브라우저(dpr=1, synthetic MouseEvent 주입)로는 그리기→저장→좌표 전부 정확하다. **사용자 브라우저(dpr≥1.25)에서만 발생**하는 것이 핵심 퍼즐.

## 좌표 파이프라인 (의도된 계약)
- `/api/image?id&w=1600`: PIL로 EXIF 적용(exif_transpose) 후 리사이즈 JPEG 서빙(캐시), 응답에 ow/oh = **표시 공간의 원본 픽셀 크기**(orientation 5~8은 가로세로 스왑)
- 프론트: img를 lb.ow×lb.oh 단위 공간에 drawImage로 늘려 그리고, evPos(css→이미지 단위)로 얻은 좌표의 박스를 lb.box에 보관, 저장 시 aabbToQuad(lb.box)를 POST → jsonl 기록
- 검증 `/api/rect`: 동일하게 exif_transpose한 이미지에서 저장(또는 현재 q) 쿼드로 크롭해 스트립 반환

## 이미 수정한 것 (이 경로들은 확인 완료 — 단, 다른 결함과 결합 가능성은 열어둠)
1. EXIF 통일: 이전엔 /api/image=cv2(EXIF 적용), 검수·rect=PIL(무시) 불일치였다 → 전부 PIL+exif_transpose로 통일, ow/oh도 표시 기준
2. **applyImage 캐시 히트 버그**: show()가 캐시 히트 시 applyImage(cached, null)로 호출해 lb.ow/lb.oh가 **이전 장 크기로 잔존** → 크기가 다른 다음 이미지가 이전 장 프레임으로 왜곙 그려지며 라벨 좌표 파손(오늘 코드에서 확정·수정: Image 객체에 _ow/_oh 저장, applyImage가 항상 갱신. 브라우저 실측으로 장 전환 치수 추적 확인). 단, 이 수정 이후에도 사용자 환경에서 증상 지속 → 또 다른 원인이 남아 있다는 뜻
3. draw() 첫 줄에서 캔버스 백킹 버퍼를 CSS 크기×dpr에 동기화(레이아웃 변화 시 표시 수직 압축 → 아랫변 히트 밀림 현상)
4. hitTest 판정 띠를 박스/3로 캡, DPR 반영 그리기 transform, 모드 localStorage 복원, 저장 전 E 검수(q 파라미터), 1~4 방향 선택 저장(upright 필드)

## 내 가설 (코드 추적으로 미확정 — 확인 부탁)
- H1: dpr≠1에서만 성립하는 그리기/저장 경로의 스케일 오차. 다만 evPos와 draw가 같은 lb.s/ox/oy를 공유하므로 내부 일관성은 깨지지 않아야 하고, stored = drawn×0.85(원점 기준)가 되려면 '사용자가 보는 화면'과 '내부 좌표 공간'이 달라지는 경로가 필요한데 코드에서 못 찾았다
- H2: 장 전환마다 fitView가 재실행되고 휠 줌 상태·백킹 동기화의 ox/oy 보정이 섞이는 타이밍 문제 — 특히 이미지 로드 직후(onload 전 레이아웃) getBoundingClientRect 시점
- H3: Windows 배율 + 브라우저 줌 조합에서 clientX/getBoundingClientRect의 스냅이 누적되는 경우
- H4: imgCache(>12 evict)나 모드 전환 시 남는 stale 상태 중 좌표에 영향을 주는 것
- H5: 사용자가 "100%"라고 믿는 상태와 실제 lb.s/fitS의 불일치(표시되는 zoom 텍스트는 s/fitS 비율이라 항상 100%로 표시됨 — 이 표기 자체가 오해 소지)

## 요청 사항
1. 위 파일들(`webtool.html` 우선: fitView/resizeCanvas/draw/evPos/wheel/mousedown/mousemove/clampBox/saveBox/applyImage/show, 그리고 `webtool.py`: api_image/api_rect/_load_gray)을 실제 코드에서 검토해, dpr≠1 환경에서 "stored = drawn × ~0.85, 좌상단 기준"이 성립하는 구체적 메커니즘을 특정해 달라
2. 재현이 dpr 의존적인 상태에서도 잡을 수 있게, "그린 박스 == 저장 박스"를 구조적으로 보장하는 설계로 개선해 달라(예: 캔버스 좌표계 자기검증 캘리브레이션, 저장 시점 라운드트립 어설션, pointer 이벤트 좌표 단일화 등)
3. 사용자 환경에서 1회 실행으로 좌표 파이프라인 전체를 점검하는 셀프 테스트 절차 제안
4. 참고: 검증 스트립의 4방향/자동 유리 쿼드는 부가 기능이고, 본 건의 본질은 **라벨러 캔버스의 그리기↔저장 좌표 일치**다
