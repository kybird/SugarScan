# SugarScan OCR 파이프라인 — 현재 상태와 인식 실패 가설 (Claude 문의용)

작성: 2026-09-04 (GLM 세션). 읽는 분은 이 문서와 저장소만 보고 판단할 수 있어야
하므로 맥락을 전부 적었다. 검증 가능한 숫자를 우선하고, 가설은 근거와 반증
방법을 붙였다.

## 1. 파이프라인 개요

혈당계(SMBG) 사진에서 측정값을 읽는 2단 파이프라인 (전부 단말/로컬 학습):

```
원본 사진(EXIF 지님, 83.5%가 orientation=6)
  → [1단] GM 검출기 (YOLOX-nano, 416×416, 1클래스 lcd_screen)
      화면(유리 전체)의 축정렬 박스를 찾는다
  → [2단] 워프: 박스를 320×160 회색 프레임으로 cv2.warpPerspective 스트레치
  → [3단] CTC 리더 (작은 CRNN, TF) — 320×160 → 숫자열(1~3자리)
```

- 데이터: Datumo TILDE 실촬 2,512장 (업스트림 크당 GT 측정값 포함).
- 좌표 정본: **표시(EXIF 적용) 좌표계** (2026-09-02 통일 — 그 전까지 일부
  로더가 raw 를 써서 라벨/이미지가 어긋났던 것이 저성능의 주원인 중 하나였음).
- 학습 인프라: `assets_dev/train/` — 웹 라벨러(webtool.py)·캐시 빌더
  (build_cache_v2.py)·CTC 트레이너(ctc_reader_v2.py)·평가(eval_reader.py).

## 2. 현재 성능 (2026-09-03까지의 측정)

### GM 검출기

| 모델 | 전체 검출(2,512) | 비고 |
|---|---|---|
| 베이스(Roboflow GM_SCREEN 957/319) | 2,007 (79.9%) | ft 시작점 |
| +ft1 (사람 LCD 라벨 211장 혼합) | 2,482 (98.8%) | 무라벨 시험 294장 중 93.9% 회수 |
| +ft2 (관례 100% 정정, 라벨 294장) | **2,494 (99.3%)** | val AP 71.98 |

회수 박스 품질 눈검: 무라벨 회수 8/8 유리 부착. 잔여 미검출 18장.

### CTC 리더 (ft2 쿼드로 재구축한 캐시, ft 60ep)

| 지표 | 값 |
|---|---|
| 캐시 holdout(1,122장, 학습 미사용) **완전일치** | **131 (11.7%)** |
| 한 글자차(편집거리 1) | 6.5% |
| **예측 길이 != GT 길이 (길이 붕괴)** | **61%** |
| 학습셋 정확일치 | 16.1% (과적합 격차 4.4pp) |
| 예측 길이 분포 | 1자리 19% / 2자리 42% / 3자리 33% / 4자리 6% |

역사: 원류 기준선 5.1%(EXIF 버그 시절) → 좌표·쿼드 정리 후 10.3% → 관례
정정 후 11.7%. 참고로 같은 실사진에서 앱의 규칙 엔진(SegmentRuleEngine)은
완전일치 0% — CTC 가 낫지만 절대치는 여전히 낮다.

## 3. 가설 — CTC 가 인식 못하는 이유 (근거 순)

### H1. 워프 압착: 박스(≈0.83 종횡비)를 2:1 로 무조건 늘린다 (가장 강함)

- **근거 ①**: 길이 붕괴 61%. 숫자를 놓치거나(136→36) 하나 더 만들어내는
  (1360) 오류가 지배적이다 — 인식 내용이 틀린 게 아니라 **글자 수를 세지
  못한다**. CTC 는 시간축(가로)으로 글자를 세는데, 세로 2.4× 압착은
  글자의 시간축 경계를 무너뜨린다.
- **근거 ②**: 실측 — 화면 박스 실측 종횡비(가로/세로) 중앙값 ≈0.83(세로가
  긴 화면)인데 워프가 이걸 320/160=2.0 으로 늘린다. 즉 세로 방향 ~2.4×
  압착이 모든 실사진 샘플에 강제된다.
- **근거 ③**: 학습셋조차 16.1% 다. 과적합(암기)이 안 일어난다는 뜻은
  모델이 같은 이미지를 다시 봐도 일관되게 못 읽는다는 것 — 입력 표상
  자체가 열화돼 있다는 신호.
- **반증 방법**: 종횡비 보존 워프(letterbox)로 캐시를 재생성해 ft 만 돌려
  비교. 길이 붕괴율이 크게 내려가면 H1 확정.

### H2. 사전학습(합성)과 실사진 워프의 기하 불일치

- 합성 렌더러(synth_lcd.py)는 **320×160 캔버스에 처음부터 비례 맞춰**
  숫자를 그린다(7세그+시간줄+단위+mem 포함, 구성 요소는 충실). 반면
  실사진은 H1 의 압착을 겪는다. 즉 pretrain 40ep 이 모델에게 가르친
  "숫자의 모양"과 ft 단계의 실제 입력 모양이 다르다.
- **반증**: 합성 렌더러에 "원본 종횡비 → 2:1 스트레치" 증강을 넣어
  재생성·재학습. 혹은 H1 처방(letterbox)이 실사진·합성 양쪽을 같은 기하로
  묶는 것이므로 H1 검증이 H2 도 절반 검증한다.

### H3. 쓰레기 rect (~8–13%)

- GM 쿼드가 화면이 아닌 곳(버튼 영역·케이스)을 잡은 경우가 측정된
  바 있다(캐시 표본 10장 중 3장 불량 전례). 이런 샘플은 GT 만 있고
  내용이 숫자가 아니다 — 노이지 라벨로 학습을 오염시키고 holdout 에서는
  무조건 오답.
- **반증**: 캐시 전수에 대해 "워프 결과에 7세그 유사 전경이 있는가" 필터를
  걸고 제외 후 재학습. 혹은 눈검 전수.

### H4. 합성 렌더러의 실화면 요소 부족 (약함)

- 합성은 반사광(글레어)·키스톤(사다리꼴 왜곡)·극단 회전을 재현하지
  않는다. 다만 현재 합성이 pretrain 용이고 ft 가 실사진이므로, H1/H2 가
  먼저고 이건 2차.
- **반증**: H1–H3 처치 후에도 오답이 글레어/사다리꼴 사진에 집중되면
  렌더러 실화면화(계획상 'A 경로'의 일부로 이미 예정)가 다음.

### 참고: 이미 기각된 가설

- 모델 용량 부족 — 이전 실험에서 확대 없이도 학습셋 74.5%까지 암기한
  적이 있다(당시 holdout 0.3%의 누수 학습이었지만, 용량 자체는 충분).
- 시간 줄 간섭 — 예전 측정에서 오류의 2.7%만 기여(기각급).
- EXIF/좌표 불일치 — 2026-09-02 전면 수정 완료(효과로 5.1→11.7%).

## 4. 가설 — GM 미검출 18장의 원인 (실물 분류 기반)

18장 몽타주(`_diag/gmmiss/gm_miss18.png`)를 육안 분류한 결과:

| 원인 | 건수 | id |
|---|---|---|
| 극단 각도/기울임 | 6 | 126·134·233·713·92·97 |
| 반사광/가림 | 4 | 700·716·722·726 |
| 비정상 화면 스타일(소형·창문형 등) | 4 | 607·703·808·96 |
| 어두움/저대비 | 2 | 2317·2319 |
| 불명(정상적으로 보임) | 1 | 1044 |

- 18장 중 12장은 베이스 모델(79.9%) 때부터 쭉 못 찾던 **영구 미검출** —
  라벨에 넣어 학습시켜도(ft2 데이터에 포함된 적 없음: 무라벨) 안 잡히는
  난소수. 나머지 6장은 ft1→ft2 전환에서 생긴 회귀분(0.2%).
- **해석**: 검출률 99.3%의 잔여는 데이터 증가가 아니라 (a)각도·조명의
  커버리지(증강), (b)소수 화면 스타일의 라벨 확보로만 줄어드는 성격.
  18/2512=0.7% 는 이미 양호하며, CTC 인식률에 비하면 우선순위가 낮다.
- **반증/처방 실험**: 6장 재라벨+재ft, 혹은 학습 증강에 극단 회전·글레어
  합성 추가. 1044(불명)는 모델 출력 confidence 를 직접 봐야 한다.

## 5. 다음 실험 제안 (우선순위)

1. **H1/H2 통합 검증 — 종횡비 보존 워프(letterbox)**: build_cache_v2 의
   워프를 "박스 비율 유지 + 나머지 패딩"으로 바꾸고(선택지: 패딩 색=
   화면 가장자리 평균) 캐시 재생성 → ctc ft 60 → holdout 채점.
   예상: 길이 붕괴 급감 → 완전일치 큰 폭 상승. 이것이 본 문서의
   핵심 질문이다: **이 처방이 맞는가, 놓고 있는 병목이 더 있는가?**
2. H3 — 캐시 정화(전경 없는 rect 제거).
3. H4 — 렌더러 실화면화(압착·키스톤·글레어) — 1 이 성공한 뒤.
4. GM 잔여 18장 — 별도 소과제.

## 6. 재현 명령

```bash
# 캐시 재생성 (입력: gmscreen_quads.jsonl + labels.jsonl)
conda run -n sugartrain python assets_dev/train/build_cache_v2.py
# CTC 파인튜닝 (사전학습 best 에서 60ep)
conda run -n sugartrain python assets_dev/train/ctc_reader_v2.py ft 60
# holdout 채점 (reader_preds.json 갱신)
conda run -n sugartrain python assets_dev/train/eval_reader.py
# GM 전량 추론 (실험은 --ckpt/--out 로 운영 파일 보호)
conda run -n sugartrain python assets_dev/train/detect_datumo_gm.py \
  --ckpt assets_dev/train/yolox_out/gmscreen_ft2/best_ckpt.pth --out <실험파일>
```

주요 파일: `build_cache_v2.py`(워프 로직 — H1 처방 위치), `synth_lcd.py`
(합성 렌더러 — H2/H4), `ctc_reader_v2.py`(모델: Input(160,320,1) → conv×3
s2 → 시간축 40 → dense 11 → CTC loss), `eval_reader.py`(평가),
`webtool.py`(라벨러·모니터). 캐시 npz 키: real_train/real_holdout(+ids).
