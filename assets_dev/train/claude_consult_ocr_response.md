# claude_consult_ocr.md 검토 응답 — 결론: 가설 전체가 계측 버그 위에 서 있었다

작성: 2026-09-04 (Claude). 재현 명령과 숫자는 전부 아래에 있다.

## 요약

`claude_consult_ocr.md` 의 H1~H4 는 **전부 검토할 필요가 없다.** 문서의 출발점인
"CTC 완전일치 11.7% · 길이 붕괴 61%" 가 모델 성능이 아니라 **평가 스크립트의
EXIF 버그**였다. 같은 모델·같은 이미지·같은 워프에서 `ImageOps.exif_transpose`
한 줄을 넣고 빼는 것만으로:

| | 완전일치 | 길이 불일치 |
|---|---|---|
| EXIF 미적용 (지금까지의 `eval_reader.py`) | **14.7%** | 61.0% |
| EXIF 적용 | **90.7%** | 4.3% |

(표본 300, `reader_model` 그대로, 재학습 없음)

**CTC 리더는 처음부터 잘 읽고 있었다.** 옆으로 누운 이미지로 채점당하고 있었을
뿐이다. 워프 압착(H1)도, 합성/실사진 기하 불일치(H2)도, 쓰레기 rect(H3)도
지금 성능의 원인이 아니다.

> **내 첫 답변을 정정한다.** 이 문서의 초판에서 나는 H1 을 "근거 있음"으로
> 판정하고 letterbox 대신 띠 크롭을 권했다. **틀렸다.** 문서가 제시한 숫자를
> 전제로 받아들이고 그 위에서 추론했기 때문이다. 종횡비 0.78 도, 자릿수 쏠림도
> 실제로 측정된 사실이지만, **그것이 낮은 정확도의 원인이라는 연결이 틀렸다.**
> 전제를 재는 것이 먼저였다 — 저장소의 `patterns/verify-premises-before-executing`
> 가 정확히 이 실수를 막으라고 있는 페이지다.

## 1. 진짜 원인 — G20 이 놓친 네 번째 파일

2026-09-02 의 G20 작업이 EXIF 좌표계를 세 곳에서 통일했다: `build_cache_v2.py`,
`detect_datumo_gm.py`, `golden_bench.dart`. **`eval_reader.py` 는 그 목록에
없었다.** 그래서 학습 입력은 고쳐졌는데 **채점만 옛 좌표계에 남았다.**

```python
# eval_reader.py (수정 전, 63행)
with Image.open(p) as pil:
    pil.load()
    img = cv2.cvtColor(np.asarray(pil.convert("RGB")), cv2.COLOR_RGB2GRAY)
    # ← PIL 은 EXIF 를 무시한다. 그런데 quads 는 표시 좌표계다.
```

원본의 **83.5%가 orientation=6** 이므로, 평가 표본 다섯 중 넷이 "옆으로 누운
이미지에 똑바른 좌표를 물린" 크롭으로 채점됐다. 문서 §2 의 역사
(5.1% → 10.3% → 11.7%)는 전부 이 경로로 잰 숫자다.

### 부수적으로 찾은 두 번째 계측 버그

`ctc_reader_v2.py` 의 자체 holdout 채점도 틀려 있었다(308·320행):

```python
gt_strs = [... for v in row if int(v) != NUM_CLASSES]   # NUM_CLASSES = 11
```

패딩은 `blank = NUM_CLASSES - 1 = 10` 인데 **11 과 비교해서 걸러지지 않는다.**
2자리 라벨 `97` 의 GT 문자열이 `9710` 이 되어 **2자리 표본(전체의 20%)이 전부
오답으로 집계**됐다. 이 버그만으로 완전일치가 92.9% → 74.6% 로 찍힌다.

**두 버그가 겹쳐서 "학습셋조차 16.1%" 라는 관측이 나왔고, 그게 문서 §3 의
H1 근거 ③("암기가 안 된다 = 입력 표상이 열화됐다")이 됐다.** 실제로는 암기가
아니라 채점이 안 되고 있었다.

## 2. 고친 것

| 파일 | 수정 |
|---|---|
| `eval_reader.py` | `ImageOps.exif_transpose` 추가 (+ 이유 주석) |
| `ctc_reader_v2.py` | `!= NUM_CLASSES` → `!= NUM_CLASSES - 1` (2곳) |

**학습 코드·워프 기하·모델 구조는 한 줄도 건드리지 않았다.** 재학습도 하지
않았다. 아래 숫자는 전부 **기존 `reader_model` 그대로**의 것이다.

## 3. 고친 뒤의 진짜 성능

```
$ conda run -n sugartrain python eval_reader.py
hold-out total=2138 (skipped 0)
exact=2034 (95.1%) wrong=104
```

다만 **95.1% 는 낙관적인 숫자다** — `eval_reader.py` 의 holdout 정의는 "손라벨
안 한 장"이라 캐시의 ft 학습 split 과 겹친다. **누수 없는 정직한 숫자는 캐시
holdout 기준 92.9%** 다:

| 기준 | 표본 | 완전일치 | 길이 불일치 |
|---|---|---|---|
| **캐시 holdout (학습 미사용, 정직한 값)** | 1,122 | **1,042 (92.9%)** | 33 (2.9%) |
| 캐시 train 참고 | 600 | 583 (97.2%) | — |
| eval_reader (split 겹침 있음) | 2,138 | 2,034 (95.1%) | — |

- 과적합 격차 **4.3pp** (97.2 → 92.9). 건강한 수치다.
- 길이 붕괴 **61% → 2.9%**. 문서 §3 의 지배적 실패 모드가 통째로 사라진다.
- 누수 점검: train/holdout id 겹침 **0건**. holdout 중 id 이웃(±1)이 train 에
  있는 장은 874장이지만 **그중 GT 까지 같은 장은 6건**뿐 — 연속 id 가 같은
  화면의 연사가 아니라는 뜻이라, 근접 중복 누수는 무시할 수준이다.
- ft 는 합성만 학습한 `pre_best`(08-31)에서 시작하므로 실사진 누수 경로가 없다.

## 4. 남은 진짜 오류 104건의 성격 (이제부터가 실제 과제다)

`eval_reader.py` 재실행 출력에서:

```
('glucose_batch1/136',  '98',  '92')     한 글자 오독
('glucose_batch1/1466', '108', '106')    한 글자 오독
('glucose_batch1/1540', '115', '119')    한 글자 오독
('glucose_batch1/141',  '122', '1122')   자릿수 증가(중복)
('glucose_batch1/1596', '109', '1009')   자릿수 증가(중복)
('glucose_batch1/1494', '119', '9')      자릿수 붕괴
('glucose_batch1/1565', '97',  '2')      자릿수 붕괴
```

**이 앱에서 위험한 것은 `98`→`92`, `115`→`119` 부류다.** 값이 그럴듯해서
범위 검증기도 프레임 합의도 못 잡는다(G17 보고서가 `317`→`319` 를 두고
지적한 바로 그 클래스). 자릿수가 무너지는 부류(`119`→`9`)는 오히려 안전하다 —
값이 범위를 벗어나 걸러진다.

타임스텝 진단(`diag_timestep.py`)으로 붕괴 20건을 보면 전형적으로 이렇다:

```
id=glucose_batch1/1494  GT='119'  pred='9'
  raw(40)  : .......................................9
```

40 타임스텝 중 **39칸이 blank** 이고 마지막 한 칸만 살아 있다. 이건 형태가
애매해서 헷갈린 게 아니라 **그 장에서 모델이 아무것도 못 본 것**이다 — 크롭이
빗나갔거나(H3 의 쓰레기 rect) 극단 조건이거나. 즉 **남은 오류의 일부는 여전히
H3 계열일 수 있다.** H1(워프 압착)과는 무관하다.

## 5. 다음에 할 일 — 순서를 다시 매긴다

1. **기준선을 다시 쓴다.** `claude_consult_ocr.md` §2 의 표와 §3 의 가설
   전체가 무효다. 문서를 폐기하지 말고 **"계측 버그로 무효" 라고 표시해서
   남길 것** — 이 저장소가 `DONE.md` §3 에 사고를 쌓아 두는 것과 같은 이유다.
2. **오류 104건을 성격별로 분류한다.** 한 글자 오독(위험) vs 자릿수 붕괴
   (안전) vs 크롭 실패. **한 글자 오독만이 진짜 과제다.**
3. **H3(쓰레기 rect)는 살아 있다** — §4 의 "전부 blank" 패턴이 그 신호다.
   다만 이제 전체의 8~13% 가 아니라 **오류 104건 안의 일부** 규모다.
4. **H1·H2·letterbox·띠 크롭은 하지 말 것.** 92.9% 를 내는 기하를 원인
   불명의 가설로 뜯는 것은 순손실이다. 워프를 다시 볼 이유가 생긴다면
   그건 §4 분류가 "크롭 실패" 를 다수로 지목했을 때다.
5. **다른 채점 경로도 같은 버그가 있는지 훑을 것.** G20 이 세 곳을 고치고
   네 번째를 놓쳤다. `assets_dev/train/` 에서 이미지를 PIL 로 여는 모든
   자리를 한 번에 세어 두는 편이 낫다 — 같은 사고가 세 번째다
   (라벨러 좌표계 → 힌트 이중회전 → 평가 EXIF).

## 6. 재현

```bash
conda run -n sugartrain python eval_reader.py        # 95.1% (수정 후)
conda run -n sugartrain python diag_timestep.py      # 캐시 holdout 92.9% + 타임스텝
```

`diag_timestep.py` 는 이번에 추가한 진단 도구다. 재학습 없이 기존 체크포인트로
캐시 holdout 을 채점하고, 길이가 무너진 표본의 타임스텝별 argmax 40칸을 그대로
찍는다. 앞으로 판독 변경을 검증할 때 재사용할 수 있다.
