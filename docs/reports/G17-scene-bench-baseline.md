## 왜 그렇게 했나

- **엔진 구성은 앱 부트스트랩과 동일한 생성 기본값**(`SegmentRuleEngine()`,
  균등 4셀 · blur 60 · separability 0.25 · ROI 없음). 벤치가 엔진을 따로
  조정하는 순간 기준선이 아니게 된다. 임계값·기하는 전혀 건드리지 않았다.
- **판정은 labels.jsonl 의 value 문자열과 완전일치**. 오독(값을 냈는데 다름)과
  미인식(값을 내지 않음)을 절대 한 칸에 합치지 않았고, 미인식은 게이트·조립
  사유별로 쪼갰다. 사유 구분은 엔진 실패 메시지 접두사로 매겼다 —
  '초점이 흐'부터(메시지는 활용형 '흐립니다'라 받침에서 어긋난다),
  '표시를 배경과', 조립 문제 이름(blank/unknownGlyph/malformed).
- **지연은 엔진이 스스로 잰 `OcrResult.latency`** 를 그대로 썼다(전체 프레임과
  값을 낸 프레임을 나눠 제시).
- **자릿수 변동 오독은 숫자↔숫자에만** 센다. `318`→`LO` 처럼 글자가 나온
  오독은 자릿수 비교가 무의미해서 `numAsHiLo` 로 따로 뺐다.
- `--limit` 은 셀 벤치와 같은 간격 표본(stride) — 앞부분만 집으면 표본이
  한쪽으로 치우친다(README 의 G15 교훈).

## 읽는 법 — 어디서 무너지는가

- **값을 낸 프레임 123장 중 120장(97.6%)이 오독이다.** 완전일치 3장.
  원본 프레임을 그대로 넣는 경로에서는 값을 낸다는 것 자체가 거의 경보다.
  이전 세션의 관측(60장 0정답 · 318→LO · 49→HI)과 일관된 기준선이다.
- **미인식 1877건 중 1313건(전체의 65.7%)이 초점 게이트**다. 합성 이미지에
  센서 노이즈가 없어 라플라시안 분산이 60 을 넘기 어려운 것 — 예고된
  성질이며, 실촬 프레임에서는 다르게 나올 수 있다.
- **오독의 2/3(120 중 81)이 숫자→`HI`/`LO` 유형.** 격자가 어긋난 상태에서
  일부 자리가 글자 패턴(`L`=D·E·F, `H`의 부분집합)과 해밍 거리 안쪽으로
  떨어지면 조립기의 글자 닻 판정이 표시 전체를 `LO`/`HI` 로 확정해 버린다.
  게이트를 통과한 프레임에서 가장 먼저 막아야 할 구멍이다.
- **대비 축이 가장 뚜렷하다**: 30~80 은 99.3%가 거부로 끝(오독 0.68%),
  140~200 은 오독 9.28%. 고대비일수록 게이트를 통과하고, 통과한 뒤엔
  격자 어긋남이 오독으로 새어 나간다.
- **여백 5~15% 구간이 오독 7.75%로 최고**, 15~25% 는 4.09% 로 가장 낮다.
  여백이 크면 균등 4셀 격자가 여백 위에 놓여 blank/unknownGlyph 로 안전하게
  버려지고, 중간 여백에서 셀이 숫자에 걸쳐 우연한 패턴이 만들어진다.
- **회전은 0~3° 에서 오독 7.04%로 오히려 최고다.** 회전이 클수록 초점
  게이트에 걸려 거부되어 오독이 줄어든다 — 안전해지는 것이 아니라
  못 읽는 방향으로 새는 그림이다.
- 참고(벤치에 태우지 않은 앱 레이어): 정렬 전처리기
  (`photo_preprocessor.dart`)를 거치면 합성 60장 기준 정답 38%·오독 10%
  이다(G16 세션 측정). 이 기준선은 그 전처리기를 거치지 않는 **엔진 자체**의
  수치다.

## 재현 — 같은 데이터로 두 번

같은 명령을 두 번 돌렸다. 판정 수치 SUMMARY 라인이 **완전히 동일**하다.

```
SUMMARY n=2000 exact=3 misread=120 digitChanged=32 rejected=1877
  reasons=blur:1313,sep:0,blank:201,unknown:357,malformed:6,other:0
  HI:83/0/2/1/80 LO:73/3/3/0/67 numAsHiLo=81 missing=0 undecodable=0   (1회차)
SUMMARY (위와 라벨·건수 전부 동일)                                          (2회차)
```

두 리포트 파일의 diff 는 실행 시각·벽시계·지연 백분위(측정 오차) 세 가지뿐:


## 건드리지 않고 남긴 것

- 임계값(`onRatio`, `minSeparability`, `minBlurScore`, `maxHammingDistance`)과
  기하·프로파일 전부 무수정. 나쁜 숫자가 결과물이다.
- `photo_preprocessor.dart` 를 벤치에 태우지 않았다(엔진 자체 기준선이
  이 작업의 목적). 참고 수치만 위에 옮겼다.
- 라벨에 극성(dark-on-light) 키가 없어 극성별 분해는 하지 못했다.
  G16 보고서의 기록대로 사양 키 목록에 없는 탓이다.
- 게이트를 통과한 프레임만의 조건부 수치(97.6% 오독)는 본문에서 파생
  계산으로 제시했다 — 벤치 출력 자체는 전체 기준 표를 낸다.
- 워크스페이스에 원래 있던 추적 안 된 파일(`run_windows.bat`, `.zcode/`)은
  내 작업이 아니라 그대로 뒀다.
