## 1. 결론부터

**dpr 과는 무관한 버그다.** 캔버스가 박스를 그리는 좌표계(`lb.ow` × `lb.oh`)가
**장 전환에서 한 장씩 밀려** 있었고, 그래서 저장된 쿼드가 **직전 장의 표시 크기**
안에서 표현됐다. `dpr` 은 상관 변수였을 뿐 원인이 아니다 — 검증 브라우저에서
재현되지 않은 것은 dpr 이 1이어서가 아니라 **장을 연달아 넘기지 않았기 때문**이다.

증명은 산술이 아니라 픽셀로 했다. 저장된 쿼드에 `(이 장 크기 / 직전 장 크기)`
배율을 곱해 크롭하면 LCD 가 정확히 잘린다.

| id | 표시 크기 | 직전 장 | 저장된 박스 | 배율 보정 후 | 판정 |
|---|---|---|---|---|---|
| `glucose_batch1/1001` | 2414×3218 | (첫 장) | (564,433)-(1935,2090) | — | 정상 |
| `glucose_batch1/1005` | 3096×4128 | 1001 (2414×3218) | (559,345)-(1881,1779) | ×1.2825 → (716,443)-(2412,2282) | **파손** |
| `glucose_batch1/1013` | 2170×2893 | 1005 (3096×4128) | (598,615)-(2451,**2920**) | ×0.7009 → (419,431)-(1718,2046) | **파손**(경계 초과) |

보정 전 1005 크롭은 화면 좌상단 일부(`10`만 보임), 보정 후는 `106 mg/dL` 전체와
시간줄까지 정확히 들어온다. 사용자가 스크린샷에서 재구성한 좌표
(764,440)-(2321,2085) 와도 오차 범위에서 일치한다.

라벨러의 LCD 모드 장 순서(모델 예측 없는 장 먼저 → id 오름차순)를 재현하면
1001 → 1005 → 1013 이 정확히 연속이다. **한 장 밀림이 결정적으로 성립한다.**

### 왜 "고쳤는데 그대로"였나

`webtool.html` 의 `applyImage(cached, null)` 캐시 히트 버그(의뢰서 §"이미 수정한
것" 2번)가 **바로 이 원인이 맞다.** 다만 파일 시각을 보면

- `webtool.html` 수정 **01:18**
- `screen_boxes.jsonl` 기록 **01:21**

즉 문제의 3건은 수정 3분 뒤에 저장됐고, **그때 브라우저에 떠 있던 탭은 수정 전
JS 를 돌리고 있었을 가능성이 압도적으로 높다.** 서버는 `Cache-Control: no-store`
를 보내고 있으므로 새로고침만 했다면 새 JS 를 받는다 — 즉 새로고침이 실제로
일어나지 않았거나, 새로고침은 나중에 하고 판단 근거로는 **그 전에 저장된 데이터**를
본 것이다.

**이 애매함 자체가 진짜 결함이다.** "지금 이 탭이 어느 빌드를 돌리고 있는가"를
사람이 알 방법이 없었다. 그래서 아래 §2 의 방어선은 원인 수정이 아니라
**원인을 몰라도 파일이 오염되지 않게** 하는 데 초점을 맞췄다.

## 2. 넣은 방어선 — 5중

의뢰 §2("그린 박스 == 저장 박스를 구조적으로 보장")에 대한 답이다.
순서대로, 앞의 것이 뚫려도 뒤의 것이 막는다.

### ① 좌표계에 이름표 (`lb.frameId`)
`lb.ow`/`lb.oh` 는 이제 **혼자 바뀌지 않는다.** 이미지 객체·크기·장 id 셋이
`applyImage(img, id, gen)` 한 곳에서만 함께 설정된다. `show()` 진입 시
`frameId = null`, `img = null` 로 두어 **앞 장 사진 위에 새 장의 박스를 그리는
상태 자체가 존재할 수 없다**(로딩 중 캔버스는 비어 있다).

### ② 세대 토큰 (`lb.gen`)
`show()` 는 호출마다 세대를 올린다. 네트워크 응답과 `img.onload` 는 자기 세대가
아직 유효할 때만 좌표계를 갱신한다. 장을 연달아 5번 넘겨도 프레임이 현재 장과
일치하는 것을 브라우저에서 확인했다.

### ③ 저장 직전 검문 (`frameGuard`)
`Space` 저장과 방향 저장(1~4) 모두 통과해야 한다.
- 이미지 미로딩 → 차단
- `frameId ≠ 현재 장` → 차단
- `lb.ow/oh ≠ img._ow/_oh` → 차단 (크기만 밀린 경우를 잡는다)
- 박스가 이미지 밖 → 차단

### ④ 서버 검증 — **핵심 방어선** (`_verify_frame`)
클라이언트는 자기가 틀렸는지 스스로 알 수 없다. 그래서 저장 요청에 **그때 실제로
그린 프레임 크기(`ow`/`oh`)를 함께 보내게 하고, 서버가 원본 파일에서 직접 잰
크기와 대조**한다. 어긋나면 HTTP 409 로 거부한다.

```
좌표계 불일치 — 브라우저는 2414x3218 프레임으로 그렸는데 glucose_batch1/1005 의
실제 표시 크기는 3096x4128 다. 저장 거부(이 상태로 저장하면 박스가 1.283배
어긋난다). Ctrl+Shift+R 후 다시 그릴 것
```

**낡은 JS 가 살아 있는 탭에서 온 요청도 파일에 닿지 못한다.** `ow`/`oh` 를 아예
보내지 않는 구버전 요청도 거부한다. 경계 초과와 8px 미만 박스도 여기서 막는다.
저장에 성공한 행에는 `ow`/`oh` 가 함께 기록되어 **나중에 검증할 수 있다**.

### ⑤ 빌드 지문 (`/api/build`)
헤더에 `build <sha8>` 을 띄우고 15초마다 서버와 대조한다. 서버 파일이 바뀌면
빨간 글씨로 `build a1b2c3d4 → 서버 e5f6a7b8 · Ctrl+Shift+R 필요` 로 바뀐다.
이제 "내가 최신 코드를 돌리고 있나?"가 화면에서 읽힌다.

### 곁들여 고친 것
- **`lb.ox *= rx` 차원 오류** — 팬 오프셋은 CSS 픽셀인데 백킹 버퍼 비율(=CSS×dpr)로
  보정하고 있었다. dpr 이 바뀌기만 해도 화면이 튄다. CSS 크기 변화분만 따라가게 고쳤다.
- **rect 0×0 방어** — 다른 탭에 가 있으면 캔버스 rect 가 0 이 된다. 그 상태로
  `fitView()` 가 돌면 `fitS=0 → lb.s=0` 이 되어 `evPos` 가 0으로 나눠 좌표가
  `Infinity` 로 죽는다. 실제로 재현했다. 이제 숨겨진 동안은 그리기를 건너뛰고
  라벨러 탭으로 돌아올 때 다시 맞춘다.
- **디스크 캐시 자가치유** — 서빙 JPEG 의 종횡비가 표시 크기와 다르면(예전
  EXIF 미적용 파이프라인의 잔재) 즉시 다시 만든다. 현재 143개 전부 정상 확인.
- **`_oriented_size` 메모이즈** — 장당 수백 번 불리는데 매번 파일을 열고 있었다.
- **`webtool.py <포트>`** — 돌아가는 인스턴스를 죽이지 않고 검증용 인스턴스를 띄운다.

## 3. 자가검증 (T) — 의뢰 §3 에 대한 답

라벨바의 **`✓ 좌표 자가검증 (T)`** 버튼(또는 `T` 키) 하나로 파이프라인 전체를
사용자 브라우저 안에서 점검한다. dpr 의존 버그는 개발자 환경에서 재현되지 않으므로
**검증이 사용자 쪽에서 돌아야 한다**는 것이 설계 요점이다.

1. **캔버스 백킹 버퍼** — `cv.width == round(cssWidth × dpr)`, `lb.dpr` 일치
2. **좌표 왕복** — 이미지 6점을 화면 좌표로 보냈다가 **마우스와 똑같은 `evPos` 로**
   되돌려 항등인지. 현재 오차 `4.55e-13 px`
3. **프레임 귀속** — `lb.frameId == 현재 장`, 서빙 JPEG 종횡비 == 프레임 종횡비,
   **서버가 말하는 크기 == 캔버스가 쓰는 프레임**
4. **저장 예행** — `frameGuard` 를 실제로 통과하는지 (파일은 건드리지 않는다)
5. **서버측 라벨 전수 점검** — 저장된 모든 라벨을 원본 파일과 대조(헤더만 읽어
   2,500장에서도 1초 안쪽) + 디스크 캐시 종횡비 + 빌드 지문 일치

### 실측 검증 결과

브라우저에서 `devicePixelRatio` 를 1 / 1.25 / 1.5 로 바꿔 가며 전부 통과.
그리고 버그를 **인위적으로 주입**해 방어선이 실제로 작동하는지 확인했다.

| 주입한 결함 | 잡은 곳 | 결과 |
|---|---|---|
| `ow/oh` 없이 저장 요청 (구버전 탭) | 서버 | 409 거부 |
| 크기만 앞 장 것으로 밀림 (실제 버그) | 클라 `frameGuard` + 서버 | 양쪽 다 거부 |
| `frameId` 가 다른 장 | 클라 `frameGuard` | 차단 |
| 경계 초과 박스 | 클라 + 서버 | 양쪽 다 거부 |
| `show()` 5회 연속 호출(응답 뒤엉킴) | 세대 토큰 | 프레임 일치 유지 |
| 정상 저장 | — | `{"ok": true}`, 값 보존 확인 |

## 5. 라벨링 도구를 버전 관리에 넣었다 (`d5366c5`)

`.gitignore` 가 `assets_dev/` 를 통째로 무시하고 있었다. 그래서 두 가지가
불가능했다.

- **"고친 JS 가 실제로 돌고 있느냐"를 확인할 수 없다.** 오늘 판단이 갈린 이유의
  절반이 이것이다.
- **라벨이 언제 어느 빌드에서 파손됐는지 되짚을 수 없다.**

좌표는 사람이 손으로 만든 자산이고 다시 만들려면 사람 시간이 든다. 데이터셋이
아니라 **소스**로 다뤄야 한다. 대용량(이미지·모델·캐시·로그)은 그대로 무시하고
도구 소스와 사람이 만든 라벨만 허용 목록으로 들였다 — 52개 파일, 345KB + 68KB.
저장소 전체는 여전히 1.16 MiB.

## 6. 앱 쪽에서 같은 성질의 문제 3건 (`5ed3f06`)

"값이 조용히 어긋난다"는 같은 종류를 앱에서 찾아 고치고 테스트로 고정했다.
`flutter analyze` 무경고 · `flutter test` 359건 통과.

### ① 통계에서 오늘 기록이 사라진다 — **사용자가 겪는 버그**
`statsReadingsProvider` 가 기간 질의의 **위쪽 경계를 구독 시점의 `now` 로 굳혔다.**
이 프로바이더는 `autoDispose` 가 아니라 기간이 바뀔 때까지 살아 있고, Drift 는
처음 만든 질의를 그대로 다시 돌린다. 그래서 **통계 화면을 한 번 연 뒤에 저장한
기록은 전부 질의 범위 밖으로 떨어진다.**

기본값 14일을 쓰는 사용자는 기간을 바꾸지 않으므로, 앱을 재시작하기 전까지
방금 잰 혈당이 통계에 나타나지 않는다.

위 경계를 열고(미래 시각 기록도 놓치지 않는다), 아래 경계는 화면 진입 시 다시
계산한다(앱을 켜 둔 채 자정을 넘기면 창이 하루씩 늘어나던 문제).
`test/app/stats_window_test.dart` — **수정 전 코드에서 실패하는 것을 확인했다.**

### ② `update(value:)` 만 부르면 정본이 따라오지 않는다
`GlucoseRepository.update` 가 `value` 와 `unit` 이 **둘 다** 있을 때만
`valueMgdl` 을 갱신했다. 값만 고치면 화면이 보는 `enteredValue` 와
통계·동기화·헬스 연동이 쓰는 정본 `valueMgdl` 이 **서로 다른 숫자**가 된다.

현재 유일한 호출부(기록 편집 시트)는 둘을 함께 넘기므로 지금 당장 터지지는
않았지만, API 가 함정으로 남아 있었다. 빠진 쪽을 저장된 행에서 채워 항상 정본을
다시 계산하게 고쳤다.

### ③ `GlucoseScanner.offer()` 의 "절대 예외를 던지지 않는다"가 지켜지지 않았다
`try` 가 **엔진 호출만** 감싸고 있었다. 정규화·검증·안정화도 같은 메서드 안에서
도는데, 그중 하나가 던지면 라이브 프레임 루프가 죽어 **스캔 화면 전체가 멈춘다.**
경계를 메서드 전체로 옮겼다.

덧붙여 **세션 토큰**을 넣었다. 추론이 도는 사이 `start()`/`stop()` 이 불리면
단위가 바뀌었을 수 있고, 옛 단위로 확정하면 값의 의미가 뒤집힌다(10~50 구간은
두 단위 모두 검증을 통과한다 — `CLAUDE.md` 가 경고하는 바로 그 구간).
늦게 돌아온 프레임은 버린다. 라벨러의 세대 토큰과 정확히 같은 처방이다.

## 7. §7 잔여 5건 — 전부 처리했다 (`d7042da`)

처음에는 동기화 의미론을 밤중에 혼자 뒤집지 않으려 남겨 두었는데, 승인을 받아
같은 날 마무리했다. `test/data/sync_engine_test.dart` 가 고정하던 결정은 그대로
두고, 그 결정이 **다루지 않던 경우**만 채웠다.

### (a) 서버 행 하나가 pull 을 영구히 막던 것 — 해결
`ReadingDto.fromJson` 이 던지면 `_pull` 이 통째로 실패하고 커서가 전혀 전진하지
않았다. 이제 해석 못 한 행은 **버리고** `SyncReport.malformed` 로 센다.

이 과정에서 인터페이스를 `List<GlucoseReading>` → `ReadingPage` 로 바꿨다. 이유가
중요하다: **다음 페이지가 있는지와 offset 을 미는 기준은 서버가 돌려준 행 수**여야
한다. 버린 행을 뺀 수로 세면 마지막 페이지로 오판해 **뒷 페이지를 통째로 놓친다.**
커서도 마찬가지라, 못 읽은 행의 `updated_at` 만 따로 읽어 함께 본다.

> 아직 UI 로는 알리지 않는다. 데이터가 사라진 것이 아니라 이 버전이 못 읽는
> 것뿐이고, 사용자가 할 수 있는 일은 "앱 업데이트"인데 그 문구를 6개 언어로
> 만드는 것은 앱 버전이 둘 이상 도는 시점의 일이다. `SyncReport` 에는 이미
> 실려 있다.

### (b) 건너뛴 pending 행 너머로 커서가 나가던 것 — 해결
이제 **커서를 그 행 앞에 세운다**(`gte` 라 다음 회차에 다시 받는다).
못 읽은 행은 **반대로** 넘긴다 — 붙잡으면 다시 받아도 또 못 읽어 그 자리에서
제자리를 돈다. 두 종류의 "건너뛴 행"을 반대로 다루는 것이 이 수정의 핵심이다.

### (c) 대기 수가 아웃박스 행을 세던 것 — 해결
`distinct entity_id` 로 세고, 시도 한도에 닿아 멈춘 행은 뺀다(그쪽은
`SyncStatusBlocked` 가 따로 알리므로 여기서도 세면 같은 것을 두 번 센다).
한도 값은 `syncMaxAttemptsProvider` 로 뽑아 **엔진과 표시가 같은 값을 보게** 했다 —
덤으로, 개수만 필요한 쪽이 엔진 전체를 만들지 않는다.

### (d) `FrameThrottler.reset()` 이 진행 중인 잠금을 풀던 것 — 해결
이제 통계만 되돌린다. 잠금은 그 작업 자신이 `finally` 에서 푼다. 스캔을 다시
시작한 직후 몇 프레임이 버려지는 것이 옳은 동작이다 — 추론 두 개가 겹쳐 돌면
엔진이 재진입 가능한지에 제품이 의존하게 되고, TFLite 인터프리터처럼 아닌 것도 있다.

### (e) 원근 펴기 중복 두 벌 — 해결
`_warpQuad` 한 벌로 접었다. 공개 함수 둘은 **출력 크기와 대비 처리만** 다르다.

접는 과정에서 문서 결함이 하나 드러났다. `warpQuadToRect` 의 주석은 "퍼센타일
대비 스케일 포함"이라고 적혀 있었지만 **코드는 그것을 하지 않는다.** 그리고 하면
안 된다 — 이 결과는 사람이 보는 화면이 아니라 밴드 검출기의 입력이고, 늘려 놓으면
검출 임계값이 벤치에 남은 수치와 다른 것을 보게 된다. 주석을 고치고, "대비를
걸지 않는다"를 테스트로 고정했다. 주석을 믿고 고치는 사람이 반드시 나온다.

### 검증
`flutter analyze` 무경고 · `flutter test` **373건 통과**(+14). 새 테스트가
고정하는 것:
- 해석 못 한 행이 있어도 pull 이 실패로 끝나지 않고 나머지를 적용한다
- 못 읽은 행이 커서를 붙잡지 않는다
- 버린 행이 페이지 경계 판정을 흐리지 않는다(6행·batch 2·2건 버림 → 4건 수신)
- pending 때문에 건너뛴 행 앞에 커서가 선다
- 한 기록을 세 번 고쳐도 "대기 1건"이고, 막힌 항목은 대기로 세지 않는다
- `reset()` 이 진행 중인 잠금을 풀지 않는다
- `warpQuadToRect` 는 대비를 걸지 않고, 같은 크기·모서리면 엔진 프레임과 기하가 일치한다

### 남은 후속 하나
`malformed` 를 사용자에게 알릴지. 앱 버전이 둘 이상 도는 시점에 결정하면 된다.


1. 브라우저에서 **Ctrl+Shift+R** (한 번은 강제 새로고침할 것)

3. **`T`** 를 눌러 자가검증 — 전부 PASS 여야 한다

   라벨선이 유리에 붙어 있으면 복구가 맞다

된다 — 추측할 필요가 없게 만들어 두었다.
