## 0. 사람이 여기까지 온 경로 — 문맥

다음 세션이 "왜 하필 합성기를 손으로 고치고 있었나"를 알아야 이어갈 수 있다.
순서대로다.

1. **GLM 이 끝낸 카드 셋(기기 단절 분할·미학습 기기 평가·기기 편중 A/B)을
   비판적으로 검토**하는 것으로 시작했다. 검토 중 내가 인용한 수치 두 개가
   근거 없음이 드러났다(형제 기기 80% 주장, HI/LO 318건). 이 경험이 이후
   "수치는 재현되기 전까지 인용하지 않는다"는 이 세션의 운영 규칙이 됐다.

2. **"그래서 내가 뭘 해야 하나"** 로 보드 정리 → 남은 카드 전수 점검 →
   GLM 위임 프롬프트 작성으로 이어졌다.

3. 라벨링을 직접 하려다 **근본 질문에 부딪혔다**: 실기기 사진에서 직사각형으로
   숫자만 온전히 담을 수 없고 단위 글리프가 물린다. 기울이기·꼭짓점 4개 찍기를
   검토하다 원근(호모그래피) 문제로 막혔다. 사용자가 **"일반적으로 CNN 훈련할
   때 남들은 어떻게 하냐"** 고 물어 표준 관행을 확인하게 했고, 이것이 다음
   질문으로 이어졌다.

4. **"지금 만드는 게 숫자 인식기냐 LCD 인식기냐" → "검출기냐 인식기냐".**
   이 세션의 축이 된 질문이다. 답: **검출기**다. 인식기는 이미 깨끗한 크롭을
   주면 읽는다. 없는 것은 그 크롭을 주는 물건이다. (앞 문서 §1)

5. 검출기를 합성만으로 학습시키기로 하고 **GLM 에게 합성 렌더러 재작성을
   위임**했다(`glm/detector`, main 에 병합 완료 `d4374da`).

6. GLM 산출물을 **사람이 눈으로 봤다** — 여기서 결함이 무더기로 나왔다. 사용자
   지시: **"합성 스크립트 너가 수정하자"**, 이어서 **"코드를 보는데 원인을
   몰라? 3,4번도 제대로 고치자"**. 그래서 내가 직접 `synth_panel.py` 를
   고치고 있었고, 그 작업이 §1 에서 끝났다.

핵심은 **5→6 의 전환**이다. 위임한 산출물을 눈으로 검수하니 코드 결함이
나왔고, 그건 위임으로 되돌리지 않고 직접 고쳤다.

## 1. 이 세션에서 끝난 것 — `7bb19a9` (main)

`assets_dev/train/synth_panel.py` 한 파일. montage 눈검 + 코퍼스 실측으로
일곱 자리를 고쳤다. 전부 "실사진에 없는 것을 가르치던" 자리다.

| 결함 | 원인 | 고친 방식 |
|---|---|---|
| 세 자리 큰 값 과대표집 | 균등 난수 30~512 | 코퍼스 실측 분포(`labels.jsonl` 2,512행) 재표본 |
| 단위 표기가 장마다 바뀜 | 매 장 난수 | `zlib.crc32(pid)` 로 프로파일당 고정 |
| 베젤 문자 하강부(g, y) 잘림 | `getTextSize` 의 baseline 무시 | `thh + bl <= m - 2` 로 예약 |
| 글레어가 화면을 덮음 | 반사패치 0~5개, 크기 과대 | 0~2개, 크기 상한 하향 |
| 잔상(ghost)이 상시 | 무조건 그림 | 15% 확률 |
| `mem` 이 12장 중 11장 | 텍스트 채움 30% + 후보 2개 | 텍스트 8%, 도트줄 ≤2줄 |
| `mem` 과 `memory` 동시 출현 | `used_texts` 가 문자열 단위 | `_MEM_VARIANTS` 부류 단위 소진 |

**뒤의 둘은 내가 이 세션에 넣은 회귀다.** 앞의 다섯을 고치면서 만들었고, 같은
montage 눈검으로 잡았다. 기록해 두는 이유: 이 파일은 한 곳을 고치면 밀도
채움 루프를 통해 다른 곳이 움직인다.

검증: `_diag/panel_rebuild/montage_fix4_12.png` — overlap violations 0,
메모리 표기 중복 0, 값 전부 코퍼스 범위.

재현:
```
conda run -n sugartrain python synth_panel.py gen --count 12 --seed 22000 --out <dir>
conda run -n sugartrain python synth_panel.py montage --out <png> --images <dir>/images --manifest <dir>/manifest.jsonl --n 12
```

### 일부러 안 고친 것 하나

`memory` 표기가 숫자 대비 커 보인다(`mh = dh * 0.22`, montage 1·3·4·12번).
**근거 사진(1186·2498)에서 annunciator 높이 / 숫자 높이 비율을 재지 않았으므로
눈짐작으로 내리지 않았다.** 고치려면 그 두 장을 먼저 재라. 이 세션에서 근거
없는 수치를 인용해 두 번 되돌렸기 때문에 의도적으로 멈춘 자리다.

## 2. 앞 문서에서 **정정**할 것 — 엣지 밀도 7.51%

앞 핸드오프 §2 의 **"엣지 밀도 실사진 7.51%(p10 5.44%, 각 300장)"은
폐기됐다.** 저장소의 자로 다시 잰 **2.52%(n=84)** 가 그 자리에 들어갔다.

자는 `assets_dev/train/measure_panel_stats.py` 다. 손잡이를 전부 돌려 봤다:

| 설정 | median | p10 | p90 |
|---|---|---|---|
| `density --frame-exc 0` (기본) | 2.52% | 0.64% | 3.84% |
| `density --frame-exc 0.04` ← GLM 의 2.25% | 2.22% | 0.48% | 3.99% |
| 긴 변 896 정규화 제거 | 1.06% | 0.26% | 4.53% |
| 밴드 미제외 | 2.23% | 1.14% | 3.07% |

**7.51% 는 이 자의 어떤 조합으로도 나오지 않는다.** 실사진 84장의 최대값이
5.43% 인데 내가 적은 p10 이 5.44% 였다. "Canny 임계가 달랐다"는 처음 해명도
틀렸다. 그리고 "각 300장"은 성립할 수 없다 — 숫자 영역을 빼려면 밴드 라벨이
필요하고 그건 84장뿐이다.

재현:
```
cd assets_dev/train
conda run -n sugartrain python measure_panel_stats.py density --frame-exc 0
conda run -n sugartrain python measure_panel_stats.py density --frame-exc 0.04
```

**교훈은 "자를 고정하라"가 아니다.** 자는 저장소에 이미 있었고 나는 그걸
쓰지 않았다. 그리고 수치가 갈렸을 때 "자가 달라서 재현이 안 된다"고 썼는데,
자는 코드라 읽으면 된다. 해명 대신 읽고 돌렸어야 했다. 규칙으로 박았다 —
`CLAUDE.md`「수치를 인용하기 전에」와 `docs/GLM_TASKS.md` §3.7. 앞으로
양쪽 다 수치 옆에 그 값을 내는 명령과 `n` 을 적는다.
