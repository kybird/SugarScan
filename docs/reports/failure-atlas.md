# 판독 실패 아틀라스 — 어느 단계에서 틀리는가

2026-09-06 · 브랜치 `claude/failure-atlas` · 도구 `assets_dev/train/make_failure_atlas.py`
산출물 `assets_dev/train/_diag/atlas/index.html`(+imgs, gitignored — 재생성 방법은 §2)

## 0. 한 줄 요약

오답 35건을 전량 판정한 결과 **검출 단계 탓 13건(37%) · 리더 단계 탓 17건(49%) ·
귀인 불가 5건(14%)**. 과거 사람 검토의 "검출 ~66%"는 크롭만 보고 경미한 잘림까지
검출 실패로 세었 것이다 — 라벨 정량 대조를 하면 **경미한 잘림은 정답의 53%에도
있어** 원인으로 쓸 수 없고, 심각한 잘림(recall<0.7)만이 오답과 강하게 연결된다
(오답 47% vs 정답 6.4%).

## 1. 무엇을 만들었나

파이프라인의 중간 산출물을 케이스 한 건·한 행에 나란히 놓는 정적 HTML 컨택트 시트.

행 하나 = ①원본(EXIF 표시 좌표계) 위 GM 예측 쿼드(파랑)·BOX_MARGIN 크롭 박스(마젠타)·
사람 라벨(LCD 초록/밴드 노랑) ②리더에 실제 들어간 320x160 워프(+2배 확대)
③CTC 타임스텝 40칸의 argmax 문자·확률(확률<0.5 붉은 테두리) ④TTA 변형 9개의
디코드·득표 ⑤id/GT/예측/공식 득표율/오류 분류(webtool 기준) + 검출 판정 뱃지.

75행 = 오답 35(risky 11 → safe 21 → blank 3, 득표율 오름차순) + 대조군 40
(정답 중 저득표 하위 20 + 만장일치 시드 표본 20). **사전순 섞기 없음** — 중간에
멈춰도 한 층이 통째로 비지 않게(aggregate-hides-stratified-failure).

HTML 상단에 네 가지 주의를 박아두었다: CTC 타임스텝은 공간 위치가 아니다(BiLSTM
양방향 문맥), 축소 렌더로 경계 판단 금지([원본 해상도] 링크), TTA 표는 crc32 시드
재현 실행(공식 득표율이 정본), 대조군이 섞여 있다(정답에 같은 성질이 있는지 재기
전까지 원인 주장 금지).

## 2. 재생성

워크트리(코드)와 데이터(메인 트리, gitignored)가 다르므로 `--data-root` 로 지정:

```bash
conda run -n sugartrain python make_failure_atlas.py \
    --data-root D:/Project/sugarScan/assets_dev/train \
    --review _diag/atlas/agent_review.json
```

`--review` 는 1차 눈검 판정(`agent_review.json`, {id: {det, note}})을 행에 뱃지로
심는 2차 재생성용. 입력 파일은 전부 읽기 전용이고 산출물은 `_diag/atlas/` 만
쓴다. `webtool.py`·`lib/` 미수정.

## 3. 검증

- **기하 재사용을 픽셀로 증명**: 시작 시 이 도구가 `eval_reader` 기하로 만든 크롭
  12건을 npz holdout 크롭과 대조 — 12/12 픽셀 완전 일치. 어긋나면 즉시 죽는다.
  (duplicated-geometry-implementation: `load_gray`·`framed_src_rect`·`frame_crop` 을
  eval_reader 에서 추출해 import — 재구현 0줄)

  그대로 옮김(gt 체인 corrections→readings→v[1], blank 우선, 자릿수 비교 순서 포함).
  값이 갈라지면 webtool 이 정본.
- **좌표계**: EXIF 표시 좌표계 단일(G20 통일 이후 정본 파일 `gmscreen_quads.jsonl`,

- `flutter analyze` 무경고 + `flutter test` 전체 통과(변경이 python/보고서뿐이어도
  lib/ 우발 변경 탐지용 게이트). 결과는 커밋 시점 기준 통과.

## 4. Q1 — 오답 중 검출 단계 vs 리더 단계 비율

전제: holdout 1,122건, exact 1,087, 오답 35. 오답 전량을 두 방법으로 판정했다.
LCD 라벨이 있는 17건은 **라벨 대비 정량**(screen_boxes, 변별 잘림 px·recall),
없는 18건은 **오버레이 비전 눈검**(GT 숫자로 사례 대조 확인). 1차 판정이며
`agent_review.json` 의 det 클래스로 아틀라스에 박아두었다.

| 판정 | 건수 | 비율 | 사례 |
|---|---|---|---|
| 검출 단계(cut 11 + wrong_area 1 + orient 1) | 13 | 37% | 아래 참조 |
| 리더 단계(검출 정상, 숫자줄 온전) | 17 | 49% | §5 |
| 귀인 불가(경미 잘림, 정답에도 흔함) | 5 | 14% | 1405·283·1244·1226·61 |

- **심각 컷 9**(라벨 recall 0.38~0.72): 1564·1565(하단 1300~1400px, blank 2건 전부),
  1593·1598·1610·1614·606(**가로 화면 5건 전부, 좌측 700~1450px**), 1641(우측 311px=28%),
  2382(우측 1184px)
- **비전 컷 2**: 213(381의 끝자리 우측 경계 밖 → 38), 805(141의 끝자리 → 14)
- **엉뚱한 영역 1**: 1494 — 박스가 좌상단 아이콘, 숫자줄은 중앙 → blank
- **방향 1**: 2501 — 기기 가로, LCD 옆으로 누움

**과거 "검출 ~66%"와 다른 이유.** 그 검토는 크롭(워프)만 보고 판단했다. 라벨
정량 대조를 추가하자:

| 라벨 recall | 오답(17건 중) | 정답(156건 중) |
|---|---|---|
| < 0.7(심각) | **8 (47%)** | 10 (6.4%) |
| < 0.9(경미 포함) | 14 (82%) | 83 (53%) |

경미한 잘림은 정답의 절반 이상에도 있다 — LCD 라벨은 화면 전체를 감싸서, 박스가
숫자줄은 커버하고 베젤을 덜 담아도 판독에 지장이 없기 때문. 그래서 5건은
`ambiguous` 로 놓았다(예: 61 은 좌측 125px 잘림이 있지만 오답은 130→13 끝자리
누락이라 좌측 잘림과 무관할 가능성). **"라벨 대비 잘림"을 원인으로 말하려면
심각도와 잘리는 방향(숫자줄 위치)을 함께 봐야 한다.**

가로 화면(쿼드 종횡비>1.5)은 이번 오답 5건 전부가 심각 좌측 컷 — 검출 단계
전용 층이다(det-ok 오답 17엔 가로 0건). 다만 전체의 2.0%(51/2512) 층이라 개선
기여 상한 +1.17pp 인 점은 종전 문서(2026-09-04)와 같다.

## 5. Q2 — 검출이 정상인데 리더가 틀린 17건의 공통점

내역(비전 눈검으로 숫자줄 온전 확인 + 라벨 recall 1.0 3건):

- **끝자리 문제 14/17 (82%)** — 끝자리 누락 8(1717 293→23 · 2624 157→1 · 42 150→10
  · 51 85→8 · 647 98→8 · 136 98→9 · 236 344→24 · 247 294→24), 끝자리 치환
  6(101 157→151 · 1099 106→108 · 488 105→109 · 694 187→181 · 1694 179→175 ·
  2411 195→180)
- 가운데 자리 2(220 270→370 · 1086 171→111), 자릿수 추가 1(845 155→1559 —
  "지어내기" 행동, model-invents-what-it-cannot-see 와 일치)

**정답에 없는 성질인가? 아니오 — 이미지 성질로서는 변별 축을 찾지 못했다.**
17건 전부 세로 화면(종횡비 0.61~1.38)에 숫자줄이 온전히 들어간, 정답과 구별되지
않는 입력이다. 공통점은 이미지가 아니라 **오류의 위치 프로파일(후미 자리)** 이며,
이는 종전 측정(자리별 오율 80/37/18%)과 양립한다. 리더 단계 오답을 예측하는
눈에 보이는 입력 특징은 이번 검토 범위에서 **없다고 적는다.**

득표율로 나누면: 17건 중 12건은 거절선(0.778) 이하로 잡히지만 5건(1717·247·42·
694·1694, 득표 0.778~0.889)은 **모델이 확신하며 틀린** 사례이다.

## 6. Q3 — 낮은 TTA 득표율과 실제 오답의 중복

거절선 REJECT_AT=0.778(webtool 정본 값) 기준, holdout 전수:

| | 건수 | 비율 |
|---|---|---|
| 오답 중 득표 < 0.778 (잡힘) | 25/35 | 71.4% |
| 정답 중 득표 < 0.778 (희생) | 24/1,087 | 2.2% |
| 오답 중 생존(득표 ≥ 0.778) | 10 | — |

생존 10건의 내용: 검출 탓 5(1564 0.889 · 1641 0.778 · 1494 0.778 · **1598 1.0** ·
1226 0.889) + 리더 탓 확신 오독 5(§5 말단). **1598 은 가로 화면에서 좌측 708px가
잘렸는데 만장일치(1.0)로 틀렸다** — 검출 실패가 TTA 흔들기에 나타나지 않는,
게이트의 사각지대 사례다.

결론: 득표율 게이트는 리더 오류의 12/17(71%)을 잡지만 확신 오독 5건은 통과한다.
"틀린 것을 거를 뿐 맞히게 하지 않는다"는 종전 결론(TTA 일치도 연구,
2026-09-04)과 정확히 일관한다.

## 7. 부수 발견

1. **eval_reader TTA 시드가 프로세스마다 바뀐다.** `np.random.RandomState(TTA_SEED +
   (hash(cid) & 0xFFFF))` — Python 문자열 `hash()` 는 프로세스별 솔트로 무작위화된다
   (실측: 같은 cid 를 두 프로세스에서 해시 → 값 상이). 변형 선택이 실행마다 달라져
   agree 경계 근처 값이 흔들릴 수 있다. 고치지 않았다(정본 평가 경로의 동작을 바꾸는
   판단이라). 아틀라스의 TTA 표는 `zlib.crc32(cid)` 시드로 고정 재현했다고 HTML 에
   명시. 권고: eval_reader 도 crc32 로 교체 — 한 줄이고 이후 평가가 재현 가능해진다.
2. **GM 미검출 18건**(labels 2,512 중 쿼드 없음, holdout 아닌 전체 기준) — 아틀라스
   행에는 없고 HTML 머리에만 집계.
3. **라벨 커버리와 오답 분석의 어긋남**: 오답 35 중 LCD 라벨이 있는 건 17건뿐.
   라벨이 없는 18건은 비전 눈검으로 메꿨다(14 ok · cut 2 · wrong_area 1 · orient 1).
   라벨이 있으면 정량, 없으면 눈 — 이 비대칭이 `ambiguous` 판정의 정확도를 좌우한다.

## 8. 한계 — 모르는 것은 모른다고

- 비전 눈검은 1000px 축소판 기반이다. `cut` 판정의 경계 몇 픽셀은 원본 해상도
  링크로 사람이 재확인해야 한다(주의 2).
- `ambiguous` 5건의 진짜 원인은 모른다. 잘림 방향과 오답 양상이 안 맞는 쪽으로
  기우나(§4), 숫자줄 좌표가 없어 단정 불가.
- det-ok 17건이 왜 하필 끝자리에서 틀리는지는 이 아틀라스 범위 밖(모델 내부)이다.
- 라벨 없는 정답군의 검출 품질은 쟀지 않았다(정답 대조는 라벨 있는 156건만).

## 9. 사람 검토 포인트

아틀라스를 열어 다음 순서로 확인한다: ① `검출:cut` 뱃지 행의 원본 패널 — 심각
컷 9건이 진짜 숫자줄을 잘랐는지 ② `ambiguous` 5건 — 잘림이 원인인지 육안 판정
③ `검출:ok` + 거절선 통과 5건 — 확신 오독의 실화면. 판정이 바뀌면
`agent_review.json` 을 고치고 §2 명령으로 재생성하면 뱃지가 갱신된다.
