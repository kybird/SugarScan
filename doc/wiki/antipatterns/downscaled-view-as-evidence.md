# 축소본·소표본을 보고 원인을 단정하는 것

작게 줄인 이미지나 몇 장의 표본은 **판단이 가능해 보인다.** 틀렸다는 신호를 주지 않기 때문이다.

## 실패 모드

한 세션에 세 번 일어났다.

| 판단 | 근거 | 실제 |
|---|---|---|
| "266 은 똑바로 서 있다" | 620px 렌더 | 반시계 **10~15° 기울어짐** |
| "GM 박스가 `1` 을 자른다" | 같은 620px 렌더 | 박스 경계가 `1` 의 **바깥**을 지난다 |
| "마지막 자리가 잘려서 틀린다" | 오독 몽타주 8칸 | 정량 반증 2회 — 정답의 79%도 같은 성질 |

앞의 둘은 축소 때문이다. 620px 에서 몇 픽셀 차이는 렌더링 안티에일리어싱에 묻히고, **"가깝다"가 "닿았다"로 보인다.** 세 번째는 표본 문제다 — 실패만 모아 보면 데이터셋의 공통 성질이 전부 원인처럼 보인다.

주의할 점: **스케일링 버그가 아니었다.** 박스를 원본에 그린 뒤 이미지를 축소했으므로 좌표는 정확했다. 도구는 맞았고 판독이 틀렸다. 그래서 코드를 검사해도 안 나온다.

## 왜 반복되는가

축소본은 싸고 빠르다. 여러 장을 한눈에 볼 수 있어 **더 많이 본 것 같은 착각**을 준다. 실제로는 장당 정보량이 줄어든 것이고, 특히 **경계·정렬·미세 기울기** 판단은 축소에서 가장 먼저 사라지는 정보다.

## 점검 체크리스트

- [ ] 이 판단이 **몇 픽셀** 차이에 달려 있는가. 그렇다면 원본 해상도로 확대해서 봤는가
- [ ] 몽타주로 본 것을 원인 주장으로 쓰고 있지 않은가 — 몽타주는 **개별 사실 확인**(이 GT 가 맞는가)에는 좋고 **인과 주장**에는 나쁘다
- [ ] 실패 사례만 봤는가. **정답 사례에도 같은 성질이 있는지** 재라
- [ ] 눈으로 본 것을 숫자로 재확인했는가. 못 재는 주장이면 그렇다고 적어라

## 무엇이 좋은 쓰임인가

축소·몽타주가 **틀린 도구는 아니다.** 이 저장소에서 오독 43장 전수 GT 검수는 몽타주로 했고(타일이 320×160 원본 해상도), 43/43 이 맞다는 확실한 결론을 냈다. 차이는 **묻는 질문**이다 — "이 GT 가 맞나"는 타일 하나로 답이 나오지만, "왜 틀리나"는 대조군과 정량이 필요하다.
