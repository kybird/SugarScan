# 선언은 있는데 소비하는 코드가 읽지 않는다

설정·프로파일에 값을 적어 두면 그 값이 쓰인다고 믿게 된다. 그런데 소비하는
쪽에 그 값을 읽는 분기가 **없으면 아무 일도 일어나지 않는다.** 에러도 경고도
없다. 잘못된 값을 쓰면 터지지만, **읽히지 않는 값은 침묵한다.**

## 실패 모드

- 선언에 없는 키를 쓰면 `KeyError` 가 난다. 반대는 조용하다 — 있는 키를
  코드가 안 읽는 것은 아무 신호도 내지 않는다.
- 그래서 **그 값이 맞는지 아무도 검증하지 않는다.** 화면은 늘 옛 동작인데,
  선언을 읽는 사람은 새 동작을 기대한다.
- 값을 고쳐 보고 "안 먹네" 하면, 대개 값을 더 크게 바꿔 본다. 여전히 아무
  일이 없으니 **다른 원인을 찾아 헤맨다.**

## 실제 사례

sugarScan 합성기(2026-09-15), 한 세션에서 세 건이 같은 모양으로 나왔다.

```
time=dict(pos="top-left")   렌더러에 top-* 분기가 없어 below 로 떨어졌다.
                            accuchek_active 는 그 선언을 한 채 몇 주를 갔다.
unit=dict(hug=0.04)         hug 를 읽는 코드가 없었다.
                            hug=0.00 과 0.45 의 간격이 둘 다 65px 이었다.
dot_panel=True              선언한 프로파일이 하나도 없었고, 의미가 생기는
                            조합(dotrow_* 보유)도 존재하지 않았다.
```

세 번째가 특히 나쁘다 — 값이 **에디터의 스위치로 노출되어** 있었다. 사람이
켜고 끄며 "반응이 없네" 를 반복했다.

## 왜 생기는가

- 선언은 싸다(한 줄). 분기는 비싸다(배치·충돌·좌표). 선언을 먼저 적고
  분기는 나중에 하려다 잊는다.
- 리뷰가 선언 쪽만 본다. "이 기기는 시간이 위에 있다" 는 선언은 읽으면
  맞아 보인다. 그 선언이 코드에 닿는지는 실행해야 안다.
- 되돌리기로 분기만 사라지는 경우도 있다 — 선언은 다른 파일에 있어 남는다
  (`doc/raw/2026-09-15.md` Case 4 의 `git checkout --`).

## 예방 체크리스트

- [ ] 값을 하나 넣었으면 **그 값을 바꿔 결과가 달라지는지 그 자리에서 잰다.**
      "넣었다" 가 아니라 "0.0 과 0.45 가 다르게 나온다" 를 보고한다
- [ ] 값의 **후보 목록을 소비하는 코드 옆에 둔다.** 렌더러가 분기하는 값만
      고를 수 있게 하면 오타가 옛 동작으로 떨어지는 길이 막힌다
      ([[enumerate-what-the-code-branches-on]])
- [ ] 노브를 노출하기 전에 **그 노브를 켠 기기가 하나라도 있는지** 본다.
      아무도 안 켜는 스위치는 지운다
- [ ] 전수 조사가 싸면 한다 — 값을 하나씩 바꿔 산출물 해시를 비교하면
      죽은 노브가 한 번에 나온다
- [ ] 선언과 분기를 다른 커밋에 나누지 않는다
