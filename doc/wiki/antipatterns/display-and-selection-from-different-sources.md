# 화면에 깔린 것과 조작 대상이 서로 다른 소스에서 온다

목록을 보여 주는 코드와 "지금 선택된 것"을 만드는 코드가 **다른 배열을 읽으면**,
사용자는 화면을 보고 판단하는데 파괴적 동작은 화면 밖 대상에 닿는다. 정렬·필터·
모드가 추가되는 순간 두 경로는 반드시 갈라진다.

## 실패 모드

`devices.html` 에서 실제로 일어난 일: 표시 목록은 `viewOf()`(정렬·필터·모드
반영)로 바뀌었는데 선택을 만드는 함수들은 `memberOf()`(그룹 구성원)를 계속
읽었다. 기기 필터가 걸려 화면에 43장만 있는 상태에서 `a`(전체 선택)를 누르자
선택 집합에는 그 그룹의 782장이 들어갔고, 한 번의 저장이 **사람이 10시간 넘게
붙인 라벨 782장(코퍼스의 31%)을 덮었다.**

선택은 화면 밖에 있어 눈으로도 확인되지 않는다. "선택 N장" 숫자만이 유일한
단서인데, 그 숫자를 볼 이유가 사용자에게 없다.

이 사고 전에 같은 파일에서 선택 규칙을 네 번 고쳤다(저장 후 선택 교체 → 지우기
후 선택 확장 → 입장 시 자동 선택 → 클릭이 곧 선택). 매번 기존 모드에서만
확인했고 **새로 만든 모드에서 선택을 시험하지 않았다.**

## 왜 생기나 (First Principles)

- 표시는 눈에 보이므로 바꾸면 바로 확인된다. 선택은 **상태**라서 보이지 않는다.
  그래서 표시 경로만 새 요구에 맞춰 진화하고 선택 경로는 남는다.
- 정렬·필터·모드는 "무엇을 보여 줄까"의 문제로 인식되지만, 실제로는 **"무엇을
  조작 대상으로 삼을까"의 정의를 바꾸는 변경**이다.
- 파괴적 동작(덮어쓰기·삭제)은 대개 선택 집합을 그대로 신뢰한다.

## 막는 법

1. **표시 목록을 만드는 함수 하나를 정본으로 두고**, 선택을 만드는 모든 경로가
   그 함수만 읽게 한다. 선택은 표시 목록의 부분집합이라는 것을 코드로 강제한다.
2. 모드·필터·정렬을 추가할 때 **선택을 새 모드에서 시험한다.** "몇 장 선택됐고,
   저장 payload 에 무엇이 실려 가는가"를 직접 확인한다(가로채기 테스트면 충분).
3. **이미 값이 있는 대상을 덮어쓰는 동작에는 개수를 보여 주고 확인을 받는다.**
   새로 채우는 것과 덮는 것은 되돌림 비용이 다르다.
4. 화면에 **현재 선택 수**를 항상 띄운다. 사용자가 마지막으로 눈치챌 지점이다.
