# 분모가 다른 두 수치를 같은 이름으로 나란히 찍는다

비교 출력이 두 수치를 나란히 인쇄한다. 이름이 같으니 비교가 성립하는 것처럼
보이는데, **무엇에 대한 비율인지**가 서로 다르다. 그 위에 진단이 쌓이고,
진단이 카드가 되고, 카드가 설계 결정이 된다.

## 실패 모드

비교 줄에는 두 숫자와 이름 하나만 있다. 분모는 각자의 자(ruler) 안에 있고
출력에 없다. 그래서:

- **차이가 항상 한 방향으로 나온다.** 계통 오차라 표본을 늘려도 안 사라진다.
- 그 차이를 설명하려고 **실제 원인을 찾는다.** 그럴듯한 원인이 늘 있다.
- 진단이 누적된다 — 지표 하나의 오해가 설계 판단으로 자란다.

## 실제 사례

합성 검증기가 종횡비를 이렇게 찍었다:

```
종횡비 w/h   합성 median=0.734 | 실측 0.792 [0.705, 0.975]
```

합성 쪽은 **캔버스**(유리 + 몸체 마진) w/h 였고, 실측 쪽은 **GM 쿼드**
(화면) w/h 였다. 캔버스는 유리에 마진을 더한 것이라 **구조적으로 항상 더
좁다.** 같은 물건으로 재면 맞았다:

```
캔버스 0.734 · 유리 0.800 · 실측 0.792   (seed 31000 n=300)
```

그 사이 쌓인 진단은 이랬다: '합성이 실측보다 좁다' → '가로형이 부족하다' →
'프로파일 12종이 코퍼스 54종을 대표하지 못한다'. 마지막은 카드가 되어 사람
판단 대기까지 올라갔다. 근거 두 개 중 하나가 이 오해였다(다른 하나는 극성
측정 오류였다).

고치면서 **검증기가 밴드 기하를 아예 안 찍고 있었다**는 것도 드러났다 —
합성기의 핵심 산출물인데 비교 대상이 없었다.

## 왜 생기는가

- 자(ruler)는 각자 파일에 있고 분모는 그 안의 코드다. 비교하는 쪽은 이미
  계산돼 있는 필드를 집어 쓴다 — `manifest["wh"]` 가 무엇의 w/h 인지는
  이름에 없다.
- 두 값이 **비슷한 범위**에 있으면 의심이 안 든다. 0.73 과 0.79 는 그럴듯한
  차이다.
- 차이가 계통적이라 **설명이 붙는다.** 설명이 붙으면 검증이 끝났다고 느낀다.

## 예방 체크리스트

- [ ] 비교 줄에 **분모를 적는다** — "밴드/유리", "w/h(유리=GM쿼드)" 처럼
      이름 자체에 기준을 넣는다
- [ ] 합성 쪽에서 실측 대응물을 만들 때, 실측 자의 **코드를 읽어** 무엇을
      재는지 확인한다. 필드 이름으로 추측하지 않는다
- [ ] 대응물이 없는 축은 **없다고 인쇄한다.** 비워 두면 다음 사람이 아무
      값이나 갖다 댄다
- [ ] 차이가 늘 한 방향이면 **원인을 찾기 전에 기준을 의심한다**
- [ ] 핵심 산출물인데 비교 줄이 없는 축이 있는지 확인한다
