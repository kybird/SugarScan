# 같은 좌표계를 공유하면서 디코더 관례를 통일하지 않는 것

`cv2.imread` 는 EXIF orientation 을 **자동 적용**하고, `PIL.Image.open` 은 **무시**한다. 같은 파일을 두 라이브러리로 읽는 코드가 같은 좌표계를 공유하면 그 순간 갈라진다.

## 실패 모드

Datumo 원본의 **83.5%(2,098/2,512)가 orientation=6** 이다. 그래서:

- 라벨러(cv2)는 올바른 세로 표시 → 사용자가 라벨링하기 좋았다
- 검수·캐시·검출(PIL)은 누운 원본 사용 → 검수 SRC 가 90° 돌아 보이고, 라벨 좌표(표시 공간)와 파이프라인 좌표(raw)가 불일치
- **CTC 학습 rect 다수가 "옆으로 누운 숫자 + 올바른 GT"** — 저성능의 숨은 주원인 후보

증상이 "검수창에서만 원본이 회전돼 보인다"로밖에 안 떠올라, 관례 차이를 의심하기까지 오래 걸린다.

## 점검 체크리스트

- [ ] 같은 이미지를 읽는 모든 경로가 **같은 EXIF 처리**를 하는가 (Python cv2 / Python PIL / Dart `package:image`)
- [ ] 좌표계 정본이 문서에 한 줄로 적혀 있는가 (여기서는 "표시(EXIF 적용) 이미지의 원본 픽셀")
- [ ] API 응답의 크기(ow/oh)가 그 정본 기준인가
- [ ] 디스크 캐시가 파이프라인 변경 뒤에도 유효한가 (종횡비 자가 점검)

## 실측한 현재 상태 (2026-09-02 정정)

처음에는 세 곳 전부 무처리라고 적었다. **재 보니 두 곳은 이미 처리되고 있었다.**
"무처리일 것이다"를 코드 확인 없이 옮겨 적은 것이 이 페이지 자신의 결함이었다.

| 경로 | 실측 | 판정 |
|---|---|---|
| `cv2.imread` | EXIF **적용**(4.11 기본, ori=6 표본에서 확인) | — |
| `PIL.Image.open` | **무시** | — |
| `package:image` `decodeImage` | JPEG 디코드 시점에 **픽셀에 굽는다**(ori 5~8 표본 242장 전부, 예외 0) | — |
| `build_cache_v2.py` | PIL 무회전 이미지 + **표시 좌표계 쿼드** | **어긋남 — 진짜 결함** |
| `detect_datumo_gm.py` | 1차 `cv2.imread`(적용). PIL **폴백만** 무시 | 폴백 경로만 결함 |
| `golden_bench.dart` | `package:image` 가 이미 굽는다 | **결함 아님** |
| `eval_reader.py` | PIL 무회전 + 표시 좌표계 쿼드 | **어긋남 — 2026-09-04 에 발견** |

**그래서 과거 `golden_bench` 수치는 좌표계 오염이 아니다.** 재해석할 필요가 없다.

## 네 번째 파일 — 통일 작업이 채점 경로를 빠뜨렸다 (2026-09-04)

위 표는 2026-09-02 시점에 **학습·검출 경로만** 훑었다. 같은 좌표계를 쓰는
**채점 경로(`eval_reader.py`)가 목록에 없었다.** 그래서 G20 이 세 곳을 통일한
뒤에도 평가만 옛 좌표계에 남아, 원본의 83.5%를 옆으로 누운 채 채점했다.

같은 모델·같은 이미지·같은 워프에서 `exif_transpose` 한 줄 차이(표본 300):
**완전일치 14.7% ↔ 90.7%**, 길이 불일치 61.0% ↔ 4.3%.

**학습 입력만 고치고 채점을 빠뜨리면 "고칠수록 지표가 안 오르는" 상태가 된다.**
그 상태에서 나온 저성능 숫자가 워프 기하를 의심하는 가설 문서 한 편을 낳았고,
두 계측 버그를 고치자 재학습 없이 92.9% 가 나왔다 → [[metric-path-not-under-test]]

디코더 관례를 통일할 때는 **이미지를 여는 모든 자리**를 세어야 한다. 학습·검출·
표시뿐 아니라 **채점·진단·분석 스크립트까지.** 이 저장소에서 좌표계 사고는
이걸로 세 번째다(라벨러 프레임 → GM 힌트 이중회전 → 평가 EXIF).

## 여기서 배운 것

이 페이지는 "관례가 갈린다"는 개념은 맞았지만 **가해자 지목이 틀렸다.** 원인이
같아 보인다고 해서 같은 파일이 범인인 것은 아니다. 지목하기 전에 그 파일을
열어서 확인해야 한다 — 이 저장소에서 좌표 사고가 반복되는 이유의 절반이
"확인 없이 이름표를 믿는 것"이다.
