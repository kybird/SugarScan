## Case 1: 코퍼스 크기 곡선 — 방향별 2,000에서 합성 게이트를 넘고 포화한다

### Grounding
- Git Context: `hash:5d85cd4`
- Evidence: `assets_dev/train/band_out/curve_eval.log` · `band_out/eval_*.jsonl`
- Confidence: 5/5

### Hypothesis
합성 밴드 검출망을 **스크래치로** 학습할 때 방향별 몇 장이 필요한가.
모델(BandNet width 1.0, 0.504M)·스텝(8,000)·시드를 고정하고 장수만 바꾼다.
평가는 **굽는 시드가 다른** 세트 V 1,000장(docs/SPEC.md §9.4), 게이트는 IoU 가
아니라 숫자 필드 포함률(§7-3 · §9.5).

### Results
    방향별  학습장수   합격률   세로형   가로형  검출실패  IoU세로  IoU가로  최악프로파일
      500     1000   91.90%  90.11%  93.88%     0   0.9127  0.9373   78.57%
     1000     2000   97.50%  96.77%  98.31%     0   0.9310  0.9516   85.71%
     2000     4000   99.60%  99.81%  99.37%     0   0.9476  0.9629   97.62%
     4000     8000   99.60%  99.62%  99.58%     0   0.9566  0.9708   97.62%
     7998    15996   99.80%  99.81%  99.79%     0   0.9648  0.9758   97.62%

### Analysis
- **합성 게이트(99%)는 방향별 2,000장에서 넘는다.** 그 뒤로 합격률은 거의 평평
  하다(99.60 → 99.60 → 99.80).
- **검출 실패가 전 구간 0이다.** 사전학습 없이 합성 1,000장만으로도 홀드아웃
  전량에서 상자가 나온다. 남는 문제는 '찾느냐'가 아니라 '변을 맞추느냐'다.
- **합격률이 평평해진 뒤에도 IoU 는 계속 오른다**(세로 0.9476→0.9648,
  가로 0.9629→0.9758). 즉 포화한 것은 **게이트 지표**이지 상자 품질이 아니다.
  게이트를 통과율로만 보면 이 개선이 안 보인다.
- **가로형이 세로형과 대등하거나 낫다**(7998 점에서 99.79% 대 99.81%,
  IoU 는 가로가 더 높다). 50:50 으로 균등 생성한 결과다(§9.6). 폐기한 계열에서
  가로형이 실촬 22% 검출 실패하던 것과 방향이 정반대다.
- **최악 프로파일이 97.62% 에 붙어 장수로 안 풀린다.** onetouch_ultra 42장 중
  1장이다. 세 점(2000·4000·7998) 모두에서 불합격인 장은 딱 둘이고 정체가 같다:

      panel_20261002_343  onetouch_ultra  score 0.999  좌 변이 숫자를 31.9px 파고듦
      panel_20261002_631  wide_unknown    score 1.000  우 변이 숫자를 40.9px 파고듦

  둘 다 **가로형**이고 둘 다 **좌우**가 잘린다. 점수가 1.0 에 가까우니 못 찾는
  것이 아니라 **변을 짧게 잡는다.** 폐기된 계열에서 실촬 271장을 쟀을 때 나온
  치우침 패턴(좌 43% · 우 38% 파고듦, 상하는 11~13%)과 같은 방향이다 —
  모델도 코퍼스도 바뀌었는데 같은 방향이 남았다.
- 따라서 다음에 볼 곳은 장수가 아니다. 가로 변 회귀가 왜 짧게 나오는지다.
  후보: 가로형 밴드가 길어서 칸 중심에서 좌우 끝까지의 거리가 크다(stride 16
  에서 짧은변 3~5칸인데 긴변은 10칸 넘는다) · 배정 반경 1.5칸이 긴 축에는
  좁을 수 있다 · GIoU 가 긴 축의 상대 오차에 둔하다.

## Case 2: 합성 게이트 99.6% 가 실촬에서 무너지는 이유 — 배율도 비율도 아닌 배경 내용

### Grounding
- Git Context: `hash:741dc9d` (도구·결과), `hash:628715b` (지름길 자)
- Evidence: `assets_dev/train/_diag/band_real/datacluster_curve_07998*.jsonl`
- 자: `eval_band_real.py --xml --crop --crop-pad --mask-bg`,
  `measure_panel_stats.py shortcut --by`
- Confidence: 4/5

### Hypothesis
BandNet(curve_07998)이 합성 홀드아웃에서 99.60%(세트 V, 굽는 시드가 다름)를
내고도 실촬에서 무너진다. 코퍼스를 500→7,998 로 16배 늘려도 실촬 포함률이
49~58% 에서 움직이지 않았다. 훈련 루프를 재설계해야 하는가?

### Results

**기각 1 — 척도 불일치.** 밴드가 프레임에서 차지하는 비(넓이):
합성 세로형 0.152 · 가로형 0.140(`synth-band --vs canvas`, n=16,000) vs
실촬 0.093(`band-frame`, n=271). 선형으로 0.390 vs 0.305, **1.27배**.
있지만 "예측 넓이 = 기기 전체 넓이의 0.94" 를 설명하지 못한다.

**기각 2 — 비율 지름길.** 합성에서 정답 상자는 유리 쿼드의 거의 고정된 아핀
축소다(세로형 band_w/glass_w 0.812 [p10 0.725 p90 0.874], band_cx 0.497 ±0.025).
그렇다면 "유리 모서리를 찾아 비율만 곱하는" 지름길이 가능하다. 숫자를 한 장도
보지 않는 오라클을 **같은 게이트**(digit_box 100% 포함)에 걸었다
(fit=T 16,000 → test=V 1,000):

    방향별 4파라미터   46.70%
    기기별 96파라미터  69.40%
    학습된 모델        99.60%

30점이 남는다. 유리 안쪽에서 장마다 달라지는 것은 숫자뿐이므로 **모델은 숫자를
읽는다.**

**확인 — 배경 내용.** Datacluster CC0 238장(Datumo 와 기기·촬영자·배경·나라가
전부 다른 독립 코퍼스). 기기 상자는 **자로만** 썼다(기기는 밴드가 아니다):

    입력                        예측/기기넓이  기기안  배경뭄   >=90%안   n
    전체 사진(기준)                    0.94   0.613   32.9%     9.4%   234
    배경만 단색, **배율 동일**          0.36   1.000    2.6%    63.2%   231
    기기 상자 크롭(pad 0.05)           0.20   1.000    0.0%    99.1%   235

배율 교란은 여백 쓸기로 뺐다 — pad 0.5/1.0/2.0 에서 0.77/0.90/0.92 로 전체
사진(0.94)에 수렴한다.

### Analysis
- Confirmed: 성적을 움직이는 것은 **프레임 안의 비기기 내용**이다. 배율이
  아니다(같은 배율에서 배경만 없애면 기기안 0.613→1.000).
- Refuted: 훈련 재설계 · 데이터 증량 · 척도 조정 · 비율 지름길.
- 모델은 두 단계를 배웠다. 2단계(유리 안에서 숫자로 상자를 짚는 일)는 멀쩡하다.
  1단계(프레임의 여러 사각형 중 어느 것인가)가 없다 — **합성에 경쟁 사각형이
  한 번도 나온 적이 없기 때문이다.** 생성기는 기기 바깥을 단색 판(bg_col)으로
  채운다(`synth_panel.py:516` 이 이미 적어 둔 내용).
- 남는 격차: 배경을 없애도 99.1% 가 아니라 63.2% 다. 기기 몸체 자체의 구조
  (버튼·각인·외곽선)도 경쟁 사각형이다 — 두 번째, 더 작은 성분이다.
- Implications: SPEC §9.7("장면과 광학 결손은 일반화에 맡긴다")의 폴백 조건이
  충족됐다. 다만 폴백으로 적어 둔 **실촬 파인튜닝**이 아니라 **생성기가 장면을
  그리는 쪽**이 원인을 직접 겨냥한다. 라이선스도 자유롭다.
- **진단용 오라클을 제품 성적으로 인용하지 않는다** — `--crop`/`--mask-bg` 는
  배포 경로에 없다. 폐기된 계열이 정확히 그 함정(사람이 그린 LCD 쿼드로 잘라
  재기)에서 16.6% 를 78.6% 로 보이게 했다.
