## Case 1: 공개 저장소에 남의 사진이 일주일 올라가 있었다 — 문서 그림 한 장에 섞여서

### Grounding
- Git Context: `hash:b21da36` (제거) · `hash:25a9141` (구조적 예방)
- Evidence: `docs/reports/profile-expansion-compare-2026-09-12.png` (커밋 `411c16f`,
  421,674 바이트) · `git ls-files` 조회 · 미러 클론 재검증
- Confidence: 5/5

### Error

사람이 물었다: "라이센스위반안했지?"

조회해 보니 `git ls-files assets_dev/upstream` 는 0건이었다. 규칙("실사진을
커밋하지 않는다")은 데이터 폴더에 대해서는 지켜지고 있었다. 그런데 **문서
폴더에서 새고 있었다** — `docs/reports/` 의 PNG 한 장 안에 Datumo 실사진 크롭
6장(`1329`·`2502`·`2513`·`1435`·`1438`·`1440`)이 들어 있었다. 2026-09-12 에
커밋됐고, 저장소는 공개였다.

### Analysis

- Root cause: 규칙을 **경로**로 지키고 있었다(`assets_dev/upstream` 는
  gitignore). 사진이 **다른 형식으로 다른 경로에** 들어오는 길은 막혀 있지
  않았다. 비교 그림·몽타주·시트는 실사진을 합성과 나란히 놓는 것이 목적이라
  구조적으로 이 사고를 부른다.
- Why non-obvious: 추적 중인 이미지가 26개였고 그중 23개가 앱 아이콘이었다.
  나머지 3개 중 2개는 그래프였다. **세 개를 다 열어 보기 전에는 알 수 없었다** —
  파일명(`profile-expansion-compare`)만으로는 합성끼리의 비교로 읽힌다.
- Datumo 이용 조건은 **미확인**이다(`docs/LICENSES.md` §4). 허용된다고 말할
  근거가 없으므로 위반 가능성을 전제로 처리했다.

### Fix Code

제거 후 **구조로 막았다** — 같은 사고가 다시 나지 않게 데이터를 저장소 밖으로
옮기고 정션을 걸었다(코드 참조 82곳을 고치지 않았다):

```powershell
New-Item -ItemType Junction `
  -Path 'D:\Project\sugarScan\assets_dev\upstream' `
  -Target 'D:\Project\sugarScan-corpus'
```

그리고 규칙을 **경로가 아니라 용도**로 다시 적었다(`LICENSES.md` §1.4):
조건 미확인·귀속 의무 있는 실사진은 **학습 금지, 검증만 허용**.

### 히스토리 제거 — 로컬만으로는 안 끝난다

커밋은 `origin/main` 포함 원격 4곳에 있었다. **작업 트리가 더러우면
filter-branch 가 거부**하는데, 다른 에이전트의 미완성 작업이 있어 커밋도
stash 도 할 수 없었다. 우회: **미러 클론에는 작업 트리가 없다.**

```bash
git clone --mirror <remote> purge.git
cd purge.git && git filter-branch --index-filter 'git rm --cached --ignore-unmatch -q <path>' -- --all
rm -rf refs/original && git reflog expire --expire=now --all && git gc --prune=now
git push --force --all
```

검증은 **새로 클론해서** 했다 — 같은 저장소에서 확인하면 로컬 객체를 보게 된다.

남은 것: (1) GitHub 은 수거 전까지 커밋 해시로 접근을 허용하므로 Support 요청이
필요하다. (2) **로컬 히스토리에는 아직 그 blob 이 있다** — 로컬이 origin 보다
51 커밋 앞서 있어서, 여기서 푸시하면 되살아난다.

## Case 2: 버튼을 그려야 하나 — 실패를 갈라 보니 순서가 뒤집혔다

### Grounding
- Git Context: `hash:769894f`
- Evidence: `_diag/audit/roboflow_aug_s0.jsonl` · `rf_split.json` 봉인 시험 687장
- Confidence: 4/5

### Hypothesis

사람이 물었다: "합성기에 버튼도 추가해야할까?" 생성기가 버튼을 한 번도 그린
적이 없으므로 버튼 오인이 남는다는 것이 그동안의 의심이었다.

### Results

`aug_s0`, 배포 상자가 숫자 칸을 담는가 기준으로 실패를 갈랐다:

| 모집단 | 성공 | **딴 데** | 일부만 담음 | 미검출 |
|---|---|---|---|---|
| Datumo 272 | 96.7% | 1.5% | 1.8% | 0% |
| Roboflow 개발 586 | 87.7% | 3.9% | 8.4% | 0% |
| Roboflow **봉인 시험** 687 | 91.8% | **0.9%**(6장) | **7.0%**(48장) | 0.3% |

### Analysis

- 버튼·로고 오인이 사는 "딴 데"는 **0.9%** 뿐이다. 지배적 실패는 위치가 아니라
  **잘림 7.0%** 이고, 그건 생성기가 아니라 **손실·타깃**의 문제다.
- 처방 비용이 7배 뒤집힌다: 잘림은 `--grow`/`--under-w` 로 **생성기 작업 0**,
  버튼은 전체 기기 장면으로 1~2일.
- Implications: "어느 개입이 큰가"를 묻기 전에 **실패를 종류별로 세어야 한다.**
  그 전까지 우리는 가장 눈에 띄는 실패(버튼 오인)를 가장 큰 실패로 착각했다.
  눈에 띄는 것과 잦은 것은 다르다.
- 1% 미만 구간은 687장·8시드로도 통계적으로 못 가른다. 전체 기기 장면을
  판정할 때 이걸 미리 알고 시작해야 한다.

## Case 3: 학습 증강을 빼 두고 한 달을 보냈다 — 넣으니 시드 퍼짐이 3분의 1로 줄었다

### Grounding
- Git Context: `hash:e154cac`
- Evidence: `_diag/audit/*.jsonl` 8시드 · `rf_split.json` 봉인 시험 687장
- Confidence: 5/5

### Hypothesis

사람이 물었다: "논문에 따르면 합성데이터만으로 실촬데이터 적합이 이루어진다고
봣다... 데이터증강을 해야하는거아니냐?"

`train_band.py` 는 학습 증강을 **의도적으로 뺐다** — "변이는 생성기가 만든다"
(SPEC §9). 그 원칙의 값은 "무엇이 무엇을 움직였는지 가를 수 있다"였다.

### Results

| 배포 상자가 숫자 칸 포함 | `bg` 8시드 | `aug` 8시드 |
|---|---|---|
| Datumo 272 | 93.9% (SD 1.58) | 96.9% (SD 0.81) |
| Roboflow 개발 586 | 76.3% (SD 4.09) | 85.7% (SD 2.46) |
| Roboflow 봉인 시험 687 | 82.2% (SD **6.35**) | 89.7% (SD **2.22**) |
| 미검출(시험) | 77.9장 | 4.2장 |

합성 VB 도 퇴행 없이 개선(τ=1.2 99.14% → 99.64%, 프로파일 최저 96.61% → 97.92%).

### Analysis

- Confirmed: 네 모집단 전부 개선. 퇴행 0.
- **성적보다 중요한 것은 SD 다.** 봉인 시험 6.35 → 2.22. 이 프로젝트를 한 달간
  괴롭힌 것이 "같은 레시피인데 시드마다 14점 흔들린다"였고, 그래서 ±5점급
  효과를 잴 수 없었다(계획 §11.3). 증강이 그 잡음 자체를 줄였다.
- Why it was missing: 원칙("변이는 생성기가")이 **생성기가 아직 안 그리는
  축**(센서 잡음·JPEG·조명 불균일, SPEC §9.7.4)까지 덮는 것으로 읽혔다.
  원칙은 그 축을 덮으라는 말이 아니었는데 그렇게 작동했다.
- 한계: 블러·밝기·잡음·JPEG·배율/위치를 한꺼번에 켰다. **무엇이 효과를 냈는지
  모른다.** 원칙이 지키려던 것을 실제로 잃었다 — 그 값을 알고 치른 것이다.

## Case 4: 자르는 것과 큰 것은 대가가 다른데 손실은 같게 봤다

### Grounding
- Git Context: `hash:02f1735` · 구현 `hash:769894f`
- Evidence: `_diag/fix2/*.jsonl` 3조건 × 8시드
- Confidence: 5/5

### Hypothesis

사람 관찰: "여전히 원시예측이 숫자도 다 포함하지못하는경우가 많네."
측정하니 봉인 시험 687장에서 **일부만 담음 7.9%** 가 지배적 실패였다.

숫자를 자르면 리더가 못 읽는다(치명). 상자가 크면 τ 안에서는 무해하다.
**GIoU 는 둘을 같게 본다.** 손잡이 둘을 만들어 갈랐다:
- `--grow` 정답 상자를 사방으로 키워 학습 — 모든 상자가 커진다
- `--under-w` **모자란 변에만** 벌점 — 맞는 상자는 안 건드린다

### Results

봉인 시험 687장, 배포 상자가 숫자 칸 포함 / 배포·숫자칸 넓이비 p50:

| 조건 | 포함률 | 크기 p50 | 합성 VB τ=1.2 |
|---|---|---|---|
| `aug` | 89.7% | 2.30 | 99.64% |
| `agrow` | 95.4% | 2.96 | **2.48%** |
| `aunder` | **96.2%** | **2.85** | **99.03%** |
| `aboth` | 96.7% | 3.59 | **0.12%** |

기전: "일부만 담음" 7.9% → 1.7%, "딴 데" 1.7% → 1.9%(그대로).

### Analysis

- **비대칭 손실이 대칭 손실보다 이 과제에 맞다.** 외과적으로 모자란 변만
  고치니 포함률 +6.5점을 크기 +24% 로 샀다. `grow` 는 같은 것을 사면서 모든
  상자를 키운다.
- **`agrow`/`aboth` 의 합성 붕괴는 정의 문제다** — 정답을 키워 학습시키는데
  게이트는 키우기 전 주석과 면적비를 견준다. 능력이 아니라 자가 안 맞는다.
  그래도 사전 등록 규칙을 사후에 고치지 않았고, 크기 대가에서 어차피 `aunder`
  가 이겨 판정이 뒤집히지 않는다.
- **우선순위가 두 번 뒤집혔다.** 어제는 "딴 데 0.9% < 일부만 7.0%" 라 버튼을
  미뤘고, 오늘 잘림을 고치니 "딴 데 1.9% > 일부만 1.7%" 가 됐다. 어제 판단이
  틀린 것이 아니라 **소진된 것**이다. 실패 구성은 개입마다 다시 세야 한다.

## Case 5: 주 지표에 54% 짜리 바닥이 있었다 — 대조군을 안 만들어서 몰랐다

### Grounding
- Git Context: `hash:1c038e9`
- Evidence: `assets_dev/train/diag_prior_memo.py`, `docs/BAND_EXP_PLAN.md` §21.1
- Confidence: 5/5

### Discovery

사람이 "딱봐도 모델이 그냥 학습할때 LCD 의 위치가 있었던 비율을 외운걸로
보인다"고 했다. 외웠는지 재려고 **늘 학습 사전평균 상자만 내놓는 검출기**를
대조군으로 만들었다. 외운 것인지는 기각됐는데, 대조군 쪽에서 다른 것이 나왔다.

```
개발 586            담음     담음 ∧ 면적<=2    면적비 중앙
상수 상자          54.3%         0.0%          6.37
모델 atone        93.5%        47.9%
```

**주 지표로 다섯 회차를 써 온 '배포 담음'의 바닥이 54.3% 였다.** 상자가
면적비 6.37 로 거대하면 아무것도 안 보고도 숫자 칸을 덮는다.

### Analysis

- Why non-obvious: 지표 이름이 "담음"이라 0 에서 시작하는 것처럼 읽힌다.
  그리고 사슬(82.2 -> 89.7 -> 96.2 -> 97.3)이 **움직이기는 했다** — 물렁한
  자도 개입에 반응하므로 바닥을 의심할 계기가 안 생긴다.
- Impact: §18~§20 의 모든 수치가 이 자로 나왔다. 값이 틀린 것은 아니지만
  **"몇 점 올랐다"의 의미**가 달라진다. 게이트(담음 ∧ 면적<=2)는 상수 상자가
  0.0% 라 바닥이 0 이다.
- Action taken: 담음 단독 인용을 금지하고 게이트를 함께 낸다. 대조군 계산을
  `diag_prior_memo.py` 에 고정했다.
- 외운 것인가 자체는 기각이다: 딴 데에서 예측이 사전평균에 **더 멀다**
  (0.290 대 통과 0.238). 다만 **크기**는 사전분포 쪽이다 — 딴 데의 예측
  면적은 정답의 5.06배이고 학습 사전분포(0.0781)가 정답(0.0098)보다 가깝다.

## Case 6: "작은 밴드를 못 봐서 못 맞힌다"를 두 방법으로 고쳤는데 둘 다 더 나빠졌다

### Grounding
- Git Context: `hash:2358849`
- Artifact: `assets_dev/train/_diag/fix5`, `_diag/fix6`, `docs/BAND_EXP_PLAN.md` §20.1·§21
- Confidence: 5/5

### Hypothesis

실촬 밴드는 학습 코퍼스보다 2.3~4배 작다(밴드높이/긴변 합성 0.484 대 실촬
0.118). 작은 밴드를 못 보여 줘서 작은 밴드에서 무너진다 — 보여 주면 낫는다.

### Results

두 가지 **다른** 방법으로 작게 만들었다.

1. 학습 증강의 축소 하한을 내렸다(0.55 -> 0.35 -> 0.20).
2. 생성기의 촬영 배율 하한을 내렸다(0.25 -> 0.10) + 화면 내 위치를 흩었다.
   분포는 실촬에 붙었다: 밴드 0.139(실촬 0.118) · 중심거리 0.101(0.105).

```
밴드 크기 사분위별 (Roboflow 개발 586, 시드 4)
             Q1 가장작음    Q2     Q3    Q4 가장큼
atone  통과      90.6     95.4   94.3     93.8
       딴 데      5.4      1.7    1.5      0.2
ascene 통과      86.1     91.1   93.0     90.6
       딴 데      9.4      4.1    1.9      1.2
afar   통과      84.6     88.0   92.6     88.8
       딴 데     11.4      6.3    2.1      0.7
```

증강 쪽도 같다(§20.1): Q1 통과 91.3 -> 90.1 -> 86.5.

### Analysis

- Confirmed/Refuted: **기각.** 노린 칸(Q1)이 매번 가장 크게 나빠졌고
  용량-반응이 반대 방향으로 단조다.
- 첫 실패 때 세운 설명("증강은 이미 그려진 896 그림을 또 줄여 획을 뭉갠다")은
  두 번째 실패에 **적용되지 않는다** — 생성기 포즈 단계에서 작게 앉혔으니
  획은 원래 해상도에서 출발한다. 서로 다른 기전인데 결과가 같다는 것이
  가설 자체를 무너뜨린다. 설명이 하나 반박됐을 때 가설을 살리려고 두 번째
  설명을 짜는 대신, **다른 방법으로 같은 개입을 재는 것**이 갈랐다.
- Key metrics: 밴드가 /16 특징맵(26x26)에서 차지하는 세로 칸 수로 보면
  절벽이 보인다.

```
실촬 Roboflow 개발   중앙 3.0칸 · p10 1.9 · p90 4.6
세로 칸 수      n      통과     딴 데
  ~2.5       187    90.9%    5.3%
2.5~3.5      211    95.6%    0.9%
3.5~5        157    94.5%    0.5%
구판 합성 중앙 12.6칸 · 새 합성기 3.6칸
```

- Implications: 데이터 분포가 아니라 **특징맵 해상도**가 무는 것으로 보인다.
  학습을 2~3칸 구간으로 옮기면 약한 감독이 다수가 되어 전체가 흐려진다.

## Case 10: 획 선명도 자가 잡음을 재고 있었다

### Grounding
- Git Context: `hash:5944d48`
- Evidence: `assets_dev/train/diag_stroke_sharp.py`
- Confidence: 5/5

### Error

생성기 배율을 내리기 전에 "작게 그리면 획이 뭉개지지 않나"를 재려고
선명도 자를 만들었다(에지세기/대비). 합성이 일관되게 무디게 나왔다.

```
밴드높이px            합성 n       합성    실촬 n       실촬
20~40              31   0.9880      38   1.3707
40~60              31   0.7589      65   0.8409
60~90              47   0.5382      44   0.6136
```

LONG_SIDE 를 896 -> 3072 로 올려도 선명도가 0.609 -> 0.617 로 안 움직여
이상해서, 밴드 **바깥 평평한 자리**의 에지 에너지를 쟀다.

```
합성 (새 생성기)  n=80  에지 0.000  표준편차 0.00
실촬 Roboflow    n=80  에지 11.447  표준편차 4.06
```

### Environment Context
- Packages: cv2.Sobel 기반 자작 지표
- Migration Issue: No

### Fix Code

```python
# 결론 철회. 잡음 축은 학습 증강이 이미 덮는다:
#   생성기 원본 0.000 -> --aug 9.520  대  실촬 11.447
# 생성기를 손대지 않는다.
```

### Analysis

- Root cause: mean(|grad|)/contrast 는 **잡음도 에지로 센다.** 합성은
  평평한 자리가 정확히 0 이고 실촬은 11.4 다. 두 코퍼스 차이의 상당 부분이
  획이 아니라 센서 잡음·압축 흔적이었다.
- Why it failed: 자를 만들 때 "무엇이 이 값을 올릴 수 있는가"를 안 적었다.
  획도 올리고 잡음도 올린다. **둘을 가르는 대조(평평한 자리)를 자 안에
  넣었어야 했다.**
- How it was fixed: 결론을 철회하고 생성기를 안 건드렸다. 이 자를 굽기
  **전에** 돌린 것이 값을 했다 — 돌린 뒤였으면 "획이 뭉개져서 졌다"는
  그럴듯한 사후 설명이 남았을 것이다.
