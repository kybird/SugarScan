## Case 1: 공개 저장소에 남의 사진이 일주일 올라가 있었다 — 문서 그림 한 장에 섞여서

### Grounding
- Git Context: `hash:b21da36` (제거) · `hash:25a9141` (구조적 예방)
- Evidence: `docs/reports/profile-expansion-compare-2026-09-12.png` (커밋 `411c16f`,
  421,674 바이트) · `git ls-files` 조회 · 미러 클론 재검증
- Confidence: 5/5

### Error

사람이 물었다: "라이센스위반안했지?"

조회해 보니 `git ls-files assets_dev/upstream` 는 0건이었다. 규칙("실사진을
커밋하지 않는다")은 데이터 폴더에 대해서는 지켜지고 있었다. 그런데 **문서
폴더에서 새고 있었다** — `docs/reports/` 의 PNG 한 장 안에 Datumo 실사진 크롭
6장(`1329`·`2502`·`2513`·`1435`·`1438`·`1440`)이 들어 있었다. 2026-09-12 에
커밋됐고, 저장소는 공개였다.

### Analysis

- Root cause: 규칙을 **경로**로 지키고 있었다(`assets_dev/upstream` 는
  gitignore). 사진이 **다른 형식으로 다른 경로에** 들어오는 길은 막혀 있지
  않았다. 비교 그림·몽타주·시트는 실사진을 합성과 나란히 놓는 것이 목적이라
  구조적으로 이 사고를 부른다.
- Why non-obvious: 추적 중인 이미지가 26개였고 그중 23개가 앱 아이콘이었다.
  나머지 3개 중 2개는 그래프였다. **세 개를 다 열어 보기 전에는 알 수 없었다** —
  파일명(`profile-expansion-compare`)만으로는 합성끼리의 비교로 읽힌다.
- Datumo 이용 조건은 **미확인**이다(`docs/LICENSES.md` §4). 허용된다고 말할
  근거가 없으므로 위반 가능성을 전제로 처리했다.

### Fix Code

제거 후 **구조로 막았다** — 같은 사고가 다시 나지 않게 데이터를 저장소 밖으로
옮기고 정션을 걸었다(코드 참조 82곳을 고치지 않았다):

```powershell
New-Item -ItemType Junction `
  -Path 'D:\Project\sugarScan\assets_dev\upstream' `
  -Target 'D:\Project\sugarScan-corpus'
```

그리고 규칙을 **경로가 아니라 용도**로 다시 적었다(`LICENSES.md` §1.4):
조건 미확인·귀속 의무 있는 실사진은 **학습 금지, 검증만 허용**.

### 히스토리 제거 — 로컬만으로는 안 끝난다

커밋은 `origin/main` 포함 원격 4곳에 있었다. **작업 트리가 더러우면
filter-branch 가 거부**하는데, 다른 에이전트의 미완성 작업이 있어 커밋도
stash 도 할 수 없었다. 우회: **미러 클론에는 작업 트리가 없다.**

```bash
git clone --mirror <remote> purge.git
cd purge.git && git filter-branch --index-filter 'git rm --cached --ignore-unmatch -q <path>' -- --all
rm -rf refs/original && git reflog expire --expire=now --all && git gc --prune=now
git push --force --all
```

검증은 **새로 클론해서** 했다 — 같은 저장소에서 확인하면 로컬 객체를 보게 된다.

남은 것: (1) GitHub 은 수거 전까지 커밋 해시로 접근을 허용하므로 Support 요청이
필요하다. (2) **로컬 히스토리에는 아직 그 blob 이 있다** — 로컬이 origin 보다
51 커밋 앞서 있어서, 여기서 푸시하면 되살아난다.

## Case 2: 버튼을 그려야 하나 — 실패를 갈라 보니 순서가 뒤집혔다

### Grounding
- Git Context: `hash:769894f`
- Evidence: `_diag/audit/roboflow_aug_s0.jsonl` · `rf_split.json` 봉인 시험 687장
- Confidence: 4/5

### Hypothesis

사람이 물었다: "합성기에 버튼도 추가해야할까?" 생성기가 버튼을 한 번도 그린
적이 없으므로 버튼 오인이 남는다는 것이 그동안의 의심이었다.

### Results

`aug_s0`, 배포 상자가 숫자 칸을 담는가 기준으로 실패를 갈랐다:

| 모집단 | 성공 | **딴 데** | 일부만 담음 | 미검출 |
|---|---|---|---|---|
| Datumo 272 | 96.7% | 1.5% | 1.8% | 0% |
| Roboflow 개발 586 | 87.7% | 3.9% | 8.4% | 0% |
| Roboflow **봉인 시험** 687 | 91.8% | **0.9%**(6장) | **7.0%**(48장) | 0.3% |

### Analysis

- 버튼·로고 오인이 사는 "딴 데"는 **0.9%** 뿐이다. 지배적 실패는 위치가 아니라
  **잘림 7.0%** 이고, 그건 생성기가 아니라 **손실·타깃**의 문제다.
- 처방 비용이 7배 뒤집힌다: 잘림은 `--grow`/`--under-w` 로 **생성기 작업 0**,
  버튼은 전체 기기 장면으로 1~2일.
- Implications: "어느 개입이 큰가"를 묻기 전에 **실패를 종류별로 세어야 한다.**
  그 전까지 우리는 가장 눈에 띄는 실패(버튼 오인)를 가장 큰 실패로 착각했다.
  눈에 띄는 것과 잦은 것은 다르다.
- 1% 미만 구간은 687장·8시드로도 통계적으로 못 가른다. 전체 기기 장면을
  판정할 때 이걸 미리 알고 시작해야 한다.
