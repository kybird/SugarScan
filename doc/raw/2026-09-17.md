## Case 1: 층 중앙값 하나로 축을 판정했다가 이상치 한 장을 원인으로 보고했다

### Grounding
- Evidence: `docs/reports/gm-preproc-letterbox-ab-2026-09-16.md` 「2026-09-17 정정」절 ·
  `assets_dev/train/gm_preproc_ab.py` `--paired` ·
  `assets_dev/train/diag_gm_candidate_tie.py`
- Confidence: 5/5

### Discovery
전처리 A/B 에서 채널 축(학습 BGR / 추론 RGB)을 고친 팔이 **가로 층에서 나쁘다**
고 보고했다. 근거는 층별 IoU 중앙값(0.799 → 0.768)과, 한 장이 0.526 → 0.039 로
무너진 것이었다. 그 장을 "채널 축의 불안정성"이라고 적었다.

사람이 물었다 — **"채널순서가 죽은건 왜그렇지 화일포맷문제냐 우리 리더가
일관성이 없는거냐?"** 답하려고 재 보니 내 귀속이 틀렸다.

짝지어 보면(같은 장, 같은 체크포인트, 전처리만 다름):

```text
전체 n=405  승 161 · 패 95 · 무 149  중앙 +0.0032  평균 +0.0080
가로 n=42   승  5 · 패 14 · 무  23  중앙 -0.0044  평균 -0.0195
세로 n=363  승 156 · 패 81 · 무 126  중앙 +0.0054  평균 +0.0112
```

가로는 **절반 이상이 무승부**이고 중앙값과 평균이 다섯 배 갈린다 — 꼬리가
평균을 끌고 있다는 신호다.

### Environment Context
- Packages: sugartrain · YOLOX
- Migration Issue: No

### Analysis
- Root cause(보고의): n=45 짜리 층의 **중앙값 하나**로 축을 판정했고, 그 층에
  이상치가 하나 있다는 사실을 함께 보지 않았다. 승·패·무를 세었으면 무승부
  23/42 가 먼저 보였을 것이다.
- Root cause(현상의): 무너진 장은 채널과 무관했다. 두 전처리의 입력이 픽셀
  평균 **3.37/255** 밖에 안 다르고, 그 사진은 |R−B| 평균 **6.7** 로 거의
  무채색이라 R↔B 를 바꿔도 화소가 안 변한다. 진짜 원인은 **후보 두 개가
  0.3% 차이로 붙어 있는데 넓이가 33.5배 다른 것**이다 — 기기 전체
  2417×2920 과 작은 조각 463×455. 무엇이든 조금 흔들면 top-1 이 뒤집힌다.
- 대조군: 같은 방식으로 1598 을 보면 입력 차가 더 큰데도(12.98) 1위가 77% 차로
  명확해 상자가 안 뒤집힌다. 즉 "입력이 달라서"가 아니라 "모델이 못 정해서"다.
- How it was fixed: 보고서에 정정 절을 붙이고, 자에 `--paired` 를 넣어 승·패·무
  와 꼬리 이름을 같이 찍게 했다. 카드 Result 에도 정정 노트를 달았다.
- 같은 날의 거울: Case 9 는 **문턱 세기가 연속량의 이동을 삼키는** 반대 방향을
  지적했다. 한쪽에서 집계의 함정을 잡아 놓고 다른 쪽에서 반대 함정에 빠졌다 —
  요약 통계 하나로 판정하지 않는다는 규칙이 두 방향 모두에 적용된다.

## Case 2: "실촬 0장"이 데이터만 세고 가중치를 안 셌다

### Grounding
- Evidence: `assets_dev/train/yolox_synthband_exp.py` 머리말 ·
  `doc/kanban/cards/합성만으로-사진에서-값까지-한-번-통과시킨다.md` Goal ·
  `docs/LICENSES.md` §1.1
- Confidence: 5/5

### Discovery
마일스톤 문구는 **"실촬은 전 구간에서 뺀다(학습도 검증도)"** 다. 나는 검출기를
학습하고 결과마다 "실촬 0장"이라고 적었다. 학습 데이터는 정말 0장이었다.

사람이 라이선스를 물었을 때 계보를 그려 보고 알았다 — 그 검출기는
`gmscreen/best_ckpt.pth` 에서 파인튜닝했고, **gmscreen 은 Roboflow 실촬
1,276장으로 학습된 체크포인트**다. 데이터에는 실촬이 없지만 **가중치에는 있다.**

사람 지적: **"마일스톤경로로 갈려고했는데 왜 지금 또 저렇게 되버린거야."**

### Environment Context
- Packages: sugartrain · YOLOX
- Migration Issue: No

### Analysis
- Root cause: 검출기 카드 Goal 이 "기존 gmscreen 체크포인트(화면 검출,
  2026-08-28)에서 출발해"라고 **명시**했고, 나는 그대로 따랐다. 카드를 집을 때
  **상위 마일스톤 문구와 대조하지 않았다.** 두 문장이 저장소 안에서 서로
  어긋나 있었고 둘 다 사람이 쓴 것이다.
- Why non-obvious: "실촬 0장"은 데이터를 세면 참이다. 가중치를 세야 거짓이
  드러난다. **세는 대상이 하나 빠져 있었고, 빠진 것을 세지 않으면 검산이
  통과한다.**
- How it was fixed: 사람 결정으로 시작점을 `weights/yolox_nano.pth`
  (COCO 사전학습)로 바꾼다. COCO 는 일반 사물 80종이라 혈당계 도메인과
  무관하다(그 체크포인트 `cls_preds` 80채널로 확인). 부수 효과로 Roboflow
  CC BY 4.0 귀속 의무가 사라진다.
- Where the rule now lives: `yolox_synthband_exp.py` 머리말에 "시작점 규칙 —
  되돌리지 말 것"으로 박았다. 코드에 두지 않으면 다음 사람이 카드 Goal 을 보고
  다시 gmscreen 을 집는다.
- 일반화: **파생물의 계보는 데이터에서 끝나지 않는다.** "X 를 쓰지 않는다"를
  검산할 때 학습 데이터·사전학습 가중치·라벨 출처를 각각 세야 한다.
  하나만 세고 통과시키면 나머지가 조용히 따라 들어온다.

## Case 3: 사전학습이 가르친 것과 우리가 시킨 것이 달랐다 — 밴드는 LCD 의 40%

### Grounding
- Git Context: `hash:f92b874`
- Artifact: `_diag/synthband_v0|v1_coco|v2_a2/{B,C}.jsonl` ·
  `screen_boxes.jsonl`(사람 LCD 411) · `band_boxes.jsonl`(사람 밴드 277)
- Confidence: 5/5

### Hypothesis
사람이 웹툴에서 Roboflow 라벨을 보고 지적했다 — **"얘는 LCD 를 라벨링한거고,
우린 밴드를 라벨해서 훈련했잖아."** 사전학습 체크포인트(`gmscreen`)가 배운
목표와 우리가 시킨 목표가 다르다. 그 불일치가 실제로 얼마나 큰가, 그리고
그것이 성적에 어떻게 나타나는가.

### Results

같은 사진에 LCD 라벨과 밴드 라벨이 **둘 다** 있는 119장에서:

```text
밴드 넓이 / LCD 넓이   p10 0.301 · 중앙 0.391 · p90 0.460
밴드가 LCD 안에 완전히 든 장   119 / 119
```

세 체크포인트를 같은 세트·같은 정답으로(분모 동일) 나란히:

```text
세트 B (n=1000)        실패   IoU중앙   IoU최소   필드p1
v0 (gmscreen+합성900)     1   0.9179   0.7340   0.9720
v1 (COCO+합성900)        10   0.8943   0.2865   0.9312
v2 (COCO+합성5000)        0   0.9567   0.8534   1.0000

세트 C (n=300)
v0   0   0.9144   0.6501
v1   5   0.8940   0.6563
v2   0   0.9553   0.8409
```

### Analysis
- Confirmed: 목표는 어긋났지만 **헛것은 아니었다.** 밴드는 LCD 의 부분집합이고
  (119/119 완전 포함) 넓이로 약 40% 다. gmscreen 이 배운 "혈당계에서 화면은
  여기다"가 그대로 쓸모 있었고, 모델은 상자를 40% 로 조이는 것만 새로
  배우면 됐다. **v0 > v1 이 그 전이의 크기다.**
- 그런데 **v2 가 데이터만으로 그 전이를 넘어섰다.** 즉 목표가 어긋난
  사전학습이 주던 이득은 합성 4,100장으로 대체 가능한 수준이었다.
  합성이 공짜인 도메인에서는 **전이보다 양이 싸다.**
- Key metric: IoU 최소가 0.65 → 0.84. 한 장을 고친 것이 아니라 **꼬리가
  사라졌다.** 2026-09-17 Case 1 에서 해부한 "특별한 성질 없는 한계 장"이
  학습이 얇아서 생긴 자리였다는 것이 이것으로 확인된다.
- Implications: 시작점에서 `gmscreen` 을 뺐으므로 그와 함께 딸려 오던 셋이
  파이프라인에서 사라진다 — 목표 불일치(LCD vs 밴드) · 라벨 거칢(전부 축정렬
  외접 사각형) · Roboflow 기기 다양성 부족. 라이선스로도 CC BY 4.0 귀속이
  빠진다(docs/LICENSES.md §1.1).
- 나란히 놓지 않은 것: A val AP(v0/v1 0.818/0.770 vs v2 0.945)는 분모가 다르다
  (A val 100장 vs A2 val 300장). B·C 만 비교 가능하다.

## Case 4: 증강 축이 난수가 아니라 예외 경로였다 — 촬영 배율

### Grounding
- Git Context: `hash:fe0ebc5`
- Evidence: `assets_dev/train/measure_panel_stats.py coco` · 탐침 `synth_coco/Z1` · 통제군 `synth_coco/P00`
- Confidence: 5/5

### Discovery
사람이 Roboflow 실촬 라벨을 보고 "확대축소도 필요할거같더라"고 했다.
합성기에는 `zoom` 변수가 **이미 있었다.** 그래서 처음엔 "있는데 폭이 좁은가"
로 보였지만, 코드를 읽으니 난수가 아니었다:

```python
for zoom in (1.0, 0.92, 0.84, 0.76, 0.68, 0.60):
    Mk, Mr = _mats(1.0, zoom)
    if _in(_warp_pts(_glass0, Mk, Mr)):
```

쿼드가 캔버스를 넘칠 때만 내려가는 **예외 사다리**다. 기본이 늘 1.0 이라
유리가 항상 캔버스를 꽉 찼다. 변수 이름과 값의 범위만 보면 "0.60~1.0 을
흔든다"로 읽히지만 실제 분포는 1.0 에 붙은 스파이크였다.

### Analysis
- **왜 눈에 안 띄었나**: 증강 축의 존재를 *이름*으로 확인하면 걸린다.
  `zoom` 이 있고 범위도 있으니 있는 것처럼 보인다. 걸러낸 것은 **산출물의
  분포를 잰 것**이다 — 상자의 선형 배율 퍼짐 p90/p10 이 실촬 1.90 배인데
  합성은 1.21 배였다. 축의 존재가 아니라 축의 **분포**를 재야 한다.
- **모집단이 다른데 어떻게 비교했나**: 실촬 상자는 '전체사진 속 LCD',
  합성 상자는 '기기크롭 속 밴드'다. 절대값은 못 맞댄다. 대신 **퍼짐 비율은
  무차원**이라 비교된다. 자가 그 주의를 출력에 찍게 했다.
- **폭을 계산으로 못 정한다**: 여백 난수가 이미 1.21 배를 만들고 있어
  1.21 x 1.61 = 1.95 를 기대했는데 실측은 1.64 였다. 두 균등난수의 곱은
  분위수가 곱해지지 않는다. 측정으로 (0.42, 1.0) 을 골라 1.97 배를 얻었다.
- **통제가 성립했는지 확인**: 같은 탐침에서 종횡비가 소수점 넷째자리까지
  그대로였다(p10 1.3353 · 중앙 1.5103 · p90 1.7209). 배율만 움직였다.
- **딸려 나온 버그**: 워프 경계색이 `body_col` 이었다. 줌이 예외 경로일
  때는 가장자리 실오라기라 무해했지만, 난수로 돌리는 순간 화면의 상당
  부분이 몸체색 판이 된다. 물러나 찍으면 드러나는 것은 몸체가 아니라
  촬영 장소다 — `bg_col`(826행이 이미 쓰던 값)로 고쳤다.
  **드문 경로를 흔한 경로로 바꾸면 그 경로의 근사가 드러난다.**
- 각도는 반대였다 — 이미 난수였다(roll ±15° 는 2026-09-15 사람 결정).
  그리고 기울기는 실사진으로 **채점할 수 없다**: 사람 라벨도 검출기 출력도
  전 장이 0.00° 축정렬이다(`band_det_tilt_real.py` 머리말). 설계값이다.

## Case 5: 사람이 "라벨할 수 없다"고 선언한 장을 정답으로 쓰고 있었다

### Grounding
- Git Context: `hash:1b7dc65`
- Evidence: `assets_dev/train/band_label_excluded.jsonl` · `_diag/synthband_real/v2_scorable/scorable.jsonl`
- Confidence: 5/5

### Error
`eval_synthband_real.py` 가 `band_exclusions.drop()` 을 **한 번도 부르지 않았다.**
`band_exclusions.py` 는 2026-09-14 에 사람 판정으로 세운 단일 출처인데
(머리말: "사진이 숫자칸 영역을 잘라 먹었으면 제외한다"), 평가 경로가 그 파일을
import 하지도 않았다.

제외 선언 5장은 **전부 가로형**이다:
    frame-cuts-digit-field   3장
    no-upright-normalization 2장
그리고 5장 모두 내가 쓰던 평가 모집단(가로형 46장) 안에 있었다 — 11% 다.

### Fix Code
```python
from band_exclusions import load_excluded
...
excluded = set(load_excluded())
ids = [i for i in ids if i not in excluded]
n_dropped = n_before - len(ids)
print(f"  사람 제외 선언으로 뺀 장 {n_dropped} (band_label_excluded.jsonl)")
```

### Analysis
- **근본 원인**: 제외 목록은 "라벨 품질"의 축으로 만들어져 라벨링·분할 경로에만
  꽂혔고, 나중에 생긴 평가 경로가 그 축을 몰랐다. `band_exclusions.drop()` 이
  "뺀 수를 인쇄한다"는 배려까지 갖춘 좋은 API 였는데 **부르는 쪽이 없었다.**
- **왜 안 들켰나**: 빠진 5장이 검출은 됐다. 실패 수가 안 움직이니 이상 신호가
  없었다. 움직인 것은 IoU 중앙값이었고(가로형 0.7366 -> 0.7556), 그 방향이
  "좋아지는" 쪽이라 더더욱 의심할 계기가 없었다. **사람이 못 그린다고 한 라벨과
  겨루면 검출기는 맞게 내고도 진다.**
- 같은 조회에서 모집단 자체도 틀려 있었다. 평가가 기기 단절 분할의 id 목록
  (258장)을 쓰고 있었는데, 그 분할은 **실사진 파인튜닝용**이다. 합성만으로
  학습한 모델에는 누수가 성립하지 않아 정답이 있는 장을 버릴 이유가 없다.
  사람 지적: "실촬은 훈련에사용하지 않으니 평가로 사용할수있는거아니야?"
  실측 — 채점 가능 276장, 사람 제외를 빼면 271장(세로형 226 · 가로형 45).
- **함께 잰 천장**: 코퍼스 사진 2,512장 중 가로형은 51장이고 그 51장은 **이미
  전부 밴드 라벨이 붙어 있다**(라벨 없는 가로형 0장). 즉 가로형 평가 모집단은
  라벨을 더 붙여 늘릴 수 없다 — 천장이 코퍼스 자체다.

## Case 6: 배제한 데이터셋을 자로 썼다 — 그리고 그 값이 생성기로 들어갔다

### Grounding
- Git Context: `hash:fe0ebc5`
- Evidence: `assets_dev/train/synth_panel.py` CAM_ZOOM_RANGE 주석 · `docs/LICENSES.md` §1.1

### Error
사람 지적: "roboflow 데이터셋은 배제하기로했다 맞지?"

맞다. Roboflow 두 데이터셋은 CC BY 4.0 이고, 저작자 표시 의무 때문에 이 계열
작업에서 빠져 있다(`docs/LICENSES.md` §1.1 계보표). 나는 그것을 **학습에는
쓰지 않았지만 자로 썼고**, 거기서 나온 수치에 합성기의 설계값
`CAM_ZOOM_RANGE = (0.42, 1.0)` 을 맞췄다. 근거가 코드 주석 · 커밋 메시지
`fe0ebc5` · 이 문서 Case 4 에 모두 박혔다.

게다가 **모집단이 틀렸다.** Roboflow 는 우리 코퍼스가 아니라 별개 이미지
세트인데, 거기서 잰 LCD 넓이비 0.0562 를 "실촬 수치"라고 말했다.
우리 코퍼스(평가 모집단 271장)에서 다시 재니 0.2403 이었다 — **4배 틀렸다.**
그 틀린 값으로 "합성과 실촬의 배율 격차가 넓이 8.6배"라는 진단을 세웠고,
바른 값으로는 2.0배다.

### Fix Code
```python
# 우리 코퍼스에서, 평가 모집단과 같은 장에서 잰다.
#   python measure_panel_stats.py band-frame
#   -> 사람 밴드 라벨 + LCD 쿼드가 있고 사람 제외 선언에 없는 장, n=271
```
`CAM_ZOOM_RANGE` 는 **값을 고치지 않고** 근거 무효를 표시했다 —
`no-real-photo-ruler-for-synth` 가 합성 설계값을 실사진 측정으로 되먹이는 것을
금지하므로, 사람이 보고 선언해야 한다.

### Analysis
- **근본 원인**: 배제의 범위를 "학습 데이터"로만 읽었다. 라이선스가 이유인
  배제는 **그 데이터로 정한 설계값**까지 포함한다 — 설계값은 저장소에 남아
  계속 산출물을 만들기 때문이다. 계보가 데이터에서 가중치로 흐르는 것과
  같은 형태다.
- **같은 실수의 두 번째 판**: 2026-09-16 에 "실촬 0장 학습"이라고 보고했는데
  시작점 체크포인트가 실촬로 학습된 것이었다(데이터만 세고 가중치를 안 셌다).
  이번은 **학습만 보고 자를 안 봤다.** 축이 하나 늘었을 뿐 형태가 같다.
- **왜 안 들켰나**: Roboflow 는 열람 도구(webtool)에 열려 있어서 손이 닿기
  쉬웠고, "실촬 분포"라는 말이 어느 실촬인지 묻지 않고 지나갔다.
  숫자에 모집단을 적는 규칙이 있었는데(`concepts/metric-provenance`),
  모집단 이름은 적었지만 **그 모집단을 써도 되는지는 묻지 않았다.**
- **딸린 오진**: 8.6배라는 틀린 격차로 "전체 사진 성적 붕괴는 배율 때문"이라고
  설명했다. 바른 값 2.0배(선형 1.42배)로는 그 설명이 약하다. 실제로 예측
  상자를 조회하니 94.9%가 여전히 LCD 안에 들고 넓이가 정답의 1.7배였다 —
  배경으로 도망간 것이 아니라 밴드 대신 화면을 문 것이다.

## Case 7: [폐기] 합성 규모 곡선 — 방향별 몇 장이면 되는가

### Grounding
- Evidence: doc\kanban\abandoned\합성-규모-곡선-—-방향별-몇-장이면-되는가.md
- Confidence: 4/5

### Discovery
이 길은 아니었다 — 카드가 폐기됐다. 폐기 사유(안티패턴 원재료):

사람 결정(2026-09-17): 이전 모델 실험을 전부 폐기하고 구조부터 다시 설계한다(CLAUDE.md, 커밋 5b09116). 이 카드는 폐기된 구조(depthwise 를 안 켠 2.242M, COCO 60% 전이) 위에서 '몇 장이면 되는가'를 재는 것이라 답이 나와도 새 구조로 옮길 수 없다.

살려 둘 것 — 새 설계에서 다시 쓴다:
1) 스텝을 고정하고 장수만 바꾼다. 에폭 25 고정이면 200장 세트 300스텝 대 6,400장 세트 10,000스텝으로 33배 차이라 장수와 계산량이 뒤섞인다.
2) 에포크 길이는 이미지 반복으로 맞춘다. YOLOX 는 no_aug 구간에서 eval_interval 을 무시하고 매 에포크 평가하므로, max_epoch 를 키우면 평가가 시간을 다 먹는다(실측 32초/에포크, 런 하나 3시간 15분, 체크포인트 6GB).
3) 한 번 굽고 중첩 부분집합으로 자른다. 각각 다른 시드로 구우면 인접 점 차이에 시드 잡음이 섞인다.
4) 게이트는 IoU 가 아니라 숫자 필드 포함률이다. IoU 는 양방향으로 틀린다 — IoU<0.75 인 41장 중 19장은 상자가 커서 낮았고(리더에 무해), IoU>=0.75 인데 포함률<0.95 인 장이 62장이었다.

코드는 남겨 둔다(build_scaling_sets.py · run_scaling_curve.sh · yolox_scale_*_exp.py · synth_coco/S_scale). 새 구조가 정해지면 exp 만 갈아끼우면 된다.

### Analysis
- Why non-obvious: 다음 세션이 같은 벽에 다시 부딪히지 않게 하는 기록이다.
- Action taken: 주기 compile에서 안티패턴 승격 후보로 검토할 것.
