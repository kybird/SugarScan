## Case 1: hold-out 정의가 레거시 파일이었다 — 학습한 장 1,169건이 평가에 섞여 있었다

### Grounding
- Git Context: `hash:86b7613`
- Evidence: `eval_reader.py` 수정 전 `hold-out total=2138 exact=2034 (95.1%)` /
  수정 후 `total=1122 exact=1042 (92.9%)` — 캐시 기준 수치와 자릿수까지 일치
- Confidence: 5/5

### Error
`eval_reader.py` 가 `labeled.jsonl` 에 있는 id 를 평가에서 제외했다. 그 파일은
**옛 밴드 라벨**(프레임 검증 이전, 2026-09-04 에 `band_boxes.jsonl` 로 대체돼
이제 아무도 안 읽는다)이고 리더 학습셋과는 358장 중 203장만 우연히 겹쳤다.

### Fix Code
```python
# hold-out 의 정의는 리더가 학습한 장을 뺀 것이다. 정본은 캐시의 real_train_ids.
trained = {str(v) for v in np.load(str(CACHE))["real_train_ids"]}
...
if cid in trained:
    continue
```

### Analysis
- Root cause: 제외 집합의 **정본이 어디인지** 정해지지 않아, 이름이 비슷한
  레거시 파일이 그 역할을 하고 있었다.
- 양방향으로 틀렸다: 멀쩡한 356장이 평가에서 빠져 **라벨러의 '판독' 칸이 비어
  보였고**(사용자가 "인식 실패냐"고 물어서 드러났다), 동시에 **학습셋 1,372장 중
  1,169장이 평가에 섞여** 성적이 부풀려졌다.
- 사용자 질문이 아니었으면 안 나왔다. UI 의 빈칸이 데이터 파이프라인의 정의
  오류를 드러낸 경로다.

## Case 2 (verification): TTA 를 거절이 아니라 **투표**에 쓰면 답까지 고쳐진다

### Grounding
- Git Context: `hash:8ca74e3` · 도구 `assets_dev/train/diag_tta_vote.py`
- Evidence: holdout 1,122장. 기본 greedy 94.83%/위험군 1.60% → TTA 다수결(N=8)
  96.88%/1.07%. **오답 58건 중 복구 29건, 정답 1064건 중 파손 6건 → 순증 +23**
- Confidence: 5/5

### Results
| | 완전일치 | 위험군 |
|---|---|---|
| 기본 greedy | 94.83% | 1.60% |
| TTA 다수결 | **96.88%** | **1.07%** |

배포형(확신도 낮은 장에만 TTA): τ=0.70 이면 **평균 추론 1.87회**로 95.54%.
τ=0.99 면 5.46회로 96.43%. 전량이면 9회로 96.88%.

### Analysis
- 오늘 처음으로 **완전일치와 위험군이 동시에** 좋아졌다. 거절은 틀린 것을
  버릴 뿐이고 투표는 답을 고친다.
- 복구 사례가 `18→184`·`23→233`·`10→184` 처럼 **자릿수가 무너졌던 것들**이다.
  프레이밍이 흔들리면 살아나는 종류라는 뜻.
- **대조군을 함께 쟀다.** 사용자 요청은 "틀린 것만 적용"이었지만 배포에서는
  무엇이 틀렸는지 모르고, 정답 쪽 파손(6건)을 안 세면 "실패만 보고 결론"이
  된다 → [[aggregate-hides-stratified-failure]]
- 한계: 파손 6건이 있다(`179→175`·`100→180`). 다수결이 항상 옳지는 않다.

## Case 3 (discovery): 승격 게이트의 "완전일치 ≥98% + 미인식 ≤5%" 는 전체 기준으로 읽으면 **산술적으로 불가능**하다

### Grounding
- Git Context: `hash:8ca74e3`
- Evidence: 5% 를 거절하면 전체 기준 완전일치의 상한이 95% 다. 투표+거절
  결합 실측에서 채택분 기준으로는 득표율 0.667 에서 99.54%, 0.889 에서 99.90%
- Confidence: 5/5

### Discovery
`IMPLEMENTATION_PLAN.md` §2.7 의 게이트 세 조건 중 둘이 **서로 모순**이다.
"완전일치 ≥98%" 를 **전체 표본 기준**으로 읽으면 미인식 5% 와 동시에 만족할 수
없다. **채택분 기준**("값을 낸 것 중 98% 가 맞다")으로 읽어야 성립한다.

투표+거절 결합 실측:

| 요구 득표율 | 채택분 완전일치 | 치명적 오독 | 미인식 |
|---|---|---|---|
| 0.667 | 99.54% | 0.45% | 4.0% |
| 0.778 | 99.72% | 0.27% | 5.3% |
| 0.889 | 99.90% | 0.09% | 7.7% |

### Analysis
- 채택분 해석에서는 완전일치 조건이 전 구간에서 충족되고, **남은 병목은 오독과
  미인식의 맞교환 하나**다. 0.778 지점이 세 조건 모두 아슬아슬하다.
- **이건 해석이지 확정이 아니다.** 원문 의도는 사람이 정해야 하고, 어느 쪽이냐에
  따라 출시 판단이 갈린다. 정하기 전에는 "게이트 통과"라고 부르지 않는다.
- 미측정: 이 수치는 **사진 한 장** 기준이다. 게이트는 실촬 골든셋 + 여러 프레임
  기준으로 쓰였다.

## Case 4: 사용자 전수 피드백 — 병목이 리더가 아니라 **검출기**로 옮겨갔다 (66%)

- Evidence: 사용자가 남은 오류 35건을 한 장씩 눈으로 검토해 분류
- Confidence: 5/5

### Discovery
| 분류 | 건수 |
|---|---|
| 검출: 경계 근접(박스가 마지막 숫자에 붙음) | 11 |
| 검출: 가로 LCD 미포함 | 8 |
| 검출: 영역 자체가 틀림(내부 일부 / 혈당기 전체) | 4 |
| 회전 | 3 |
| 조명·반사 | 4 |
| 기종 반복(중간·끝 숫자) | 4 |
| 폰트(이탤릭) | 1 |

**검출 문제가 23/35 = 66%.** 나는 하루 종일 리더만 파고 있었다.

사용자의 두 논리적 지적이 특히 날카로웠다:
- `647`(98의 9를 8로): "경계 근접이면 다른 케이스처럼 9가 나와야 일관성이
  있지 않나" → **경계에서 정보가 사라지면 결과가 임의적**이 된다. 특정 방향의
  오독을 예측할 수 없다는 뜻이고, 이는 "잘못 본다"가 아니라 "안 보인다"다.
- `845`(155→1559): "9가 들어갈 공간이 없는데" → 지어내기가 **아직 남아 있다.**
  다만 TTA 득표 0.44 로 거절 대상에 들어간다.

### Analysis
- **내 자동 분류는 실패했다.** 잉크 검출이 LCD 베젤을 잡아 정답의 93%도 "경계
  근접"으로 나왔다. 사람이 한 장씩 본 분류가 훨씬 나은 데이터였다 →
  [[downscaled-view-as-evidence]] 의 반대 사례: 자동 지표가 사람 눈보다 나쁠 수 있다.
- Action taken: G25(검출기 640)·G26(비대칭 여유)·G27(합성 실화면화) 지시서 작성.

## Case 5: 극성 정규화가 없어 **베젤이 잉크보다 어두운** 화면에서 세그먼트 판별이 무너진다

### Grounding
- Git Context: `hash:8ca74e3`
- Evidence: `glucose_batch1/488`(GT 105 → 109) — 극성 판정 확신도 **0.04**
  (어두운 픽셀과 밝은 픽셀 수가 거의 같다). 베젤 최소 3 · LCD 배경 중앙값 70 ·
  숫자는 그보다 조금 더 어두움
- Confidence: 5/5

### Discovery
`synth_lcd.py` 가 극성을 **50:50 으로 섞어** 생성하고(67~76행) 파이프라인
어디에도 극성 정규화가 없다. 그래서 모델은 극성 무관해야 하고, **"어두우면
세그먼트"라는 규칙을 쓸 수 없다** — 대비만 본다. 그 결과 밝은 반사선이
세그먼트처럼 보인다(사용자 관찰: "흰색에 가까운데 이걸 오독하는 건 문제").

더 근본적으로, 크롭 안에 **베젤이 잉크보다 어둡게** 들어 있어 전역 임계·극성
규칙 자체가 성립하지 않는다.

극성별 오답률: 정상(어두운 숫자) 2.85% · 반전(밝은 숫자) 3.66% — 차이는 작다.
즉 극성 자체보다 **극성이 모호한 장**이 문제다.

### Analysis
- Action taken: CLAHE 를 시험했으나 **기각**(아래 Case 6).
- 남은 후보: 2채널 입력(원본+국소정규화)으로 모델이 고르게 하기.
  전역 단일 처방이 실패하는 패턴을 피하는 방향이다.

## Case 7 (verification): 범용 OCR 기각 — 근거는 맞았지만 **문서에 적힌 이유는 틀렸다**

### Grounding
- Git Context: `hash:8ca74e3` · 도구 `assets_dev/train/bench_external_ocr.py`
- Evidence: EasyOCR, 표본 150장(holdout 간격 추출). 가장 관대한 채점(자릿수
  맞는 후보 우선)을 줬다
- Confidence: 5/5

### Results
| 엔진/조건 | 완전일치 | 장당 시간 |
|---|---|---|
| 우리 파이프라인(TTA) | **147/150 = 98.0%** | — |
| EasyOCR · 우리 크롭 | 14/150 = 9.3% | 0.07s |
| EasyOCR · 원본 전체 | 2/150 = 1.3% | 0.75s |

원시 출력: `177`→`2005`, `100`→`090`, `53`→`02033028`. **7-세그먼트 획 사이의
간격을 글자 경계로 오인**해 한 숫자를 여러 개로 쪼갠다.

### Analysis
- **사용자가 D-2 의 전제를 반박했고 그게 옳다.** `IMPLEMENTATION_PLAN.md` D-2 는
  "7-세그먼트는 상태 공간이 유한하고 구조가 명시적이라 학습 모델이 과잉"이라며
  EasyOCR 을 규칙 판독기로 대체했다. 그런데 **숫자의** 상태 공간은 유한하지만
  **사진의** 상태 공간은 무한하다 — 조명·각도·반사·기종·폰트. 오늘 실패한 35건이
  전부 후자다. 두 상태 공간을 같은 것으로 본 것이 그 문장의 오류다.
- 결론(범용 OCR 미사용)은 살아남지만 **이유가 바뀐다**: "구조가 단순해서"가
  아니라 **"범용 OCR 이 7-세그먼트를 문자로 인식하지 못해서"** 다. 이제 이건
  추측이 아니라 측정이다.
- 라이선스는 확인해 뒀다: PaddleOCR 은 코드·가중치 모두 Apache-2.0(GitHub API
  + HuggingFace 모델 카드 `license: apache-2.0` 직접 확인). EasyOCR 가중치는
  여전히 미확인(LICENSES.md §4). 여기서는 **벤치마크로만** 썼다.
- Tesseract 는 시스템 실행파일이 필요해 재지 않았다.

## Case 8: 검출 오차가 좌우 비대칭인데 여유는 대칭으로 주고 있었다

### Grounding
- Git Context: `hash:8ca74e3`
- Evidence: 사람 라벨 396장과 GM ft3 박스를 변마다 대조
- Confidence: 5/5

### Discovery
| 변 | GM 이 안으로 들어온 정도(중앙) | 10% 넘게 잘린 장 |
|---|---|---|
| 왼쪽 | +0.019 | 32 |
| **오른쪽** | **+0.060** | **104** |
| 위 | −0.002 | 6 |
| 아래 | −0.014 | 10 |

`BOX_MARGIN` 은 스칼라 하나로 **사방에 같은 값**을 준다(2026-09-04 도입).
오른쪽 오차가 왼쪽의 3배인데 같은 여유를 주므로, 왼쪽은 필요 이상(배경만 늘어
숫자가 작아진다)이고 오른쪽은 여전히 부족하다.

### Analysis
- Why non-obvious: 여유를 넣을 때 "사방에 준다"까지는 맞게 했지만 **변마다
  다르게 줄 수 있는지**를 묻지 않았다. 편향을 이미 측정해 놓고도 그 비대칭을
  처방에 반영하지 않았다.
- 사용자가 "앞에도 추가하도록 해보자"고 지적해서 다시 본 자리다. 실제로 왼쪽도
  32장이 걸려 있어 무시할 수준은 아니다.
- Action taken: G26 지시서를 (왼,오른,위,아래) 네 값으로 바꾸고 네 조건
  (대칭 .10 / 대칭 .15 / 비대칭 오른쪽 .20 / 비대칭 확대)을 비교하도록 작성.
