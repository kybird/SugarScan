## Case 1: 검출률 99.4% 는 정확도가 아니라 "출력이 있었나" 였다

### Grounding
- Git Context: `hash:c977ff11593195e44b7df91d3dca6266840602e9`
- Evidence: `docs/DONE.md` GM ft3 승격 절 · `assets_dev/train/detect_datumo_gm.py`
- Confidence: 5/5

### Discovery

사용자가 "LCD 를 제대로 못 찾는 경우가 많다"고 했는데 기록에는 **검출률
99.4%** 로 적혀 있었다. 둘이 어긋나서 그 99.4% 가 무엇을 센 값인지 되짚었다.

`detect_datumo_gm.py` 는 검출 결과가 하나라도 있으면(그리고 박스가 8px 이상이면)
행을 쓰고 `n_ok` 를 센다. 즉 **박스를 내놨는지**를 세는 값이지 **박스가 맞았는지**가
아니다. 사람 LCD 라벨 393장과 IoU 를 재니:

| | IoU 중앙 | >=0.9 | >=0.75 | <0.3 |
|---|---|---|---|---|
| 쓰고 있던 base | 0.795 | **7.4%** | 65.6% | 0.5% |
| ft3 | 0.828 | 10.4% | 76.3% | 0.0% |
| ft4 | 0.761 | 5.0% | 55.7% | 1.3% |

거의 안 놓치지만(<0.3 이 0.5%) 거의 안 맞는다(>=0.9 가 7.4%). 사용자가 본
"기기 몸통까지 먹는 박스"는 면적비 1.5배 이상이 16장(4.1%)인 꼬리였다.

### Analysis
- Why non-obvious: 지표 이름이 "검출률"이라 정확도로 읽힌다. 코드를 보기
  전에는 두 의미가 구분되지 않는다.
- Impact: 검출이 병목이 아니라는 판단의 근거였다. 그 판단 위에서 "밴드
  라벨링으로 전환"이 기각됐고, 이번 세션에서 같은 판단을 다시 했다.
- Action taken: ft3 를 정본으로 승격(IoU 전 지표 우세). ft4 는 퇴보라 기각.
  DONE.md 에 "이 IoU 대조 표본은 두 모델의 학습 데이터와 겹치므로 검출기
  성능 수치로 인용하지 말 것"을 함께 적었다.

## Case 2: 개선한 생성기가 파이프라인에 연결되지 않은 채 두 카드를 돌았다

### Grounding
- Git Context: `hash:c977ff11593195e44b7df91d3dca6266840602e9`
- Evidence: `assets_dev/train/synth_profiles.py` · `build_profiled_cache.py` ·
  `build_cache_v2.py:146`
- Confidence: 5/5

### Discovery

기기 프로파일 카드와 DSEG 카드가 연달아 완료됐는데, 둘 다 새 파일
`synth_profiles.py` 에 구현됐고 `synth_lcd.py` 는 "한 줄도 고치지 않았다"고
보고서에 적혀 있다. 기준선 팔을 보존하려는 올바른 판단이었다.

그러나 **기본 캐시를 만드는 `build_cache_v2.py` 는 여전히 `synth_lcd.py` 를
부른다.** 프로파일 렌더러는 `build_profiled_cache.py` 가 만드는 A/B 캐시에서만
쓰인다. 즉 두 카드의 성과가 곁가지에만 있고 기본 경로에는 닿지 않는다.

대비 실측이 그것을 드러냈다(숫자 영역 p95-p5, 300장):

| | 중앙 | p10 | 40 미만 |
|---|---|---|---|
| 실사진 | 117.5 | 85.7 | **0.0%** |
| 합성 profiled | 87.0 | 35.0 | 15.0% |
| 합성 synth_lcd (기본 경로) | 93.0 | 31.0 | **17.3%** |

기본 경로가 더 나쁘다.

### Analysis
- Why non-obvious: 두 카드 모두 AC 를 정직하게 만족했고 보고서도 정확했다.
  "기본 경로에 반영한다"가 어느 카드의 AC 에도 없었을 뿐이다.
- Impact: 생성기 개선이 최종 모델에 닿는지 아무도 재지 못한 상태로 두 번의
  A/B 가 돌았다.
- Action taken: 「생성기 일원화」 카드를 만들고 뒤따르는 생성기 카드 전부의
  선행으로 두었다.

## Case 3: 대리 지표가 목표와 반대로 움직였다 — pre-only 평가

### Grounding
- Git Context: `hash:c977ff11593195e44b7df91d3dca6266840602e9`
- Artifact: `docs/reports/generator-quality-baseline-2026-09-11.md` ·
  `device-profile-generator-2026-09-11.md` · `dseg-renderer-swap-2026-09-11.md`
- Confidence: 4/5

### Hypothesis

합성만 학습한 모델을 실사진에서 재면 생성기 품질을 볼 수 있다 — 파인튜닝이
실사진으로 다시 배우므로 최종 성적으로는 생성기 효과가 안 보인다는 관찰에서
나온 설계였다.

### Results

세 팔(기기 단절 홀드아웃 1,138장, pre-only):

| 층 | pre_v1 | pre_profiled | pre_DSEG |
|---|---|---|---|
| 완전일치 | 0 | 11 | 19 |
| **위험(자릿수 보존 오독)** | 34 | 115 | **138** |
| 무출력 | 712 | 0 | - |

새니티: 같은 체크포인트의 합성 val 은 279/300(93%) → 266/300(88.7%).

### Analysis
- Refuted: 이 지표는 품질 계기가 아니다. 완전일치가 오르는 동안 위험층이
  함께 오른다.
- 다만 그 위험층 해석에 주의가 필요하다. 실사진을 한 장도 안 본 모델에게
  도메인 밖 이미지를 억지로 디코딩시킨 결과다. 렌더가 좋아질수록 blank 대신
  무언가를 찍으니 위험층이 느는 것은 무출력 712→0 의 뒷면이다. "생성기가
  위험을 키운다"로 읽으면 과잉 해석이다.
- 합성 val 도 품질 계기가 아니다. 쓰레기를 일관되게 그리는 생성기도 자기
  val 에서 100% 가 나온다. 93%→88.7% 하락은 합성이 어려워졌다는 뜻이지
  나빠졌다는 뜻이 아니다 — 방향 해석이 불가능하다.
- Implications: 생성기 품질의 유일한 판정은 **ft 뒤 실사진 성적**이다.
  카드에 정정을 달았다.

## Case 5: 사람이 못 읽는 합성 표본은 증강이 아니라 라벨 잡음이다

### Grounding
- Git Context: `hash:c977ff11593195e44b7df91d3dca6266840602e9`
- Evidence: 합성 300장 대 실사진 300장 대비 측정(숫자 영역 p95-p5)
- Confidence: 4/5

### Discovery

사용자가 합성 출력을 눈으로 보고 "폰트와 크기도 일정하고 날짜와 단위 표시도
겹쳐 있다"고 지적했다. 렌더해 보니 그 위에 더 큰 문제가 있었다 — 여러 표본에서
숫자가 배경에 잠겨 **사람도 읽을 수 없다.**

| | 대비 중앙 | p10 | 40 미만 | 25 미만 |

| 실사진 | 117.5 | 85.7 | **0.0%** | 0.0% |

| 합성 synth_lcd | 93.0 | 31.0 | 17.3% | 3.7% |

실사진은 대비 40 미만이 **한 장도 없다.** 합성은 15~17%.

### Analysis
- Why non-obvious: 열화는 증강으로 보인다. 강할수록 강건해진다는 직관이 있다.

  잡음이다. 표준 합성 파이프라인은 글자가 읽히는 선에서 열화를 멈춘다.

- Action taken: 「합성 열화 상한」 카드. 목표는 대비 40 미만 0%. 단 "전부
  선명하게"가 목표가 아니다 — 실사진에도 흐린 장이 있으므로 중앙값과 분산을
  함께 보고하게 했다.

## Case 6: 칸반 보드가 git 워크트리마다 갈라져 폐기 카드가 되살아났다

### Grounding
- Git Context: `hash:c977ff11593195e44b7df91d3dca6266840602e9`
- Evidence: `llm-wiki` `lib/find-doc-root.js` (별도 저장소에서 수정됨)
- Confidence: 5/5

### Design Decision

한 저장소에 링크 워크트리가 여럿 있는 상태에서 두 곳의 `llm-wiki board` 가
서로 달랐다.

```
주 워크트리   TODO 9 · done 18 · abandoned 3
부 워크트리   TODO 2 · done 21 · abandoned 2
```

부 워크트리 TODO 에 주 워크트리에서 폐기한 카드가 살아 있었다. 에이전트가
그것을 집으면 폐기된 일을 한다. 반대로 주 워크트리에 세운 카드 7장이 부
워크트리에서 보이지 않았다. `doc/kanban/activity.jsonl` 은 병합할 때마다
충돌했다(같은 날 두 번).

### Alternatives Considered
- Option A: 프롬프트에 `LLM_WIKI_ROOT` 를 적어 둔다 — 기각. 규율에 기대는
  해법이고, 잊으면 조용히 갈라진다.
- Option B: 보드를 git 밖으로 옮긴다 — 기각. 카드의 버전 관리를 잃는다.
- Selected: `findDocRoot` 가 git 링크 워크트리에서 **주 워크트리의 doc/** 을
  향하게 한다. `git rev-parse --git-common-dir` 의 부모가 주 워크트리 루트다.

### Analysis
- Context: 보드(카드·클레임·활동 로그)는 **프로젝트 자원**인데 브랜치 자원으로
  저장돼 있었다. 저장 위치가 의미와 어긋난 것이 결함이다.
- **Trade-offs**: 부 워크트리에서 실행한 `pick`/`done` 이 주 워크트리 파일을
  수정한다. 그 변경은 주 워크트리에 미커밋으로 남고 거기서 커밋된다 —
  의도한 동작이며 문서에 적어야 한다.
- Reversibility: High — `LLM_WIKI_WORKTREE_LOCAL=1` 로 종전 동작으로 되돌린다.
- 검증: 수정 후 두 워크트리의 board 가 TODO 8 · done 22 로 완전히 일치했다.

```python
_MEM_VARIANTS = {"M", "mem", "memory"}   # 같은 라벨 부류의 표기 변형
...
used_texts |= _MEM_VARIANTS              # 하나를 쓰면 부류 전체 소진
```

### Analysis
- Root cause: 중복 방지가 `used_texts` 라는 **문자열 집합**으로 돼 있었다.
  `"mem" != "memory"` 이므로 중복으로 잡히지 않는다.
- Why it failed: 도메인의 동일성(같은 annunciator)과 자료구조의 동일성
  (문자열 일치)이 다른데 후자를 전자의 대리로 썼다. 표기 변형이 있는 라벨은
  전부 같은 함정에 걸린다 — `M`/`mem`/`memory`, `am`/`AM`.
- How it was fixed: 변형 집합을 부류로 명시하고 부류 단위로 소진했다.
  근본 해법은 요소를 `(부류, 표기)` 로 들고 다니는 것이지만, 부류가 하나뿐이라
  상수 집합으로 막았다(범위 밖 확대는 하지 않았다).

## Case 10: 저장소에 자가 있는데 즉석으로 재고, 수치가 갈리자 해명했다

### Grounding
- Git Context: `hash:fec6e17`
- Evidence: `docs/reports/session-handoff-2026-09-12.md` §2 정정 블록
- Confidence: 5/5

### Error
핸드오프 문서에 "엣지 밀도 실사진 **7.51%**(p10 5.44%, 각 300장)" 을 적고,
GLM 이 같은 축에서 보고한 **2.25%** 와 나란히 놓았다. 두 값이 3배 넘게
갈렸는데 그 상태로 문서가 나갔다.

더 나쁜 것은 그 다음이다. 정정하면서 **"자(측정 코드)가 달라 재현되지
않았다"** 고 적었다. 사용자 지적: **"넌 코드를 볼 수 있는데 무슨 개소리야"**.

### Fix Code
자는 `assets_dev/train/measure_panel_stats.py` 로 저장소에 있었고,
`--frame-exc` 라는 손잡이까지 코드에 적혀 있었다. 읽고 돌렸다:

```
python measure_panel_stats.py density --frame-exc 0      # median 2.52% p10 0.64% p90 3.84%
python measure_panel_stats.py density --frame-exc 0.04   # median 2.22% p10 0.48% p90 3.99%
긴 변 896 정규화 제거                                     # median 1.06% p10 0.26% p90 4.53%
밴드 미제외                                               # median 2.23% p10 1.14% p90 3.07%
```

n=84(밴드 라벨이 있는 전량). GLM 의 2.25% 는 `--frame-exc 0.04` 다.

### Analysis
- Root cause: 같은 축을 재는 자가 이미 커밋돼 있는데 **즉석 스크립트로 쟀다.**
  즉석 스크립트는 커밋되지 않았으므로 나중에 무엇을 쟀는지 확인할 방법이 없다.
- Why it failed: 7.51% 는 자의 **어떤 손잡이 조합으로도 나오지 않는다.**
  결정적 증거는 실사진 84장의 **최대값이 5.43%** 인데 적어 둔 p10 이 5.44%
  였다는 것 — 분포 자체가 다른 대상에서 온 값이다. 또 "각 300장" 은 성립할
  수 없다: 숫자 영역을 제외하려면 밴드 라벨이 필요하고 그건 84장뿐이다.
  세 가설(frame_exc · 스케일 정규화 · 밴드 제외 여부)을 전부 돌려 배제했다.
- 두 번째 실패가 더 중요하다: 수치가 갈렸을 때 **해명을 지어냈다.** "자가
  달랐다"는 검증 가능한 주장인데 검증하지 않고 적었다. 자는 코드이고 읽으면
  된다. 이건 지식의 부재가 아니라 **조회하지 않고 말한 것**이다 —
  `CLAUDE.md`「증상 보고를 받으면 — 코드보다 현장을 먼저 본다」의 재발이며,
  대상이 사람의 증상이 아니라 내 수치였을 뿐이다.
- How it was fixed: 7.51% 를 출처 불명으로 폐기하고 자로 잰 2.52%(n=84) 로
  교체. 규칙을 양쪽에 박았다 — `CLAUDE.md`(+AGENTS/GEMINI 사본)
  「수치를 인용하기 전에 — 자가 이미 있는지 본다」, `docs/GLM_TASKS.md` §3.7
  「수치를 인용할 때 — 자를 명령으로 적는다」. 수치 옆에 명령과 `n` 을 적고,
  자가 없어 새로 만들면 그 스크립트를 커밋한다.
