# 2026-09-02

## Case 1: Datumo EXIF orientation 불일치 — cv2는 적용·PIL은 무시, 2,512장 중 83.5%가 ori=6

### Grounding
- Git Context: `hash:b2e10ab` (이후 assets_dev 분석 스크립트는 gitignore 대상)
- Evidence: `assets_dev/train/check_exif2.py` 분포 {6: 2098, 1: 412, 3: 2} · `rect_test/exif_1005_pilraw.png`(옆으로 누움) vs `exif_1005_cv2.png`(정상 세로) · 사용자 보고 "검수창에서만 원본이 회전돼 보인다"
- Confidence: 5/5

### Discovery
같은 JPEG를 cv2.imread로 읽으면 EXIF orientation이 **자동 적용**되고(4.11 기본), PIL Image.open은 **무시**한다. Datumo 원본의 83.5%(2,098장)가 orientation=6이라:
- 라벨러(`/api/image`, cv2)는 올바른 세로 표시 — 사용자가 라벨링하기 좋았던 이유
- api_rect/build_cache_v2/detect_datumo_gm(PIL, 무회전)은 누운 원본 사용 — 검수 SRC 90° 회전 표시·라벨 좌표(표시 공간)와 파이프라인 좌표(raw) 불일치
- **CTC 학습 rect 다수가 "옆으로 누운 숫자 + 올바른 GT"** = '1'/'0' 쏠림·저성능의 숨은 주원인 후보
- "검수 4방향에서 무조건 270°가 정답" 현상의 진짜 원인 (촬영 습관 설명은 정정됨 — raw = upright를 CCW 90° 돌린 것이라 CW 90° 보정 = 270 셀)

### Analysis
- Why non-obvious: 두 독기(cv2/PIL)의 관례 차이는 같은 파일에서만 드러나고, 라벨러와 검수가 서로 다른 경로를 쓰는 도구 구조에서는 "원본이 회전돼 보인다"로밖에 증상이 안 떠오른다.
- Impact: CTC 재학습 시 점수 대폭 상승 가능성 / GM 예측 힌트 표시 어긋남 / oob 오탐 섞임.
- Action taken: webtool 전면 통일 — `/api/image`를 PIL+`ImageOps.exif_transpose`로 디코딩(ow/oh도 표시 기준), `_load_gray`에 exif_transpose, `gmscreen_quads_oriented.jsonl` 신설(라벨러 힌트용 좌표 변환, `convert_quads_oriented.py`, 눈검증: glucose_batch1/10 쿼드가 표시 이미지에서 유리 정확히 감쌈). **미완: build_cache_v2·detect_datumo_gm·golden_bench(Dart package:image)는 여전히 무처리 — GM 파인튜닝 병합 전 exif_transpose 로더 통일 필수.**
- Anti-Patterns: [[mixed-image-decode-conventions]] — 같은 좌표계를 공유하는 코드에서 cv2/PIL/Dart를 섞어 쓰면서 EXIF 처리 관례를 통일하지 않는 것
- **[2026-09-02 정정]** 위 "미완" 목록 셋 중 둘(`detect_datumo_gm`·`golden_bench`)은 **이미 EXIF 를 처리하고 있었다.** 실측 근거와 정정 내용은 Case 13.

## Case 2: CTC hold-out 기준선 저평가 — GT blank 조인 아티팩트로 3.8% → 실제 5.1%

### Grounding
- Git Context: `hash:b2e10ab`
- Evidence: `reader_preds.json` verbatim `{"glucose_batch1/862": ["90", "9010"]}`, `{"glucose_batch1/1209": ["88", "8810"]}` — 저장본 GT 비교 exact 34/903(3.8%), labels.jsonl `reading` 대조 시 46/903(5.1%)
- Confidence: 5/5

### Error
구판 저장 코드가 GT 문자열을 라벨 id 그대로 조인해 blank(클래스 10)가 "10"으로 붙음("9010"=90). 예측은 greedy_decode가 blank를 건너뛰어 깨끗(4자리 이상 예측 0.1%).

### Fix Code
`ctc_reader_v2.py` gt_strs: `"".join(str(int(v)) for v in row if int(v) != NUM_CLASSES)` — 이미 반영돼 다음 실행부터 자동 정상. 분석 스크립트는 labels.jsonl `reading`을 진짜 GT로 사용.
### Analysis
- Root cause: 라벨 id 배열을 문자열로 조인할 때 패딩(blank=10)을 필터하지 않음
- Impact: 기준선 3.8%는 저평가(진짜 5.1%), 학습셋 6.8%도 소폭 저평가
- Anti-Patterns: [[padding-as-content]] — 패딩 값이 유효 데이터와 구분 없이 직렬화되는 구조

## Case 5 (design): 유리가 사다리꼴인 기기 — 자동 쿼드 경로는 참고로 강등, CTC는 렌더러 실화면화로

### Grounding
- Git Context: `hash:b2e10ab`
- Evidence: 1707(CareSens N Voice=하단 넓은 부채꼴 창) SRC 초록선이 몸체로 삐짐 · 위치별 정확도 80.3/37.4/17.8% · 0/1-only 예측 33.9% · 시각 부분문자열 오류 2.7%(`predictions_breakdown.txt`)
- Confidence: 4/5

### Design Decision
유리 테두리 자체가 사다리꼴인 기기가 있어 "유리=직사각형+원근" 가정은 근본적으로 깨진다. → 자동 유리 쿼드는 **미리보기 참고로 강등**(실패 시 박스 스트레치 폴백), CTC 파이프라인은 **A: 박스 라벨 유지 + 종횡비 보존 워프 + 합성 렌더러 실화면화(압착·키스톤·회전·반사광) + 4방향 증강**으로 진행. LCD 박스 라벨링(200장)은 GM 검출기용으로 그대로 유효.

### Alternatives Considered
- B: 4모서리(쿼드) 라벨링 전환 — 품질 최고지만 공수 2~3배 + 검출 모델 쿼드 출력 확장 필요 → 필요 시 2차 옵션
- 시간 줄 마스킹 — 오류 중 시각 부분문자열 2.7%로 기각 / 모델 확대 — 1,104장 74.5% 암기 실측으로 용량 아님 확인

### Analysis
- Trade-offs: A는 유리 형태를 회피(숫자 중심 학습-추론 일치)하지만 완벽한 rectification은 포기 / B는 품질 보장이지만 사람 시간+모델 확장
- Reversibility: A→B 전환 가능(A가 먼저 숫자를 낸 뒤 판단)

## Case 6: 라벨러 좌표계가 장 전환에서 한 장 밀림 — 저장 쿼드가 직전 장의 표시 크기 안에 갇힘

### Grounding
- Git Context: `hash:d5366c5` (도구 버전 관리 편입) · `hash:474da30` (빌드 지문·자가검증 보완) — 이 사고 이전에는 도구에 이력이 없어 "고친 코드가 실제로 돌았나"를 확인할 방법이 없었다
- Evidence: `screen_boxes.jsonl` 3행 실측 — `1005` 표시 3096×4128인데 저장 박스 (559,345)-(1881,1779), 직전 장 `1001` 이 정확히 2414×3218. 배율 3096/2414=1.2825 를 곱해 크롭하면 `106 mg/dL` 전체가 정확히 잘린다(`_diag/glucose_batch1__1005_rescaled.png`). `1013` 은 y1=2920 > h=2893 으로 경계 초과, ×0.7009 보정 시 정상. 라벨러 LCD 정렬 재현 결과 1001→1005→1013 이 정확히 연속.
- Confidence: 5/5

### Error
사용자가 캔버스에서 유리에 정확히 맞춘 노란 박스가, 저장 후 검수(E)에서 **좌상단으로 밀리고 0.78배로 줄어** 있었다. 의뢰서의 가설은 전부 dpr(1.25~1.5) 의존이었다 — 개발자 브라우저(dpr=1)에서 재현되지 않았기 때문.

### Environment Context
- Packages: Windows 11 / Chrome 배율 125~150% / `assets_dev/train/webtool.{py,html}` 표준 라이브러리 HTTP 서버 + 단일 파일 SPA
- Migration Issue: No (단, Case 1 의 EXIF 통일 작업 직후에 드러났다)

### Fix Code
```js
// 좌표계는 여기서만 만들어진다. 이미지·크기·id 셋이 항상 함께 바뀐다.
function applyImage(img, id, gen) {
  if (gen !== undefined && gen !== lb.gen) return;   // 늦게 온 응답은 버린다
  if (!img._ow || !img._oh || img._id !== id) { /* 저장 차단 */ return; }
  lb.img = img; lb.ow = img._ow; lb.oh = img._oh; lb.frameId = id;
  fitView(); draw();
}
```
```python
# 서버가 원본 파일에서 직접 잰 크기와 대조한 뒤에만 기록한다.
if abs(cow - ow) > FRAME_TOL or abs(coh - oh) > FRAME_TOL:
    return (f"좌표계 불일치 — 브라우저는 {cow:.0f}x{coh:.0f} 프레임으로 그렸는데 "
            f"{cid} 의 실제 표시 크기는 {ow}x{oh} 다. 저장 거부"), ow, oh
```

### Analysis
- Root cause: `show()` 의 이미지 캐시 히트 경로가 `applyImage(cached, null)` 로 불려 `lb.ow/lb.oh` 가 **이전 장의 값으로 잔존**했다. 캔버스는 박스와 이미지를 같은 변환으로 그리므로 "그린 것 == 저장한 것"은 수학적으로 항상 참이다 — **어긋날 수 있는 경로는 `lb.ow/lb.oh` 가 이 장의 것이 아닐 때 하나뿐이다.**
- Why it failed: dpr 은 상관 변수였을 뿐이다. 개발자 브라우저에서 재현되지 않은 이유는 dpr=1 이어서가 아니라 **장을 연달아 넘기지 않았기 때문**. 증상이 "배율 오차"로 보여 dpr 가설로 수렴했다.
- 왜 "고쳤는데 그대로"였나: `webtool.html` 수정 01:18, 파손 라벨 기록 01:21. 서버가 `Cache-Control: no-store` 를 보내므로 새로고침만 했다면 새 JS 를 받는다 → 그 3건은 **수정 전 JS 가 살아 있는 탭**에서 저장된 것. **"지금 이 탭이 어느 빌드를 돌리는가"를 사람이 알 방법이 없었던 것이 진짜 결함이다.**
- How it was fixed: 5중 방어. ①프레임 이름표(`lb.frameId`, 이미지·크기·id 동시 설정, 로딩 중 캔버스 비움) ②세대 토큰(`lb.gen`) ③저장 직전 `frameGuard` ④**서버가 원본 파일과 대조 후 409 거부**(낡은 JS 가 살아 있어도 파일이 오염되지 않는 유일한 층) ⑤빌드 지문(`/api/build` + 15초 폴링, 헤더에 `build <sha8>`). 저장 성공 행에는 `ow`/`oh` 를 함께 기록해 사후 검증 가능.
- 검증: `T` 자가검증을 사용자 브라우저 안에서 실행 — dpr 1/1.25/1.5 전부 통과, `evPos ∘ draw` 왕복 오차 4.55e-13 px. 버그 6종을 인위적으로 주입해 각 층이 실제로 막는 것 확인(크기만 밀린 경우는 **클라가 스스로 못 잡고 서버가 잡는다** — ④가 왜 필요한지의 실측 근거).

## Case 7: band 라벨 5건이 EXIF **미적용(회전 전)** 좌표계 — 배율 보정으로는 절대 못 맞추는 종류

### Error
Case 6 복구 후 전수 점검을 돌리자 **다른 종류의 파손 5건**이 나왔다. 원인이 Case 6 과 달라 같은 스크립트로는 못 고친다.

### Fix Code

### Analysis
- Root cause: Case 1 의 cv2/PIL EXIF 관례 불일치 시기에 저장된 라벨. 표시 이미지가 아니라 **저장(회전 전) 이미지** 좌표로 남았다.

- How it was fixed: 회전 사상 적용 후 크롭 육안 확인. 사고가 두 종류라 스크립트를 분리했다(`repair_prevframe_labels.py` / `repair_unrotated_band_labels.py`) — 한 스크립트에 두 가설을 섞으면 다음 사람이 어느 쪽이 적용됐는지 못 읽는다.
- 남은 것: `glucose_batch1/128` 은 좌표는 맞았지만 박스가 밴드치고 헐겁다(재라벨 권장).

## Case 9: 정본이 조용히 갈라지는 세 자리 — 부분 수정 · 계약보다 좁은 try · 스로틀러 reset

### Grounding
- Git Context: `hash:5ed3f06`, `hash:d7042da`
- Evidence: `test/data/glucose_repository_edit_test.dart` 정본 일관성 4건 · `test/ocr/glucose_scanner_contract_test.dart` 3건 · `test/ocr/frame_throttler_test.dart` reset 2건

### Error
1. `GlucoseRepository.update` 가 `value` 와 `unit` 이 **둘 다** 있을 때만 `valueMgdl` 을 갱신했다 → 값만 고치면 화면이 보는 `enteredValue` 와 통계·동기화·헬스 연동이 쓰는 정본 `valueMgdl` 이 **서로 다른 숫자**가 된다.

if (value != null || unit != null) {

// ② 경계는 메서드 전체 + 세션 토큰

## Case 10: 서버 행 하나가 해석되지 않으면 델타 pull 이 영구히 막힌다 — 버전 차이가 트리거

### Grounding
- Git Context: `hash:d7042da`
- Evidence: `test/data/sync_engine_test.dart` 그룹 '해석 못 한 행' 3건 + '커서' 홀드백 1건. `flutter test` 373 통과.
- Confidence: 5/5

### Error
`ReadingDto.fromJson` 이 `!`·`as String`·`fromWireName` 을 그대로 쓴다. 행 하나라도 던지면 `_pull` 이 통째로 실패하고 `syncOnce` 는 `failed` 를 돌려주며 **커서가 전혀 전진하지 않는다.** 가장 현실적인 트리거는 버전 차이 — **새 앱이 새로운 enum wireName 을 쓰면 구버전 앱은 그때부터 영원히 받지 못한다.**

### Fix Code
```dart
// 해석 못 한 행은 버리고 센다. 페이지 판정과 offset 은 '서버가 돌려준 행 수' 기준.
class ReadingPage {
  final List<GlucoseReading> readings;
  final int fetchedRows;        // 버린 행 포함
  final List<String> malformed;
  final DateTime? newestSeen;   // 버린 행의 updated_at 도 본다
}
// 두 종류의 '건너뛴 행'을 반대로 다룬다.
var next = newest;                       // 해석 못 한 행: 넘긴다
if (heldBack != null && ...) next = heldBack;  // pending 이라 건너뛴 행: 앞에 세운다
```

### Analysis
- Root cause: 읽기 관용도가 **행 단위가 아니라 배치 단위**였다. 한 행의 실패가 배치 전체의 실패로 승격된다.
- Why it failed: 스키마가 하나뿐인 동안에는 절대 안 터진다. 앱 버전이 둘 이상 도는 순간부터만 터지므로, 출시 전에는 관측 자체가 불가능하다.
- How it was fixed: (a) 행 단위로 버리고 `SyncReport.malformed` 로 센다. (b) **페이지 경계 판정과 offset 은 서버가 돌려준 행 수 기준**이어야 한다 — 버린 행을 뺀 수로 세면 마지막 페이지로 오판해 **뒷 페이지를 통째로 놓친다**(이 함정이 수정 자체보다 위험하다). (c) 커서는 못 읽은 행을 **넘기고**(붙잡으면 제자리를 돈다), 로컬 pending 때문에 건너뛴 행 **앞에 세운다**(넘기면 그 push 가 막혔을 때 서버 변경이 영영 안 온다). 두 정책이 정반대인 것이 핵심.
- 발견된 파생 결함: `MeasurementTag.fromWireName`/`ReadingSource.fromWireName` 은 모르는 값을 각각 `random`/`manual` 로 **조용히 치환**한다. 관용처럼 보이지만 그 행을 나중에 수정하면 push 가 치환된 값을 서버에 덮어써 **다른 기기의 태그를 파괴한다.** `GlucoseUnit.fromWireName` 만 던진다(단위는 추측하면 값의 의미가 뒤집히므로 이쪽이 옳다). 세 정책이 제각각이고 그중 어느 것도 버전 공존을 고려해 정해지지 않았다 — 미해결, [[wire-schema-evolution]] 참조.

## Case 11: 위키를 만들어도 **에이전트가 실제로 던지는 질의 모양**으로는 안 걸린다

### Grounding
- Git Context: `hash:a8f0591`
- Evidence: `llm-wiki search` 실측 — `FrameThrottler` · `statsReadingsProvider` · `pendingSyncCount` · `_apply` 네 개가 **위키 페이지 히트 0**(raw 로그만 걸림). 반면 "좌표계", "동기화가 안 된다", "통계에 안 보임" 같은 증상 질의는 정확한 페이지가 1위로 올라왔다.
- Confidence: 5/5

### Discovery
QMD 미설치 환경에서 `llm-wiki search` 는 **공백 토큰화 + 대소문자 무시 부분문자열 grep** 이다. 그래서 검색 성패가 "질의 토큰이 문서에 문자 그대로 들어 있는가"로 정해진다.

- 증상 질의(한국어 산문)는 잘 걸린다 — 위키 본문이 같은 어휘로 쓰여 있기 때문.
- **코드 식별자 질의는 못 걸린다.** `FrameThrottler`(CamelCase)는 페이지의 `frame_throttler.dart`(snake)와 문자열이 겹치지 않는다. `statsReadingsProvider` 는 페이지 본문에 아예 없었다.
- 한국어 조사도 방향성이 있다: 질의 토큰이 **짧아야** 걸린다("좌표계"→"좌표계가" 매칭 O, "좌표계가"→"좌표계는" 매칭 X).

### Analysis
- Why non-obvious: 위키를 쓴 사람은 개념어로 검색해 보고 "잘 걸린다"고 결론 낸다. 그런데 에이전트가 검색하는 시점은 **파일을 열기 직전**이고, 그때 손에 있는 것은 개념어가 아니라 **클래스·함수 이름**이다. 가장 중요한 순간에 정확히 안 걸린다.
- Impact: 안티패턴 14장을 써 놓고도 `FrameThrottler.reset()` 을 고치는 에이전트에게는 보이지 않는다 — 지식 그래프가 있으나 마나가 된다.
- Action taken: ①28개 페이지 `aliases` 에 코드 식별자를 넣었다(전부 1~3 히트로 회복). ②**검색은 pull 이라 물어볼 줄 알아야 걸린다**는 한계 자체는 안 없어지므로, 자주 틀리는 자리를 `CLAUDE.md` 에 "이 파일·기호를 건드리기 전에 이 페이지를 읽어라" 표로 밀어 넣었다(매 세션 로드).
- 부수 발견: `llm-wiki` 인덱서는 **하이픈 없는 `antipatterns/`** 만 스캔한다(`anti-patterns/` 는 무시돼 안티패턴 수가 0으로 나왔다). 루트 loose `.md` 는 태그와 무관하게 Concepts 로 떨어져 개념 수를 부풀린다(health report 를 `reports/` 로 옮긴 이유).

## Case 12 (design): 모르는 enum 값을 치환하지 않고 행을 버린다 — 2단계 중 1단계만 지금 한다

### Grounding
- Git Context: `hash:82262de` 직후 작업
- Confidence: 4/5 (발생 전 예방이라 실측 근거가 없다. 파괴 경로는 코드로 확인)

### Design Decision
`MeasurementTag`·`ReadingSource`·`GlucoseUnit.fromWireName` 이 모르는 값에서 `UnknownWireNameException` 을 던진다. 그 행은 pull 이 건너뛰고 `SyncReport.malformed` 로 센다. 동기화되지 않는 `TargetRangePreset` 만 기본값으로 떨어진다.

### Alternatives Considered
- **태그를 문자열 타입으로** — 저장은 이미 `wireName` 문자열이라 실질은 "도메인 타입을 없애자"다. `tag_labels.dart` 의 switch 가 컴파일 타임 exhaustiveness 를 잃고, l10n 매핑은 map 으로 남아 enum 이 이름만 바뀐다. UI 가 제시할 태그 목록도 문자열로는 안 나온다 — **얻는 것 없이 안전만 잃는다.** 기각.
- **enum 어휘를 서버에서 받기** — 서버가 이미 어휘의 정본(PG enum)이지만, 클라이언트에 필요한 건 "어휘 + 6개 언어 라벨 + 순서"다. 라벨을 서버가 보내면 의료 문구 역번역 교차검증 밖으로 나가고, `RemoteDisabled` 가 정상 상태인데 서버 없는 빌드에 태그가 사라진다. 어휘보다 데이터가 먼저 올 수 있어 **unknown 케이스는 여전히 필요**하다. 부품은 늘고 보장은 약해진다. 기각.
- **`unknown(원문)` 보존 (2단계)** — 옳지만 지금 급하지 않다. 아래 참조.
- **선택: 던지고 행을 버린다(1단계).**

### Decision Code
```dart
static MeasurementTag fromWireName(String value) =>
    values.firstWhere((e) => e.wireName == value,
        orElse: () => throw UnknownWireNameException('MeasurementTag', value));
```

### Analysis
- Context: 서버가 `create type measurement_tag as enum (...)` 이라 새 값은 **우리가 `ALTER TYPE ... ADD VALUE` 를 하기 전에는 들어올 수 없다.** 사고가 몰래 다가오지 않는 대신, 문을 여는 순간 되돌릴 수 없다.
- **Trade-offs**: 구버전에서 그 기록이 **안 보인다**(누락) vs 데이터가 **영구히 죽는다**(치환). 비대칭이 결정의 전부다 — 안 보이는 것은 앱을 업데이트하면 낫고, 덮어쓴 값은 업데이트해도 못 살린다.
- **왜 2단계를 지금 안 하나**: 1단계가 이미 파괴를 막아 **되돌릴 수 없는 상태가 아니게** 만든다. 2단계(`unknown(원문)` 보존 + `tagUnknown` l10n 6개)는 "구버전에서도 값과 시각은 보이게" 하는 UX 개선이지 데이터 보호가 아니다. 필요해지면 그때 올려도 늦지 않다.
- **배포 순서가 전부다**: ①던지는 클라이언트 배포 → ②서버 enum 에 값 추가 → ③새 값 쓰는 앱 출시. ①을 건너뛰고 ②를 하면 끝이다. **지금이 ①을 할 수 있는 가장 싼 시점**이다 — 출시 전이라 필드에 배포된 클라이언트가 0 이다.
- Reversibility: High (2단계로 언제든 올릴 수 있다)
- 검증: `flutter test` 384 통과(+11). `test/domain/wire_name_test.dart` · `test/data/reading_dto_test.dart` 그룹 '모르는 wireName'.

### Error
Case 1 이 "미완: `build_cache_v2`·`detect_datumo_gm`·`golden_bench` 는 여전히 무처리"라고 적었고, 나는 그걸 그대로 G20 지시서로 옮겼다. **셋 중 둘이 무죄였다.**

- `golden_bench.dart` — `package:image` 가 JPEG 디코드 시점에 orientation 을 픽셀에 굽는다. 내가 지시한 `decodeImage → bakeOrientation → encodePng` 은 **항상 no-op**. 위임받은 에이전트가 20장 실험으로 SUMMARY 전 항목 동일함을 확인하고 원복했다.
- `detect_datumo_gm.py` — 1차 경로는 `cv2.imread`(EXIF **적용**). PIL 은 폴백일 뿐이다. 따라서 이 스크립트가 만든 `gmscreen_quads.jsonl` 은 **처음부터 표시 좌표계**였다.
- `build_cache_v2.py` — 여기만 진짜 결함. PIL 무회전 이미지에 **표시 좌표계 쿼드**를 얹고 있었다. Case 1 의 결론("CTC rect 가 누워 있었다")은 맞았지만 원인 귀속이 셋으로 번져 있었다.

그리고 그 오진이 **더 나쁜 것을 가렸다.** `convert_quads_oriented.py` 는 머리에 "원본은 raw 좌표계"라고 적어 두고 ori=6 쿼드를 한 번 더 회전시켰다. 원본이 이미 표시 좌표계였으므로 **라벨러의 GM 파란 힌트가 전체의 83.5%(ori=6)에서 이중 회전**돼 있었다.

### Analysis
- Root cause: **파일을 열지 않고 이름표를 믿었다.** `convert_quads_oriented.py` 주석의 "원본은 raw 좌표계" 한 줄, Case 1 의 "무처리" 목록 한 줄 — 둘 다 검증 없이 사실로 취급했다.
- Why it failed: 어제 내가 쓴 안티패턴이 정확히 이것이다([[unnamed-coordinate-frame]]: "좌표가 어느 프레임의 것인지를 함께 저장하지 않는 것"). 그 페이지를 쓴 사람이 같은 날 같은 함정에 빠졌다. **개념을 아는 것과 매번 확인하는 것은 다른 일이다.**
- 왜 안 걸렸나: Case 1 에 "눈검증: glucose_batch1/10 쿼드가 표시 이미지에서 유리 정확히 감쌈"이 기록돼 있다. 지금 재현하면 **원본 쿼드**가 감싼다. 즉 그때 검증한 것은 변환본이 아니라 원본이었을 가능성이 높은데, 기록에는 "변환본을 검증했다"로 읽히게 적혀 있었다. **무엇을 검증했는지가 아니라 무엇이 통과했는지만 적으면 이렇게 된다.**
- How it was fixed: 위임받은 에이전트가 지시서를 그대로 실행하지 않고 **전제부터 실측**했다. 20장 A/B 실험(no-op 확인), 크롭 대조(이중 회전 확인). 지시서가 틀렸을 때 그것을 잡아낸 것은 사람이 아니라 위임 절차였다.
- Impact: 라벨링 재개 전에 힌트 파일이 고쳐졌다. 파란 힌트가 어긋난 채로 200장을 그렸으면 사람이 매번 힌트를 무시하고 새로 그리거나, 더 나쁘게는 힌트를 믿고 어긋난 박스를 저장했을 것이다.
