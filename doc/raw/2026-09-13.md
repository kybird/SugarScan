## Case 1: 실사진 기준선이 기기 편향 표본에서 나왔다

### Grounding
- Git Context: `hash:f23f153`
- Evidence: `docs/GLM_TASKS.md` §3.8 기준선 표, `assets_dev/train/real_baseline.json`
- Confidence: 5/5

### Discovery
합성기 조준의 기준이던 실사진 기준선이 밴드 라벨 84장에서 나왔는데, 그 84장이
기기 편향 표본이었다. 밴드 라벨 76장 중 63장이 세 기기(OneTouch UltraMini 30 ·
CareSens N 19 · 이름모를 가로형 14)였고 54종 중 39종이 0장이었다.

사람이 기기 균등 씨앗 큐로 라벨링해 54종 전량이 채워진 뒤(277행, n=264) 다시
재니 전 축이 움직였다.

```
            옛 n=84    새 n=264
  링         2.84%      1.90%
  안쪽       1.38%      1.11%
  전체 밀도  2.52%      1.77%
  극성 반전  27.4%      33.7%
  대비       104        99
  세로 band_w 0.827     0.888
  세로 cy    0.391      0.407
```

### Analysis
- Why non-obvious: 편향은 수치 자체에 나타나지 않는다. 84장이라는 n 은 적혀
  있었지만 "그 84장이 세 기기" 라는 사실은 아무 데도 없었다.
- 밴드 폭 교란(새 라벨이 더 넓다, 세로형 0.827 에서 0.901)이 원인일 가능성을
  고정 제외 박스로 배제했다. 그래도 격차가 남아 기기 구성 탓임이 확인됐다
  (세로형 링 옛 2.63% 새 1.49%).
- Impact: 이 기준선에 맞춰진 1차 작업이 통째로 과녁을 벗어났다. 근거 주석이
  달린 상수(`PITCH_RATIO`)까지 그 목표에 맞추느라 오염됐다.
- Action taken: 기준선을 `real_baseline.json` 정본 하나로 모으고 세 소비처가
  읽게 했다. 옛 n=84 값 전부를 폐기 목록에 올렸다.

## Case 3: 검출 실패가 두 갈래였다 — 크롭 잘림과 기기 약세

### Grounding
- Git Context: `hash:c28b8c1`
- Evidence: `assets_dev/train/band_det_clip_split.py`
- Confidence: 5/5

### Discovery
눈검증 시트의 최악 6장이 전부 같은 모양이었다. 사람 라벨이 GM 크롭 왼쪽
가장자리 띠로만 남고 검출기는 화면 가운데 정보칼럼을 숫자줄로 집는다.

사람 밴드 라벨이 GM 크롭 안에 든 면적 비율로 가르니:

```
python band_det_clip_split.py
  밴드가 크롭 안(>=0.95)  n=246  median 0.727  p10 0.570
  잘린 장(<0.95)          n= 18  median 0.339  p10 0.000
```

가장 많이 잘린 여섯(2431 0.030 · 1610 0.098 · 1593 0.291 · 606 0.581 ·
1614 0.603 · 1094 0.686)이 최악 여섯과 정확히 같다.

### Analysis
- Why non-obvious: 하나의 median(0.717)이 성격이 다른 두 모집단을 덮고
  있었다. 기본 눈검증 시트가 최저 n장을 뽑으므로 가장 심한 부류만 보이고
  나머지 실패 유형이 가려진다.
- 잘림은 하드 실링이다. 숫자가 크롭 밖이면 어떤 밴드 검출기도 못 이긴다.
  이건 GM 검출기 문제지 밴드 검출기 문제가 아니다.
- 하위 기기는 잘림 탓이 아니었다. 깨끗한 크롭만 봐도 약하다(UltraMini 24장
  0.574 · On Call Extra 0.573 · KOOKMIN Check 0.605, 전체 0.727).
- Action taken: 잘린 18장은 레터박스 카드로, 기기 약세는 합성 카드로 배정.

## Case 4: 학습 손실이 낮다고 훈련이 끝난 것이 아니다

### Grounding
- Git Context: `hash:c28b8c1`
- Evidence: `assets_dev/train/band_det_synth_gap.py`
- Confidence: 5/5

### Hypothesis
실사진 IoU 0.727 이 낮은 것이 훈련 부족인가 도메인 격차인가.

학습 로그만 보면 훈련은 끝난 것처럼 보였다.
`epoch 40 train 0.00166 sanity-val 0.00031` — val 손실이 train 보다도 낮다.

### Results
같은 모델을 학습에 쓴 합성 2,600장에 돌려 같은 자(poly_iou)로 쟀다.

```
python band_det_synth_gap.py --images <synth>/images --manifest <synth>/manifest.jsonl
  합성   median 0.901 p10 0.824  (세로형 0.904 · 가로형 0.862)
  실사진 median 0.727 p10 0.570  (잘린 장 제외 246장)
```

### Analysis
- Confirmed/Refuted: 둘 다 있다. 학습 데이터에서조차 1.0 이 아닌 0.10 이
  훈련·용량 여유이고, 0.901 에서 0.727 로의 0.174 가 도메인 격차다.
  후자가 크다.
- Key insight: 손실은 IoU 가 아니다. MSE 0.00031 은 정규 좌표 RMSE 약 1.8%
  인데 그 정도 좌표 오차가 IoU 로는 0.1 을 깎는다. 낮은 손실을 보고
  "수렴했으니 남은 건 데이터 문제" 로 넘어가면 용량 여유를 놓친다.
- Implications: 에폭만 늘려서는 0.83 근처가 한계다. 그 이상은 합성을 고치거나
  실사진을 학습에 넣어야 한다.

## Case 5: 고정 문턱 자가검사가 입력 분포를 넓히자 무력화됐다

### Grounding
- Git Context: `hash:e3c62cc`
- Artifact: `docs/reports/synth-overhaul-review.md`
- Confidence: 5/5

### Error
`glyph_plane_check` 가 크게 나빠졌다.

```
              병합 전    이 브랜치
  p10        0.9908     0.9384
  min        0.7043     0.0000
  0.9 미만   0.8%       8.7%   (n=300)
```

### Environment Context
- Packages: conda sugartrain (opencv-python, numpy, torch)
- Migration Issue: No

### Fix Code
아직 고치지 않았다. 카드로 세웠다 — 잉크 문턱을 패널 대비에 비례시킨다.
자가검사 정의 변경은 판단이 필요한 자리라 리뷰에서 고치지 않았다.

### Analysis
- Root cause: 검사가 `ink = abs(img - bg) > 30` 이라는 고정 문턱을 쓴다.
  열화 상한 카드가 대비 분포를 의도적으로 아래로 넓히자(실사진 p10 60 ·
  40미만 1.1% 를 맞추려고) 저대비 패널에서 잉크가 문턱을 못 넘는다.
- 수치로 확정했다. 대비와 gpc 가 단조 관계다.

```
  대비 0~40    gpc median 0.764   0.9미만 66.7%
  대비 40~60   gpc median 0.953   0.9미만 33.3%
  대비 120+    gpc median 1.000   0.9미만  2.4%
```

- Why it failed: 검사가 "글리프 평면이 어긋났다" 와 "패널이 흐리다" 를
  구별하지 못한다. 산출물은 정상이다. 최저 6장을 오버레이로 확인했고 쿼드는
  전부 숫자에 정확히 붙어 있다. 망가진 것은 검사의 분해능이다.
- 전날 이 검사가 살아 있는지 확인했던 방법(글리프 평면을 8px 어긋뜨리면
  median 0.9997 에서 0.8337)이 이제 저대비 패널에서 무의미하다. 어긋나지
  않아도 그 아래로 떨어진다.
- 일반화: 가드의 문턱이 고정이면 입력 분포를 넓히는 변경이 그 가드를
  조용히 무력화한다. 가드를 만들 때 문턱이 무엇에 상대적인지 적어야 한다.

## Case 6: 지표가 전부 통과인데 사람이 합성을 8/8 로 구분했다

### Grounding
- Git Context: `hash:cb8fbc0`
- Evidence: `assets_dev/train/synth_vs_real_sheet.py`
- Confidence: 5/5

### Discovery
합성 8장과 실사진 8장을 섞어 쿼드 없이 보였더니 사람이 8장 전부를 맞혔다.
그 시점 합성은 잰 축이 전부 통과였다. 링 2.22(목표 1.90 플러스마이너스 0.5) ·
안쪽 1.49(1.11) · 전체 2.05(1.77) · 대비 median 103(99) · 밴드 기하 4축 ·
종횡비 · 하드 검사 0.

사람이 짚은 단서:
- LCD 안 글자가 세 방식으로 섞여 있다. DSEG 세그먼트(큰 숫자), Hershey
  벡터 폰트(mem, mg/dL — 세그먼트 LCD 가 낼 수 없는 곡선), 도트 양자화
  (시간줄). 실사진 722 는 값과 날짜와 시간이 전부 세그먼트다.
- 콜론이 통짜 사각형 하나다. 실물은 사각 점 두 개(722 의 1 콜론 27).
- 글자 크기가 한 장에 4~5종이다. 실물은 큰 숫자 하나와 작은 주석 하나뿐.
- 배터리 내부가 채워져 진행 막대처럼 보이고 돌기가 없다.
- 화살표가 떠다닌다. 실물에서 화살표는 몸체에 인쇄된 미터기를 가리키는
  지시자다(ACCU-CHEK Instant 1195 · 2039 · 1193 · 1215 — 검은 창 바깥
  오른쪽 회색 띠에 점 약 10개가 인쇄돼 있고 창 안 삼각형 세그먼트가
  그것을 가리킨다).

### Analysis
- Why non-obvious: 잰 축(밀도 · 대비 · 기하 · 극성)은 분포 통계다. 사람이
  본 것은 렌더링 방식과 모양이다. 통계가 맞아도 방식이 틀리면 즉시 구분된다.
- 이 결함들은 이전 세션에서 사람이 구두로 지적했는데 카드와 raw 와 위키
  어디에도 기록되지 않았다. 그래서 실행자가 본 적이 없고 같은 결함이 렌더러
  재작성을 두 번 통과했다. 기록하지 않은 것이 원인이다.
- Action taken: 카드로 세우고 AC 에 "고친 뒤 blind 시트를 다시 내고, 사람이
  여전히 전부 맞히면 남은 단서를 카드에 추가한다" 를 게이트로 넣었다.
  `synth_vs_real_sheet.py`(pair · blind · contrast)를 커밋해 이 검토를 명령
  하나로 만들었다.

  5.43% 인데 적어 둔 p10 이 5.44% 였다. 분포 자체가 다른 대상에서 온 값이다.

  조회하지 않고 말한 것이다.
- Action taken: 7.51% 를 출처 불명으로 폐기. 규칙을 양쪽에 박았다.
  `CLAUDE.md` 수치를 인용하기 전에 자가 이미 있는지 본다, 그리고
  `docs/GLM_TASKS.md` 3.7. 수치 옆에 명령과 n 을 적고, 자가 없어 새로
  만들면 그 스크립트를 커밋한다.

- 그리고 그 리뷰 자체가 중복이었다. 다른 세션이 이미 더 낫게 해 둔 것을
  같은 경로에 151줄로 덮어썼다.
