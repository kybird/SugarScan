## Case 1: G30 밴드 크롭 A/B 가 학습 예산 불일치로 무효였다 — 대조군 60에폭·0.1238 vs 새 팔 12에폭·0.96

### Grounding
- Git Context: `hash:eba39ca` (GLM 보고서) · `hash:7d38c8f` (판정)
- Evidence: `assets_dev/train/training_log.csv`(마지막 파인튜닝 런 60에폭 최종 손실 `0.1238338053226471`, 직전 두 런도 60에폭 `0.13472022116184235` · `0.10210204869508743`) · `training_log_letterbox.csv`(12에폭 `0.643500566482544`) · `docs/reports/G30-band-crop.md`(크롭 팔 12에폭 손실 0.96)
- Confidence: 5/5

### Error
세로형 밴드 크롭 프레이밍 A/B 의 결과표가 "크롭이 나쁘다"로 읽혔다:
완전일치 97.06% → 87.79%, 위험군 0.98% → 8.29%, McNemar p=1.68e-23.

실제로는 두 팔의 **학습 예산이 달랐다.** 대조군 `reader_model/` 은
파인튜닝 재시작 7회가 쌓인 결과로 마지막 런이 60에폭·손실 0.1238 인데,
새 팔은 스크립트 기본값인 12에폭·손실 0.96 에서 멈췄다(보고서에도 하강 중이라
명시). 손실 8배 차이 나는 두 모델을 비교한 표라 프레이밍의 성적이 아니다.

같은 구멍이 직전 G29 letterbox 팔(12에폭·0.64)에도 있었다.

### Environment Context
- `assets_dev/train/ctc_reader_v2.py` 사전학습 40 + 파인튜닝 12 (스크립트 기본값)
- Migration Issue: No

### Fix Code
지시서 쪽을 고쳤다 — `docs/GLM_TASKS.md` §3.5 신설:

```text
A/B 지시서에는
- 대조군의 실제 학습 예산을 로그에서 확인해 숫자로 적는다
  (training_log.csv 의 mtime 이 모델 폴더와 같은지부터 본다)
- 새 팔의 에폭 수를 그 숫자로 명시한다. "기본값 그대로"라고 쓰지 않는다
- 보고서에 양쪽의 최종 손실을 나란히 적게 한다
- 예산 끝에서도 손실이 하강 중이면 그렇게 적고 멈추게 한다
```

대조군 로그가 현 모델의 것인지 확인한 방법:

```bash
ls -lad reader_model training_log.csv   # mtime 이 둘 다 Sep 5 03:46 로 같다
awk -F, 'NR>1 && NF==2' training_log.csv | wc -l   # 파인튜닝 320행 = 재시작 누적
```

### Analysis
- Root cause: 지시서가 "에폭 수를 건드리지 말 것"이라고 적었고, 그 말이
  가리킨 **스크립트 기본값이 대조군이 실제로 받은 예산이 아니었다.**
  대조군은 사람이 재시작을 거듭하며 만든 모델이라 예산이 코드에 없고 로그에만 있다.
- Why it failed: "하이퍼파라미터 고정"은 **두 팔 사이의** 동일성만 보장한다.
  대조군이 코드 밖에서 만들어졌다면 코드를 고정해도 대조군과는 안 맞는다.
  정확도 격차가 프레이밍 효과와 수렴 부족의 합인데 표에서는 분리되지 않는다.
- 이 실험에서 특히 위험했던 이유: 크롭은 세로만 자르므로 가로 해상도
  (= CTC 타임스텝 40)를 건드리지 않는다. G29 가 세운 기전으로는 letterbox 보다
  **유리해야 하는** 팔인데 더 못 맞았다. 기전과 결과가 어긋날 때 결과를 그대로
  믿으면 방향이 맞는 레버를 버린다.
- How it was fixed: 채택/기각 대신 **보류**로 판정하고, 에폭만 60으로 맞춘
  재측정(G31)을 지시서로 냈다. 바뀌는 값이 하나뿐임을 지시서에 못박았다.

## Case 2: 세로 지터 0.15 가 파인튜닝을 붕괴시킨다 — 크롭 프레임에는 그만한 여유가 없다

### Grounding
- Git Context: `hash:eba39ca`
- Evidence: `docs/reports/G30-band-crop.md` — 파인튜닝 손실 6.90 → 5.52(3ep) → 5.40(12ep) 동결, TTA 완전일치 15/1122 = 1.34%, 위험군 882 (78.61%). 같은 캐시에서 세로 지터만 0.08 로: 5.94(2ep) → 4.91(4ep) → 2.83(6ep). `_diag/G30/probe_digit_band.py`
- Confidence: 5/5

### Discovery
크롭이 숫자를 프레임에 꽉 채우면 **증강 지터의 여유도 같이 사라진다.**
크롭 프레임에서 숫자 아래 여유의 p5 가 0.072 라 세로 이동 0.15 는 5% 이상의
장에서 획을 자른다(숫자 띠가 검출된 660장 기준, 절단 가능 비율 0.9% → 9.5%).
라벨은 그대로인데 획이 없어지므로 CTC 가 학습할 수 없는 짝이 되고, 모델은
모든 장에 같은 값을 내는 모드 collapse 로 떨어진다.

지시서는 "크롭이 조금 어긋나도 견디게" 하려고 지터를 0.08 → 0.15 로 올리라고
적었다. **의도와 정확히 반대 효과**였다.

### Analysis
- Why non-obvious: 지터를 키우는 것은 보통 정칙화라 안전한 쪽으로 여겨진다.
  여기서는 크롭이 여유를 먼저 없앴기 때문에 같은 값이 파괴적으로 바뀌었다 —
  **증강 강도는 절대값이 아니라 프레임의 여백에 대한 상대값이다.**
- 붕괴가 조용하지 않았던 것이 다행이다: 손실이 5.40 에서 동결되고 완전일치가
  1.34% 로 떨어져 표에서 바로 보인다. 조금만 잘렸다면 정확도가 몇 pp 떨어지고
  "크롭이 별로다"로 잘못 결론났을 것이다.
- Action taken: 0.15 폐기 확정. 재측정(G31)은 0.08 로 간다.
  원인 지정은 **같은 캐시에서 지터만 바꾼 차분 실험**으로 확정됐다 —
  이미지(크롭)와 증강을 분리한 이 설계가 없었으면 "크롭이 망쳤다"가 남았다.
