## Case 1: G30 밴드 크롭 A/B 가 학습 예산 불일치로 무효였다 — 대조군 60에폭·0.1238 vs 새 팔 12에폭·0.96

### Grounding
- Git Context: `hash:eba39ca` (GLM 보고서) · `hash:7d38c8f` (판정)
- Evidence: `assets_dev/train/training_log.csv`(마지막 파인튜닝 런 60에폭 최종 손실 `0.1238338053226471`, 직전 두 런도 60에폭 `0.13472022116184235` · `0.10210204869508743`) · `training_log_letterbox.csv`(12에폭 `0.643500566482544`) · `docs/reports/G30-band-crop.md`(크롭 팔 12에폭 손실 0.96)
- Confidence: 5/5

### Error
세로형 밴드 크롭 프레이밍 A/B 의 결과표가 "크롭이 나쁘다"로 읽혔다:
완전일치 97.06% → 87.79%, 위험군 0.98% → 8.29%, McNemar p=1.68e-23.

실제로는 두 팔의 **학습 예산이 달랐다.** 대조군 `reader_model/` 은
파인튜닝 재시작 7회가 쌓인 결과로 마지막 런이 60에폭·손실 0.1238 인데,
새 팔은 스크립트 기본값인 12에폭·손실 0.96 에서 멈췄다(보고서에도 하강 중이라
명시). 손실 8배 차이 나는 두 모델을 비교한 표라 프레이밍의 성적이 아니다.

같은 구멍이 직전 G29 letterbox 팔(12에폭·0.64)에도 있었다.

### Environment Context
- `assets_dev/train/ctc_reader_v2.py` 사전학습 40 + 파인튜닝 12 (스크립트 기본값)
- Migration Issue: No

### Fix Code
지시서 쪽을 고쳤다 — `docs/GLM_TASKS.md` §3.5 신설:

```text
A/B 지시서에는
- 대조군의 실제 학습 예산을 로그에서 확인해 숫자로 적는다
  (training_log.csv 의 mtime 이 모델 폴더와 같은지부터 본다)
- 새 팔의 에폭 수를 그 숫자로 명시한다. "기본값 그대로"라고 쓰지 않는다
- 보고서에 양쪽의 최종 손실을 나란히 적게 한다
- 예산 끝에서도 손실이 하강 중이면 그렇게 적고 멈추게 한다
```

대조군 로그가 현 모델의 것인지 확인한 방법:

```bash
ls -lad reader_model training_log.csv   # mtime 이 둘 다 Sep 5 03:46 로 같다
awk -F, 'NR>1 && NF==2' training_log.csv | wc -l   # 파인튜닝 320행 = 재시작 누적
```

### Analysis
- Root cause: 지시서가 "에폭 수를 건드리지 말 것"이라고 적었고, 그 말이
  가리킨 **스크립트 기본값이 대조군이 실제로 받은 예산이 아니었다.**
  대조군은 사람이 재시작을 거듭하며 만든 모델이라 예산이 코드에 없고 로그에만 있다.
- Why it failed: "하이퍼파라미터 고정"은 **두 팔 사이의** 동일성만 보장한다.
  대조군이 코드 밖에서 만들어졌다면 코드를 고정해도 대조군과는 안 맞는다.
  정확도 격차가 프레이밍 효과와 수렴 부족의 합인데 표에서는 분리되지 않는다.
- 이 실험에서 특히 위험했던 이유: 크롭은 세로만 자르므로 가로 해상도
  (= CTC 타임스텝 40)를 건드리지 않는다. G29 가 세운 기전으로는 letterbox 보다
  **유리해야 하는** 팔인데 더 못 맞았다. 기전과 결과가 어긋날 때 결과를 그대로
  믿으면 방향이 맞는 레버를 버린다.
- How it was fixed: 채택/기각 대신 **보류**로 판정하고, 에폭만 60으로 맞춘
  재측정(G31)을 지시서로 냈다. 바뀌는 값이 하나뿐임을 지시서에 못박았다.

## Case 2: 세로 지터 0.15 가 파인튜닝을 붕괴시킨다 — 크롭 프레임에는 그만한 여유가 없다

### Grounding
- Git Context: `hash:eba39ca`
- Evidence: `docs/reports/G30-band-crop.md` — 파인튜닝 손실 6.90 → 5.52(3ep) → 5.40(12ep) 동결, TTA 완전일치 15/1122 = 1.34%, 위험군 882 (78.61%). 같은 캐시에서 세로 지터만 0.08 로: 5.94(2ep) → 4.91(4ep) → 2.83(6ep). `_diag/G30/probe_digit_band.py`
- Confidence: 5/5

### Discovery
크롭이 숫자를 프레임에 꽉 채우면 **증강 지터의 여유도 같이 사라진다.**
크롭 프레임에서 숫자 아래 여유의 p5 가 0.072 라 세로 이동 0.15 는 5% 이상의
장에서 획을 자른다(숫자 띠가 검출된 660장 기준, 절단 가능 비율 0.9% → 9.5%).
라벨은 그대로인데 획이 없어지므로 CTC 가 학습할 수 없는 짝이 되고, 모델은
모든 장에 같은 값을 내는 모드 collapse 로 떨어진다.

지시서는 "크롭이 조금 어긋나도 견디게" 하려고 지터를 0.08 → 0.15 로 올리라고
적었다. **의도와 정확히 반대 효과**였다.

### Analysis
- Why non-obvious: 지터를 키우는 것은 보통 정칙화라 안전한 쪽으로 여겨진다.
  여기서는 크롭이 여유를 먼저 없앴기 때문에 같은 값이 파괴적으로 바뀌었다 —
  **증강 강도는 절대값이 아니라 프레임의 여백에 대한 상대값이다.**
- 붕괴가 조용하지 않았던 것이 다행이다: 손실이 5.40 에서 동결되고 완전일치가
  1.34% 로 떨어져 표에서 바로 보인다. 조금만 잘렸다면 정확도가 몇 pp 떨어지고
  "크롭이 별로다"로 잘못 결론났을 것이다.
- Action taken: 0.15 폐기 확정. 재측정(G31)은 0.08 로 간다.
  원인 지정은 **같은 캐시에서 지터만 바꾼 차분 실험**으로 확정됐다 —
  이미지(크롭)와 증강을 분리한 이 설계가 없었으면 "크롭이 망쳤다"가 남았다.

## Case 3: 예산을 맞추자 격차의 6/7 이 사라졌다 — 그래도 기각했다, 오답의 성격이 바뀌어서

### Grounding
- Git Context: `hash:3d0cba0`
- Evidence: `assets_dev/train/training_log_bandcrop_ty008_e60.csv`(60에폭 최종 `0.10946083813905716`) · `training_log.csv`(기준선 마지막 런 60에폭 `0.1238338053226471`) · `assets_dev/train/_diag/G31/ab_report_ty008_e60.json`(`{'b': 15, 'c': 30, 'p': 0.0356978035551946}`) · `docs/reports/G31-bandcrop-epoch-matched.md`
- Confidence: 5/5

### Hypothesis
Case 1 에서 무효로 판정한 밴드 크롭 A/B 를, 파인튜닝 예산만 12 → 60에폭으로
맞춰 다시 잰다. 예산이 원인이었다면 격차가 좁아져야 한다.

### Results
예산은 실제로 맞았다 — 크롭 팔 60에폭 최종 손실 0.1095, 기준선 마지막 런
0.1238. 12·30에폭 지점도 0.9142/0.2754 대 0.5601/0.2668 로 같은 궤적.
**크롭 팔의 학습 손실이 오히려 더 낮다.**

완전일치 87.79% → 95.72% (기준선 97.06%). McNemar p 1.68e-23 → 0.0357.
격차 9.27pp 중 7.93pp 가 에폭 하나로 사라졌다.

오답의 구성:

```text
             완전일치   위험군   blank   안전 실패
기준선        1089       11       3       19
크롭 60에폭   1074       39       0        9
```

독립 재계산으로 보고서 표를 재현했다(reader_preds_bandcrop_ty008_e60.json,
n=1122 → exact 1074 · risky 39 · safe 9 · blank 0).
새로 틀린 30장 중 **25장이 위험군**이고, 크롭 팔 위험군 39건 중 **35건이
기준선에 없던 새 오답**이다(교집합 4건).

### Analysis
- Confirmed: Case 1 의 진단이 맞았다. 예산 불일치가 격차의 대부분을 만들었다.
  §3.5 규약(대조군의 실제 예산을 지시서에 숫자로 적는다)이 값을 했다.
- 그런데 **결론은 뒤집히지 않았다 — 이유만 유효해졌다.** 기각의 근거가
  "덜 학습된 표"에서 "예산 맞춘 표"로 바뀌었다.
- Key metrics: 완전일치 격차는 1.34pp 로 좁은데 **위험군은 0.98% → 3.48%
  로 3.5배**다. 크롭은 오답의 총량보다 **성격**을 바꾼다 — 침묵과 자릿수
  붕괴(22건 → 9건)를 줄이는 대신 자릿수 보존 오독을 28건 늘린다.
  숫자가 프레임을 채워 모델이 자릿수를 확신하게 되고, 확신이 붕괴 대신
  **그럴듯한 틀린 값**으로 나온다.
- Implications: 혈당 앱에서 자릿수 붕괴는 값 검증기와 프레임 합의가 잡지만
  자릿수 보존 오독은 통과한다. 안전 실패를 위험 실패로 바꾸는 교환은
  완전일치가 올라가도 받을 수 없다. **정확도 한 숫자로는 이 교환이
  보이지 않는다** — G31 을 완전일치만 보고 읽으면 "1.34pp 차이"다.
- 에폭을 더 늘리지 않기로 했다. 학습 손실이 이미 기준선보다 낮은데
  홀드아웃이 나쁘다 — 더 태우면 확신이 더 세져 위험군이 늘어날 쪽이다.
- 부수: 가로형 층 57.1% → 28.6%(21장). 가로형 입력은 픽셀 항등(44/44)이라
  재학습 효과다. 학습의 98.2%가 크롭된 세로형이라 가로형 풀프레임이 분포
  밖이 된다. 프레이밍을 한 층에만 적용하면 **손대지 않은 층이 분포 밖으로
  밀려난다.**

## Case 4: 정본 문서가 저장소 상태에 대해 한 사실 주장이 조용히 낡아 있었다

### Grounding
- Git Context: `hash:f10074a` (에셋이 커밋된 시점) · 발견은 `hash:289f828` 이후
- Evidence: `git ls-files --error-unmatch assets/models/7seg_classifier.tflite` → 추적됨(609,904 바이트, gitignore 대상 아님). 같은 시점 `CLAUDE.md:341` 은 "`assets/models/7seg_classifier.tflite` 는 아직 저장소에 없다"
- Confidence: 5/5

### Discovery
`CLAUDE.md`(에이전트 지침의 정본)와 `assets/models/README.md` 가 둘 다
"7seg_classifier.tflite 는 아직 없음"이라고 적고 있었는데, 파일은 `f10074a`
에서 이미 커밋돼 있었다. README 는 제목에 "(아직 없음)"을 달아 둔 채 바로
아래 표에 그 파일의 정확한 크기(609,904 바이트)를 적고 있었다 — 문서 안에서
이미 자기모순이었다.

### Analysis
- Why non-obvious: 문서의 **규약**(무엇을 하지 마라)은 어기면 사람이 지적하지만,
  문서의 **사실 주장**(무엇이 있다/없다)은 어겨도 아무도 실패하지 않는다.
  코드가 바뀌면 테스트가 깨지는데, 문서의 사실 주장을 지키는 테스트는 없다.
  에셋을 커밋한 작업은 "에셋 추가"였지 "문서 갱신"이 아니었다.
- Impact: 이 문장을 읽은 에이전트는 앱이 `ScanUnavailable` 로 떨어지는 상태를
  기본으로 가정한다. 실제로는 CNN 엔진이 살아 있으므로 진단이 어긋난다.
- 더 큰 형태: 같은 문서가 **CTC 리더가 앱에 있는지**에 대해서는 아무 말도
  하지 않아, 홀드아웃 97.06% 를 앱 성능으로 오해할 여지가 있었다.
  실제로는 `ocr_bootstrap.dart` 에 `SegmentRuleEngine` 과 7-세그먼트 CNN 만
  등록돼 있고 CTC 리더는 `assets_dev/train/` 밖으로 나온 적이 없다.
- Action taken: 두 문서를 고쳤다. "없다"를 "있다(`f10074a`)"로 바꾸되
  **없어도 동작해야 한다는 설계 불변**은 남겼다(그게 규약이고, 사실 주장이
  아니다). CTC 리더가 아직 앱에 없다는 문장을 명시적으로 추가했다.
- 일반화: 문서에 사실 주장을 적을 때는 **확인 명령을 같이 적는다.**
  "없다"보다 "`git ls-files ...` 로 확인하라"가 낡지 않는다.

## Case 5: 오프라인 지표를 세 번 재는 동안 온디바이스는 0번 쟀다 — 잴 수 있는 것만 반복해 재는 편향

### Grounding
- Git Context: `hash:289f828`
- Evidence: G29·G30·G31 세 작업 모두 같은 홀드아웃 1,122장 지표(`docs/DONE.md`). `lib/ocr/src/ocr_bootstrap.dart` 등록 엔진 = `SegmentRuleEngine` + `SevenSegCnnEngine` 뿐. 층별 실측 — 가로형 21/1122(1.9%) · 완전일치 12 · 위험군 3 · 안전 실패 6
- Confidence: 4/5

### Discovery
G32(가로형 검출 실패 13장 진단)를 다음 작업으로 집으려다 천장을 먼저 쟀다.
가로형은 홀드아웃의 **1.9%** 이고, 9건을 전부 맞혀도 완전일치 기여는
**+0.80pp**, 위험군 기여는 **-0.27pp** 다.

그리고 더 큰 사실이 그 옆에 있었다: **97.06% 를 내는 CTC 리더는 앱에 없다.**
세 번의 A/B 는 전부 PC 측 정지 사진 홀드아웃에서 돌았고, 앱이 실제로 보는
라이브 카메라 프레임 · 가이드 박스 ROI 정렬 위에서는 한 번도 재지 않았다.

### Analysis
- Why non-obvious: 홀드아웃 평가는 **싸고 재현 가능하고 표가 예쁘다.**
  실기기 측정은 비싸고 재현이 어렵다. 그래서 다음 작업을 고를 때 자연히
  잴 수 있는 쪽으로 손이 간다. 세 작업이 연속으로 같은 숫자를 다듬은 것이
  그 결과다 — 각각은 정당했지만 합치면 편향이다.
- 진단 작업(G32)은 그 자체로 모델을 전진시키지 않는다. 산출이 그림과 표라
  "무언가 진행됐다"는 느낌은 주지만 가중치도 코드도 안 바뀐다.
  진단은 **다음 수정이 정해져 있을 때** 값이 있다.
- Impact: 작업 순서를 바꿨다. G32 는 열어 두되 우선순위를 올리지 않고,
  실제 전진 경로는 ONNX 내보내기(G28 결론) → 단말/PC 패리티 →
  실기기 튜닝(`CLAUDE_TASKS.md` C2)이다.
- 점검 질문: **"이 작업이 끝나면 무엇이 달라지는가"**에 "숫자를 알게 된다"만
  답이 나오면, 그 숫자로 무엇을 할지가 이미 정해져 있는지 먼저 확인한다.
- 층을 찾았으면 크기를 곱하라는 규칙([[aggregate-hides-stratified-failure]])의
  적용 사례이기도 하다. 이번엔 작업을 열기 **전에** 곱했다.
