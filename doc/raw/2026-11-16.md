
## [2026-11-16 error] Case 4: 테스트 정리 rm 이 살아 있는 정답표를 지웠다 — 브라우저 메모리 복구

### 검색 단서
rm 사고, 테스트 정리 습관, 지우기 전 미확인, 라벨 진행 중 파일, 브라우저
메모리 복구, Q 배열, dc238_labels.jsonl, 백업 훅

### Grounding
- Git Context: `hash:85b2219`
- Evidence: dc238_labels.jsonl(219행)·dc238_labels.bak.jsonl·/api/dc238rebuild
- Confidence: 5/5

### 상황
라벨러 라우트 테스트 후 "테스트 행 정리" 습관으로 `rm -f dc238_labels.jsonl`
을 실행했다 — 그 파일은 이제 테스트 행이 아니라 **사용자가 라벨 중인 212행
정답표**였다. 삭제 전 파일 상태를 보지 않았다(운영 원칙 위반: 지우기 전에
대상을 볼 것). gitignore 영역이라 git 안전판도 없었다.

### 가설
복구 원본은 없는가 — 서버는 요청마다 파일을 새로 읽어 캐시가 없고, 파일
시스템 unlink 는 돌이킬 수 없다. 남은 원본은 **열려 있는 브라우저 탭의
메모리**(라벨러 페이지의 Q 배열: 큐 적재 시점의 저장본 + 이후 저장 merge)
뿐이다.

### 판정
Q 배열이 전량을 들고 있었다(큐 로드가 저장본을 seed 하고 post() 가
Object.assign 으로 갱신). 콘솔 fetch 한 줄로 /api/dc238rebuild 에 던져
212행 복구 성공. 단 복구 코드가 `source` 필드 대신 큐의 `skipped` 플래그를
봐서 K(판독불가) 28장이 human-noquad 로 오분류 — 값↔쿼드 결합 규칙
(값 있으면 human+쿼드, 없으면 skipped)으로 결정적 수정. 원칙: **저장
스키마의 정본은 저장 필드(source)지, 파생 뷰 플래그(skipped)가 아니다.**

### 조치
① 저장 경로(dc238·rebuild)마다 직전 상태 .bak 복사 훅 ② gitignore 예외
강제 커밋(-f)으로 원격 안전판 ③ 사용자 탭은 복구 후에도 살아 있어 이후
라벨 7행 추가 — 복구본+신규 병합 무손실 확인. 재발 방지의 핵심은 백업이
아니라 **rm 전 대상 확인**이지만, 인간은 실수하므로 훅이 뒷받침한다.
