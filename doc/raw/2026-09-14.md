## Case 1: 데이터 스케일링은 40k 에서 끝났고, 기울기만 계속 배웠다

### Grounding
- Git Context: `hash:20a15b4` · `hash:4434407`
- Artifact: `scratchpad/run_night.log` · `assets_dev/train/band_det_corner_error.py`
- Confidence: 5/5

### Hypothesis
합성 데이터 양이 밴드 검출기의 병목인가. 5k → 10k → 20k → 40k → 40k×60ep →
80k 를 같은 조건으로 굽고 사람 라벨 게이트로 잰다.

### Results

게이트(실사진, 사람 밴드 라벨 276장 기준):

| 판 | 전체 | 세로형(210) | 가로형(66) |
|---|---|---|---|
| n5k | 0.729 | 0.752 | 0.540 |
| n10k | 0.737 | 0.772 | 0.602 |
| n20k | 0.776 | 0.807 | 0.642 |
| n40k | 0.804 | 0.836 | 0.648 |
| n40k_ep60 | 0.824 | 0.850 | 0.692 |
| n80k | 0.826 | 0.847 | 0.730 |

합성 홀드아웃(GT 가 정확한 네 점, n=800):

| 판 | 모서리 오차 | 기울기 오차 | corr(GT,예측) |
|---|---|---|---|
| n10k | 3.64% | 0.624deg | 0.133 |
| n20k | 2.67% | 0.613deg | 0.057 |
| n40k | 1.74% | 0.543deg | 0.616 |
| n40k_ep60 | 1.15% | 0.194deg | 0.910 |
| n80k | 1.17% | 0.216deg | 0.947 |

### Analysis
- Confirmed: 데이터는 병목이었다. 단, **40k 에서 끝났다.** 40k→80k 는 두 배를
  부어 게이트 0.824 → 0.826, 모서리 1.15% → 1.17% 로 학습 노이즈 바닥(~0.01)
  안이다. 160k 를 굽던 중 죽이고 코퍼스를 지웠다.
- 세 축이 서로 다른 말을 한다: 게이트와 모서리 오차는 멈췄는데 **기울기
  상관만 계속 오른다**(0.910 → 0.947). 축정렬 라벨이 기울기를 못 담으므로
  그 향상은 게이트에 나타나지 않는다.
- 기울기는 **거친 위치가 포화한 뒤에야 배우는 저진폭 신호**다. 20k 까지는
  예측 기울기가 0.030deg 로 뭉개져 있다가(corr 0.057) 40k 에서 신호가 잡히고
  ep60 에서 0.910 이 된다. 합성 홀드아웃에서도 그러므로 게이트 탓이 아니다.
- 가로형만 끝까지 오른다(0.692 → 0.730). 세로형은 포화(0.850 → 0.847).

## Case 3: 파라미터의 85%가 한 줄에 있었다 — Flatten 이 위치를 지운다

### Grounding
- Git Context: `hash:0cf628e`
- Evidence: `assets_dev/train/train_band_detector.py` `BandQuadHeat`
- Confidence: 4/5

### Design Decision
밴드 쿼드 회귀의 머리부를 `Flatten + Linear(8192,512)` 에서
**모서리별 히트맵 + soft-argmax** 로 바꾼 판을 선택지로 추가했다.

```
구판 fc    conv 5단 -> 8x8x128 -> Flatten(8192) -> Linear(8192,512) -> Linear(512,8)
           4,915,344 파라미터 중 4,194,304(85%)가 Linear(8192,512) 한 줄

새판 heat  conv 4단 -> 16x16x128 -> Conv(128,128,3) -> Conv(128,4,1) -> 히트맵 4장
           soft-argmax 로 (x,y) 4개.  569,100 파라미터 (8.6배 작다)
```

### Alternatives Considered
- Option A: 그냥 키운다(채널 24→32, FC 512→1024) — 8192 병목이 그대로다.
  파라미터만 1,600만으로 부풀고 과적합 위험이 같이 오른다. 기각.
- Option B: CoordConv 로 위치 채널을 더한다 — 변경은 싸지만 원인(펴는 행위)을
  그대로 둔 채 증상만 눌렀다. 기각.
- Selected: 히트맵 + soft-argmax. 자세추정의 표준 해법이고, 격자가 16x16 이어도
  soft-argmax 가 칸 안의 소수점 위치를 연속으로 낸다.

### Decision Code
```python
p = torch.softmax(h.reshape(n, c, gh * gw) / self.temp, dim=-1).reshape(n, c, gh, gw)
ex = (p.sum(dim=2) * xs).sum(dim=-1)
ey = (p.sum(dim=3) * ys).sum(dim=-1)
```

### Analysis
- Context: 합성 홀드아웃에서는 **전부 이겼다.** 모서리 1.15% → 0.87%,
  기울기 0.194deg → 0.139deg, corr 0.910 → 0.948, 파라미터 4.92M → 0.57M.
  **실사진 게이트에서는 졌다**: 0.824 → 0.798(세로형 0.850 → 0.812).
- **Trade-offs**: 8.6배 작은 몸으로 합성 정밀도를 전부 이겼다. Flatten 가설은
  맞았다. 그러나 실사진으로 넘어가지 않았다.
- **가르지 못한 것**: heat 는 실사진의 68.9%를 1도 넘게 기울인다(fc 는 23.1%).
  헛기울기인지, 라벨이 축정렬이라 손해로 잡히는 것인지 지금 자로는 못 가른다.
- Reversibility: 높다. `--arch` 기본값을 `fc` 로 두고 옛 클래스를 남겼다.
  `load_detector` 가 state_dict 모양으로 구조를 알아내므로 옛 체크포인트
  아홉 개가 그대로 돈다(`band_det_n80k` 재측정 0.826 = 이전과 동일).

## Case 4: 사람 라벨이 전부 축정렬이라 기울기를 채점할 수 없었다

### Grounding
- Git Context: `hash:20a15b4`
- Evidence: `band_boxes.jsonl` · `screen_boxes.jsonl` · `gmscreen_quads_oriented.jsonl`
- Confidence: 5/5

### Discovery
저장소의 라벨이 **하나도 빠짐없이 축정렬**이다.

```
                    n      median   max    기울기>=0.5도
사람 밴드 상자        277    0.000   0.000      0.0%
사람 화면 쿼드        410    0.000   0.000      0.0%
검출기 화면 쿼드     2497    0.000   0.000      0.0%
```

합성은 그렇지 않다 — 밴드 쿼드 median 0.581deg, p90 1.462deg, max 4.86deg
(회전 ±1.5도가 70% 확률, 키스톤이 35% 확률로 얹힌다).

사람의 진술: **"실촬영의 각도는 제각각이다. 사람은 정확한 0도를 찍을수없다."**
그러므로 틀린 쪽은 합성이 아니라 라벨이다 — 웹툴이 드래그 상자만 그릴 수 있어
기울기를 담을 그릇이 처음부터 없었다.

### Analysis
- Why non-obvious: 라벨 파일의 스키마가 `quad`(4x2)라 기울기를 담을 수 있게
  **생겼다.** 값이 전부 축정렬이라는 것은 열어 보기 전에는 알 수 없다.
  검출기 출력조차 축정렬이었다 — 상자를 쿼드 모양으로 적은 것이었다.
- Impact: 기울기를 맞히는 모델과 0 으로 뭉개는 모델이 게이트에서 구분되지
  않는다. n20k(corr 0.057)와 n40k_ep60(corr 0.910)의 게이트 차이는 0.05뿐이다.
  **실사진에서 기울기가 맞는지는 현재 측정 불가다.**
- 더 나쁜 신호: fc 모델의 실사진 예측 기울기 분포가 **합성 GT 분포와 거의
  같다**(median 0.52~0.64 vs 0.581, p90 도 겹친다). 실촬 각도가 제각각이라면
  그럴 이유가 없다 — 모델이 사진을 재는 게 아니라 **학습 분포를 되뱉고
  있을** 가능성이 있다.
- Action taken: 라벨을 고치는 쪽(웹툴에 회전 쿼드 모드)을 제안했다가
  **철회했다.** 화면 표시 지렛대로 계산하니 사람이 핸들을 2px 안에 놓아도
  각도 오차가 0.198deg 로, 재려는 값(모델 오차 0.194deg)과 같다. 자의 잡음이
  대상과 같으면 그 자로는 못 잰다.
- 남긴 결론: 기울기는 **합성이 공짜로 가르치는 것**으로만 두고, 맞는지는
  나중에 리더가 값을 읽어서 답하게 한다.

## Case 5: 사람 라벨이 두 자리만 감쌌다 — 산출물을 본 사람이 찾았다

### Grounding
- Git Context: `hash:ef8e23e`
- Evidence: `assets_dev/train/band_label_slot_audit.py` ·
  `_diag/cmp_worst_portrait.png`
- Confidence: 5/5

### Error
사람이 검출기 비교 시트를 보고 **"사람 라벨링이 숫자를 두자리만 감싸고있네"**
라고 지적했다. 재 보니 맞았다 — 2자리 값 44장 중 **15장**이 빈 앞자리를
넣지 않고 숫자 두 개만 딱 감쌌다.

```
밴드 상자 w/h 분포
 자리   n     p5     p25   median    p95
  2    44   0.905  1.215   1.394   1.930     <- p5 가 3자리의 70%
  3   232   1.299  1.480   1.609   2.014
```

같은 2자리 값인데 어떤 장은 0.89(두 자리만), 어떤 장은 1.93(빈자리 포함).
**규약이 장마다 갈렸다.**

### Environment Context
- Packages: sugartrain
- Migration Issue: No
- 규약은 '빈자리를 넣는다'다(사람 지침). 합성기도 그렇게 그린다 — 2자리
  밴드 w/h 1.591 vs 3자리 1.601(n=40000). 검출기는 규약대로 내고도 점수를
  잃고 있었다.

### Fix Code
```
band_label_slot_audit.py    감사 자
make_band_slot_queue.py     수정 큐 + 전수 검토 큐
webtool 큐 "밴드 수정 · 빈 앞자리 누락" · "밴드 라벨 전수 검토 (의심 순)"
```
전수 큐는 자릿수별 중앙 w/h 에서 벗어난 순이다 — 끝까지 볼 필요가 없게,
중간에 멈춰도 이상한 것은 이미 본 상태가 되게.

### Analysis
- Root cause: 라벨 규약에 '빈 슬롯을 포함한다'는 항목이 **글로만 있고 자가
  없었다.** 지키는지 확인할 방법이 없으면 규약은 갈린다.
- 크기: 그 15장은 어느 모델에서도 IoU 0.53~0.62 에 갇혀 있었다(나머지는
  0.71~0.84). 전체의 5.4%라 중앙값은 0.006~0.010 만 눌렸고 **모델 비교
  순위는 바뀌지 않았다.**
- **진짜 피해는 다른 데 있었다**: 최악 사례 시트를 이 15장이 점령해서,
  라벨 결함을 모델 결함으로 읽게 만들었다. 실제로 그 시트 위에서
  "heat 구조가 세로형에서 퇴보했다"는 진단을 세우던 중이었다.
- 수정 뒤: 그 14장이 0.598 → 0.741(n80k)로 올랐다. 2자리 중앙 w/h 가
  1.394 → 1.701 로 3자리(1.647)를 넘었다 — 빈 슬롯이 들어갔다는 신호다.
  구판 v0 만 거꾸로 0.616 → 0.479 로 떨어졌다. 빈자리를 안 넣고 그리던
  합성기로 학습한 모델이라, 라벨이 규약대로 서니 손해를 봤다 — 수정이
  맞았다는 방증이다.
- 사람이 찾았다는 사실이 중요하다. **지표는 이걸 못 잡았다** — 15장이 전체
  중앙값을 0.01 도 못 움직였기 때문이다.

## Case 6: 상대 문턱으로 만든 감사 자는 합격을 선언할 수 없다

### Grounding
- Git Context: `hash:0fa69b8` 이후
- Evidence: `assets_dev/train/band_label_slot_audit.py` 머리말
- Confidence: 5/5

### Error
사람이 전수조사로 라벨을 전부 고친 뒤에도 자가 **"빈자리를 안 넣은 2자리
라벨: 5/43"** 을 계속 냈다. 사람이 물었다: **"반자리 누락 다섯장이 뭐지?
난 전수조사해서 채웟는데"**.

### Environment Context
- Packages: sugartrain
- Migration Issue: No

### Fix Code
```python
verdict = "진짜 결함" if mt < mo - 0.05 else "문턱 오탐(결함 아님)"
```
머리말에 "걸린 장 수를 합격 기준으로 쓰지 마라"를 명시했다.

### Analysis
- Root cause: 문턱이 `3자리 중앙 w/h × 0.80` 이라는 **상대 기준**이었다.
  라벨을 전부 고치면 분포가 통째로 올라가고 문턱도 따라 오른다
  (1.287 → 1.317 → 1.323). 하위 몇 장은 영원히 걸린다. **0 이 나올 수 없는
  자였다.**
- Why it failed: 기기마다 숫자 간격이 달라 **w/h 하나로 슬롯 수를 판정할 수
  없다.** 이 자는 결함을 *찾는* 데는 유효했지만 *합격을 선언*하는 데는
  처음부터 쓸 수 없었다. 발견용 자와 검증용 자는 다른 물건이다.
- 잘못된 보고: 나는 "아직 5장 남았다"고 보고했다. 그 5장 중 넷은 문턱을
  1.252~1.312 로 아슬아슬하게 못 넘긴 정상 라벨이었고, 결정적으로 **그
  무리의 게이트 IoU 가 나머지와 같거나 높았다**(0.814 vs 0.802).
  판정 신호가 눈앞에 인쇄돼 있었는데 개수만 읽었다.
- 다섯 번째 장 `1565` 는 성격이 아예 달랐다. 사람이 말했다: **"1565 는
  가로형을 90도 회전한것이다 그래서 왼쪽의 빈칸이 아니라 위쪽의 빈칸이다."**
  폭 기준 자가 구조적으로 오탐할 수밖에 없는 장이었다.

- Option A: 기하로 자동 판정(화면 쿼드가 사진 가장자리에 닿는 장 = 19장) —
  기각. 가로형은 화면이 원래 꽉 차서 닿는다. 오탐이 대부분이다.
- Option B: 라벨을 고친다 — 불가능하다. 필요한 화소가 프레임 밖이다.
- Selected: **사람 선언**. `band_label_excluded.jsonl` 에 사유와 노트를 적는다.

### Decision Code
```python
def drop(rows, key=lambda r: r["id"], report=True, where=""):
    """제외 목록에 있는 행을 뺀다. 뺀 수를 인쇄한다 — 분모가 조용히 바뀌면
    이전 수치와 나란히 인용됐을 때 아무도 눈치채지 못한다."""
```

### Analysis
- Context: **내가 틀린 자리** — 2431 을 보고 "여유/칸폭 0.24 라 제외", 2489 는
  "3자리라 빈자리가 없으니 오탐, 그대로 두라"고 판정했다. 사람이 뒤집었다.
  **세 자리가 다 보인다는 것과 숫자칸이 온전하다는 것은 다른 말**이었다.
  나는 글자가 보이는지를 봤고, 기준은 숫자칸 영역이었다.
- **Trade-offs**: 분모가 276 → 271 로 바뀐다. 이전 수치와 나란히 인용하면 안
  된다. `drop()` 이 뺀 수를 매번 인쇄하게 한 이유다.
- 사유를 두 종으로 나눈 이유: `no-upright-normalization` 은 **되돌릴 대상**이다.
  90도 회전은 밴드 검출기가 풀 문제가 아니라 그 앞에서 풀 문제다(화면을
  찾고 → digit_top 판정 → 크롭을 세우고 → 검출기). 그 단계가 생기면 두 장을
  다시 넣는다. 섞어 두면 무엇을 되돌릴지 사라진다.
- 합성이 그 분포를 안 만든다는 근거: 합성 밴드 w/h 가 `w/h<1.0` 을 0.18%만
  낸다. 실사진 두 장은 0.517 · 0.574 다. 검출기가 본 적 없는 장이다.
- Reversibility: 높다. 파일 한 줄씩이고 사유가 붙어 있다.

## Case 8: 전폭 라벨을 검토했다 — 검출기는 x 축에서 안 헤맨다

### Grounding
- Git Context: `hash:0fa69b8` 이후
- Artifact: 합성 홀드아웃 800장, `band_det_corner_error` 와 같은 예측 경로
- Confidence: 4/5

### Hypothesis
사람이 물었다: 세로형에서 밴드를 세 칸 너머 **화면 가로 전체**로 라벨하면
모델이 더 잘 찾지 않겠는가. 좌우 베젤까지 넣으면 어떤가.

### Results
오차를 축으로 갈랐다(각 축을 자기 크기로 정규화):

| ckpt | x오차 | y오차 | x/y | 폭오차 | 높이오차 |
|---|---|---|---|---|---|
| n40k_ep60 | 0.49% | 0.64% | 0.76 | 0.67% | 0.85% |
| n80k | 0.48% | 0.67% | 0.71 | 0.64% | 0.91% |
| heat40k | 0.39% | 0.42% | 0.92 | 0.51% | 0.52% |

현재 밴드가 화면 폭을 쓰는 비율:

| | p10 | median | p90 |
|---|---|---|---|
| 세로형(210) | 0.768 | 0.875 | 0.989 |
| 가로형(63) | 0.439 | 0.555 | 0.825 |

### Analysis
- Refuted. **가로가 이미 세로보다 정확하다**(x/y 0.71~0.92). 전폭 라벨은
  이미 잘하는 축을 더 쉽게 만들고 어려운 축은 그대로 둔다.
- 세로형은 이미 화면 폭의 87.5%를 쓴다. 전폭까지 늘려도 12% 늘 뿐이다.
- 가로형은 전폭이 곧 **오른쪽 정보 칼럼 포함**이다(밴드가 55%, 나머지 45%가
  시간·날짜·mg/dL). 세로형만 전폭으로 하면 **가족마다 규약이 갈린다** —
  이번에 빈자리로 겪은 것과 같은 종류의 혼란이다.
- 베젤 포함은 앞단(GM 검출기)이 이미 한 일을 뒷단에 다시 시키는 것이다.
- **내가 처음에 든 근거는 약했다**: "리더가 해상도를 잃는다"고 답했는데,
  리더는 아직 굽지도 않았고 프레이밍과 목표 크기도 우리가 정한다. 사람이
  "지금은 검출기인거알지"라고 지적했고 맞았다. 없는 하류를 근거로 상류
  설계를 막으면 안 된다. 다시 답한 근거가 위 표다.

## Case 9: 같은 래퍼로 두 번 재시작해 두 시간을 날렸다

### Grounding
- Evidence: `scratchpad/run_wide.stuck.log` · `scratchpad/wide40_train.log`
- Confidence: 4/5

### Error
가로형 비중 40% 실험이 두 번 죽었다.

1차(18:50~19:00): 6 에폭 돌다 **교착**. 프로세스는 살아 있는데 20초 동안
CPU 사용 증가가 **0초**였다. DataLoader 워커(`num_workers=4`) 교착으로 본다.
그 시각 호스트 여유 메모리가 5.7 GB 였다(다른 프로젝트의 pytest 가 12.4 GB).

2차(20:27): **같은 래퍼로** 재시작했더니 학습이 출력 없이 즉시 끝났다.
체크포인트가 만들어지지 않았다. 학습 코드를 직접 돌리면 정상이다.

### Environment Context
- Packages: sugartrain, PyTorch, Windows
- Migration Issue: No

### Fix Code
래퍼를 경로에서 빼고 학습을 직접 띄웠다. 90초/에폭으로 정상 — 기존 판
(2분/에폭)보다 오히려 빠르다.

### Analysis
- Root cause(1차): 메모리 압박 하의 워커 교착으로 **추정한다. 확정하지
  못했다** — 재현 조건을 못 잡았다.
- Root cause(2차): 실행 래퍼. 스크립트 안 인라인 heredoc 구간에서 멎는다.
- **Why it failed(진짜 교훈)**: 1차 실패의 원인을 메모리로 **단정하고** 같은
  래퍼로 재시작했다. 원인을 확정하지 않은 채 같은 경로를 다시 탄 것이
  두 번째 실패를 불렀다. 저장소 규칙 「증상이 그대로면 같은 계층을 다시 파지
  않는다」의 실행판을 어겼다 — 두 번째 시도에서 바꾼 것이 아무것도 없었다.
- 관측 방법도 부족했다. 로그가 88분간 갱신이 없는데 GPU 사용률만 보고
  "돌고 있다"고 읽었다. GPU 는 다른 프로세스 것이었다. **프로세스의 CPU
  누적 시간 증가분**이 살아 있는지 죽었는지를 가르는 신호였다.
