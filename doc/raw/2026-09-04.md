## Case 1: 평가 스크립트만 EXIF 무처리 — CTC 리더 11.7%는 모델이 아니라 계측이었다 (실제 92.9%)

### Grounding
- Git Context: `hash:b015830`
- Evidence: 동일 모델·동일 이미지·동일 워프에서 `ImageOps.exif_transpose` 한 줄 A/B (표본 300) — 미적용 `exact=44 (14.7%) len불일치=183 (61.0%)` vs 적용 `exact=272 (90.7%) len불일치=13 (4.3%)`. 수정 후 `eval_reader.py` 전량 재실행 `hold-out total=2138 exact=2034 (95.1%)`. 누수 없는 캐시 holdout 재채점 `1042/1122 = 92.9%`, 길이 불일치 `33 (2.9%)`, 학습셋 `583/600 = 97.2%`. `assets_dev/train/claude_consult_ocr_response.md`
- Confidence: 5/5

### Error
`assets_dev/train/eval_reader.py` 가 GT 대비 완전일치 **11.7~14.9%**, 길이 불일치 **61%** 를 계속 보고했다. 이 숫자가 "CTC 가 숫자를 못 읽는다"는 문제 정의의 근거가 되어 `claude_consult_ocr.md` 의 가설 H1~H4(워프 압착·합성 도메인 불일치·쓰레기 rect·렌더러 부족)가 전부 그 위에 세워졌다.

### Environment Context
- Packages: TensorFlow 2.x (conda env `sugartrain`, py3.10), Pillow, OpenCV
- Migration Issue: No

### Fix Code
```python
# assets_dev/train/eval_reader.py
from PIL import Image, ImageOps
...
with Image.open(p) as pil:
    pil.load()
    # 좌표 정본은 표시(EXIF 적용) 이미지다. gmscreen_quads.jsonl 은
    # cv2.imread(EXIF 적용)로 만들어진 표시 좌표계인데 PIL 은 EXIF 를 무시한다.
    pil = ImageOps.exif_transpose(pil)
    img = cv2.cvtColor(np.asarray(pil.convert("RGB")), cv2.COLOR_RGB2GRAY)
```

### Analysis
- Root cause: G20(2026-09-02)이 EXIF 좌표계를 `build_cache_v2.py`·`detect_datumo_gm.py`·`golden_bench.dart` **세 곳**에서 통일했으나 `eval_reader.py` 는 그 목록에 없었다. **학습 입력은 고쳐지고 채점만 옛 좌표계에 남았다.**
- Why it failed: Datumo 원본의 83.5%가 orientation=6 이라, 평가 표본 다섯 중 넷이 "옆으로 누운 이미지에 똑바른 좌표를 물린" 크롭으로 채점됐다. 누운 화면에서는 숫자가 세로로 서므로 CTC 의 시간축(가로) 분할이 성립하지 않는다 — 그래서 증상이 "길이 붕괴 61%" 라는 **그럴듯한 모델 실패 모양**으로 나타났다. 이 그럴듯함이 계측을 의심 대상에서 빼놓았다.
- How it was fixed: `exif_transpose` 한 줄. **모델·워프 기하·학습 코드는 0줄 수정, 재학습 없음.** 기존 체크포인트(2026-09-03 23:21) 그대로 92.9%.
- 누수 점검: train/holdout id 겹침 0건. holdout 중 id 이웃(±1)이 train 에 있는 장 874/1122 이지만 **그중 GT 까지 같은 장은 6건** — 연속 id 가 같은 화면의 연사가 아니므로 근접 중복 누수는 무시할 수준. ft 는 합성만 학습한 `pre_best`(08-31)에서 시작하므로 실사진 누수 경로도 없다.
- 남은 진짜 오류 104건의 성격: `98`→`92`, `115`→`119` 같은 **한 글자 오독이 위험군**(값이 그럴듯해 범위 검증기·프레임 합의가 못 잡는다). `119`→`9` 같은 자릿수 붕괴는 범위 밖으로 걸러져 상대적으로 안전.

## Case 2: 2026-09-02 Case 2 의 "수정"이 no-op 이었다 — blank(10)를 NUM_CLASSES(11)와 비교

### Grounding
- Git Context: `hash:b015830` (원 사건 `hash:b2e10ab`, [[2026-09-02#case-2]])
- Evidence: 같은 모델·같은 캐시 holdout 을 두 방식으로 채점 — 올바른 GT `1042/1122 = 92.9%` vs 스크립트의 GT 조립 `837/1122 = 74.6%`. 격차 **18.3pp**
- Confidence: 5/5

### Error
`ctc_reader_v2.py` 가 GT 문자열을 만들 때 패딩을 걸러내지 못해 2자리 라벨 `97` 이 `9710` 이 된다. 2자리 표본(전체의 20%)이 **전부 오답으로 집계**됐다.

```python
gt_strs = ["".join(str(int(v)) for v in row if int(v) != NUM_CLASSES)  # 11
           for row in y_rh]
```

### Environment Context
- Packages: 동일
- Migration Issue: No

### Fix Code
```python
# 패딩은 blank(=NUM_CLASSES-1=10)다. NUM_CLASSES(11)와 비교하면 걸러지지 않는다.
gt_strs = ["".join(str(int(v)) for v in row if int(v) != NUM_CLASSES - 1)
           for row in y_rh]
```

### Analysis
- Root cause: `BLANK = NUM_CLASSES - 1 = 10` 인데 `NUM_CLASSES`(11)와 비교했다. 라벨 배열에 11 은 존재하지 않으므로 **필터가 아무것도 거르지 않는 항등식**이 된다.
- Why it failed: **2026-09-02 Case 2 가 이 버그를 이미 발견하고 "Fix Code" 로 `!= NUM_CLASSES` 를 적으면서 "이미 반영돼 다음 실행부터 자동 정상"이라고 기록했다.** 그 수정 자체가 틀렸는데 재실행으로 확인하지 않아, 사고 기록이 **거짓 안전 신호**로 3일간 남았다. 당시 분석 스크립트는 `labels.jsonl` 을 우회 GT 로 써서 이 no-op 을 우회했고, 그래서 아무도 안 걸렸다.
- How it was fixed: 상수를 `NUM_CLASSES - 1` 로. 같은 파일의 학습셋 참고 채점(320행)도 동일 수정.
- Impact: Case 1 의 EXIF 버그와 **겹쳐서** "학습셋조차 16.1%(암기가 안 된다)" 라는 관측을 만들었고, 그것이 `claude_consult_ocr.md` H1 의 근거 ③("입력 표상 자체가 열화됐다")이 됐다. 실제로는 암기가 아니라 채점이 안 되고 있었다.

## Case 3 (verification): 가설 4개가 계측 버그 위에 서 있었다 — 전제를 재는 데 30분, 가설을 세우는 데 하루

### Grounding
- Git Context: `hash:b015830`
- Artifact: `assets_dev/train/claude_consult_ocr.md`(가설 문서, 무효) · `assets_dev/train/claude_consult_ocr_response.md`(검토 응답) · `assets_dev/train/diag_timestep.py`(진단 도구)
- Confidence: 5/5

### Hypothesis
`claude_consult_ocr.md` 의 H1: "GM 박스(종횡비 ≈0.83)를 320×160(2:1)으로 무조건 늘리는 워프가 세로를 2.4× 압착해 CTC 의 글자 경계를 무너뜨린다. 그래서 길이 붕괴 61%, 완전일치 11.7%."

### Results
| 검증 항목 | 결과 |
|---|---|
| 종횡비 ≈0.83 주장 | **사실** — 실측 중앙값 0.783 · 평균 0.816 (n=2,494) |
| 예측 자릿수 쏠림 | **사실** — GT 는 3자리 79.5%인데 예측은 3자리 33% |
| **"그래서 정확도가 11.7%다"** | **거짓** — 계측 버그 둘(Case 1·2). 같은 모델이 92.9% |
| 길이 붕괴 61% | **거짓** — 올바른 계측으로 2.9% |
| letterbox 처방의 기대효과 | 검증 불필요 — 고칠 문제가 없다. 게다가 letterbox 는 캔버스의 59%를 여백으로 버린다(직접 계산) |

### Analysis
- Confirmed/Refuted: **H1·H2 기각**(원인 아님). H3(쓰레기 rect)는 축소된 형태로 생존 — 타임스텝 진단에서 `GT='119' pred='9'` 인 장이 40칸 중 39칸 blank 로, 형태가 애매한 게 아니라 **그 장에서 모델이 아무것도 못 본** 패턴이다. 다만 규모가 전체의 8~13% 가 아니라 오류 104건 안의 일부.
- Key metrics: 92.9%(캐시 holdout, 누수 없음) · 97.2%(학습셋) · 과적합 격차 4.3pp · 길이 불일치 2.9%
- **내가 먼저 틀린 방식**: 첫 답변에서 나는 H1 을 "근거 있음"으로 판정하고 띠 크롭을 권했다. 종횡비도 자릿수 쏠림도 직접 재서 확인했는데, **그 사실들과 "그래서 정확도가 낮다" 사이의 연결만 재지 않았다.** 개별 사실을 검증하는 것과 인과 사슬을 검증하는 것은 다르다 — 전자를 여러 개 하면 후자를 한 것 같은 착각이 생긴다.
- 무엇이 실제로 끊었나: 재현하려고 `reader_preds.json` 을 읽다가 **id 가 캐시와 안 맞아서**(`KeyError`) 평가 경로를 열어 본 것. 가설을 더 잘 세워서가 아니라 **데이터를 직접 만지다 걸린 불일치**가 끊었다.
- Implications: 계측 경로(채점 스크립트·전처리 로더)는 **가설 공간 밖에 두면 안 된다.** "모델이 나쁘다"는 결론에 도달하기 전에 계측이 옳은지를 한 번 재는 비용은 이번 경우 30분이었고, 그 30분을 안 낸 대가는 하루치 가설 문서와 폐기될 실험 계획이었다.
- Action taken: 두 계측 버그 수정(재학습 0), `diag_timestep.py` 추가(재학습 없이 holdout 채점 + 길이 붕괴 표본의 타임스텝 40칸 argmax 출력), `claude_consult_ocr.md` 는 **폐기하지 않고 "계측 버그로 무효" 표시하여 보존**.
