## Case 1: 평가 스크립트만 EXIF 무처리 — CTC 리더 11.7%는 모델이 아니라 계측이었다 (실제 92.9%)

### Grounding
- Git Context: `hash:b015830`
- Evidence: 동일 모델·동일 이미지·동일 워프에서 `ImageOps.exif_transpose` 한 줄 A/B (표본 300) — 미적용 `exact=44 (14.7%) len불일치=183 (61.0%)` vs 적용 `exact=272 (90.7%) len불일치=13 (4.3%)`. 수정 후 `eval_reader.py` 전량 재실행 `hold-out total=2138 exact=2034 (95.1%)`. 누수 없는 캐시 holdout 재채점 `1042/1122 = 92.9%`, 길이 불일치 `33 (2.9%)`, 학습셋 `583/600 = 97.2%`. `assets_dev/train/claude_consult_ocr_response.md`
- Confidence: 5/5

### Error
`assets_dev/train/eval_reader.py` 가 GT 대비 완전일치 **11.7~14.9%**, 길이 불일치 **61%** 를 계속 보고했다. 이 숫자가 "CTC 가 숫자를 못 읽는다"는 문제 정의의 근거가 되어 `claude_consult_ocr.md` 의 가설 H1~H4(워프 압착·합성 도메인 불일치·쓰레기 rect·렌더러 부족)가 전부 그 위에 세워졌다.

### Environment Context
- Packages: TensorFlow 2.x (conda env `sugartrain`, py3.10), Pillow, OpenCV
- Migration Issue: No

### Fix Code
```python
# assets_dev/train/eval_reader.py
from PIL import Image, ImageOps
...
with Image.open(p) as pil:
    pil.load()
    # 좌표 정본은 표시(EXIF 적용) 이미지다. gmscreen_quads.jsonl 은
    # cv2.imread(EXIF 적용)로 만들어진 표시 좌표계인데 PIL 은 EXIF 를 무시한다.
    pil = ImageOps.exif_transpose(pil)
    img = cv2.cvtColor(np.asarray(pil.convert("RGB")), cv2.COLOR_RGB2GRAY)
```

### Analysis
- Root cause: G20(2026-09-02)이 EXIF 좌표계를 `build_cache_v2.py`·`detect_datumo_gm.py`·`golden_bench.dart` **세 곳**에서 통일했으나 `eval_reader.py` 는 그 목록에 없었다. **학습 입력은 고쳐지고 채점만 옛 좌표계에 남았다.**
- Why it failed: Datumo 원본의 83.5%가 orientation=6 이라, 평가 표본 다섯 중 넷이 "옆으로 누운 이미지에 똑바른 좌표를 물린" 크롭으로 채점됐다. 누운 화면에서는 숫자가 세로로 서므로 CTC 의 시간축(가로) 분할이 성립하지 않는다 — 그래서 증상이 "길이 붕괴 61%" 라는 **그럴듯한 모델 실패 모양**으로 나타났다. 이 그럴듯함이 계측을 의심 대상에서 빼놓았다.
- How it was fixed: `exif_transpose` 한 줄. **모델·워프 기하·학습 코드는 0줄 수정, 재학습 없음.** 기존 체크포인트(2026-09-03 23:21) 그대로 92.9%.
- 누수 점검: train/holdout id 겹침 0건. holdout 중 id 이웃(±1)이 train 에 있는 장 874/1122 이지만 **그중 GT 까지 같은 장은 6건** — 연속 id 가 같은 화면의 연사가 아니므로 근접 중복 누수는 무시할 수준. ft 는 합성만 학습한 `pre_best`(08-31)에서 시작하므로 실사진 누수 경로도 없다.
- 남은 진짜 오류 104건의 성격: `98`→`92`, `115`→`119` 같은 **한 글자 오독이 위험군**(값이 그럴듯해 범위 검증기·프레임 합의가 못 잡는다). `119`→`9` 같은 자릿수 붕괴는 범위 밖으로 걸러져 상대적으로 안전.

## Case 2: 2026-09-02 Case 2 의 "수정"이 no-op 이었다 — blank(10)를 NUM_CLASSES(11)와 비교

### Grounding
- Git Context: `hash:b015830` (원 사건 `hash:b2e10ab`, [[2026-09-02#case-2]])
- Evidence: 같은 모델·같은 캐시 holdout 을 두 방식으로 채점 — 올바른 GT `1042/1122 = 92.9%` vs 스크립트의 GT 조립 `837/1122 = 74.6%`. 격차 **18.3pp**

```python
gt_strs = ["".join(str(int(v)) for v in row if int(v) != NUM_CLASSES)  # 11
           for row in y_rh]
```

### Environment Context
- Packages: 동일
- Migration Issue: No

### Fix Code
```python
# 패딩은 blank(=NUM_CLASSES-1=10)다. NUM_CLASSES(11)와 비교하면 걸러지지 않는다.
gt_strs = ["".join(str(int(v)) for v in row if int(v) != NUM_CLASSES - 1)
           for row in y_rh]
```

### Analysis
- Root cause: `BLANK = NUM_CLASSES - 1 = 10` 인데 `NUM_CLASSES`(11)와 비교했다. 라벨 배열에 11 은 존재하지 않으므로 **필터가 아무것도 거르지 않는 항등식**이 된다.
- Why it failed: **2026-09-02 Case 2 가 이 버그를 이미 발견하고 "Fix Code" 로 `!= NUM_CLASSES` 를 적으면서 "이미 반영돼 다음 실행부터 자동 정상"이라고 기록했다.** 그 수정 자체가 틀렸는데 재실행으로 확인하지 않아, 사고 기록이 **거짓 안전 신호**로 3일간 남았다. 당시 분석 스크립트는 `labels.jsonl` 을 우회 GT 로 써서 이 no-op 을 우회했고, 그래서 아무도 안 걸렸다.
- How it was fixed: 상수를 `NUM_CLASSES - 1` 로. 같은 파일의 학습셋 참고 채점(320행)도 동일 수정.
- Impact: Case 1 의 EXIF 버그와 **겹쳐서** "학습셋조차 16.1%(암기가 안 된다)" 라는 관측을 만들었고, 그것이 `claude_consult_ocr.md` H1 의 근거 ③("입력 표상 자체가 열화됐다")이 됐다. 실제로는 암기가 아니라 채점이 안 되고 있었다.

## Case 3 (verification): 가설 4개가 계측 버그 위에 서 있었다 — 전제를 재는 데 30분, 가설을 세우는 데 하루

### Grounding
- Git Context: `hash:b015830`
- Artifact: `assets_dev/train/claude_consult_ocr.md`(가설 문서, 무효) · `assets_dev/train/claude_consult_ocr_response.md`(검토 응답) · `assets_dev/train/diag_timestep.py`(진단 도구)
- Confidence: 5/5

### Hypothesis
`claude_consult_ocr.md` 의 H1: "GM 박스(종횡비 ≈0.83)를 320×160(2:1)으로 무조건 늘리는 워프가 세로를 2.4× 압착해 CTC 의 글자 경계를 무너뜨린다. 그래서 길이 붕괴 61%, 완전일치 11.7%."

### Results
| 검증 항목 | 결과 |
|---|---|
| 종횡비 ≈0.83 주장 | **사실** — 실측 중앙값 0.783 · 평균 0.816 (n=2,494) |
| 예측 자릿수 쏠림 | **사실** — GT 는 3자리 79.5%인데 예측은 3자리 33% |
| **"그래서 정확도가 11.7%다"** | **거짓** — 계측 버그 둘(Case 1·2). 같은 모델이 92.9% |
| 길이 붕괴 61% | **거짓** — 올바른 계측으로 2.9% |

### Analysis
- Confirmed/Refuted: **H1·H2 기각**(원인 아님). H3(쓰레기 rect)는 축소된 형태로 생존 — 타임스텝 진단에서 `GT='119' pred='9'` 인 장이 40칸 중 39칸 blank 로, 형태가 애매한 게 아니라 **그 장에서 모델이 아무것도 못 본** 패턴이다. 다만 규모가 전체의 8~13% 가 아니라 오류 104건 안의 일부.

- **내가 먼저 틀린 방식**: 첫 답변에서 나는 H1 을 "근거 있음"으로 판정하고 띠 크롭을 권했다. 종횡비도 자릿수 쏠림도 직접 재서 확인했는데, **그 사실들과 "그래서 정확도가 낮다" 사이의 연결만 재지 않았다.** 개별 사실을 검증하는 것과 인과 사슬을 검증하는 것은 다르다 — 전자를 여러 개 하면 후자를 한 것 같은 착각이 생긴다.
- 무엇이 실제로 끊었나: 재현하려고 `reader_preds.json` 을 읽다가 **id 가 캐시와 안 맞아서**(`KeyError`) 평가 경로를 열어 본 것. 가설을 더 잘 세워서가 아니라 **데이터를 직접 만지다 걸린 불일치**가 끊었다.
- Implications: 계측 경로(채점 스크립트·전처리 로더)는 **가설 공간 밖에 두면 안 된다.** "모델이 나쁘다"는 결론에 도달하기 전에 계측이 옳은지를 한 번 재는 비용은 이번 경우 30분이었고, 그 30분을 안 낸 대가는 하루치 가설 문서와 폐기될 실험 계획이었다.
- Action taken: 두 계측 버그 수정(재학습 0), `diag_timestep.py` 추가(재학습 없이 holdout 채점 + 길이 붕괴 표본의 타임스텝 40칸 argmax 출력), `claude_consult_ocr.md` 는 **폐기하지 않고 "계측 버그로 무효" 표시하여 보존**.

## Case 4: CTC 리더가 **보이지 않는 자리를 지어낸다** — 949 에서 사용자가 잡았다

### Grounding
- Git Context: `hash:ca177fd`
- Evidence: `glucose_batch1/949` (GT 91) — GM 박스가 `1` 을 완전히 제외했는데 판독 `'91'` conf **0.993**. 오른쪽 끝 2열 통계: 최소 66·평균 173.5(이미지 중앙값 149, 진짜 숫자 최소 8) = **잉크 없음**. 끝 4/8/32열을 배경색으로 덮어도 `'91'` 유지(conf 0.983/0.971/0.967). 전량 절제: `diag_edge_ablation.py`
- Confidence: 5/5

### Discovery
크롭에 물리적으로 없는 숫자를 모델이 높은 확신으로 만들어낸다. 그리고 **없는 것을 보고하지 않는다** — 오른쪽 48열(가로의 15%)을 통째로 덮으면 세 번째 자리가 사라진 상태인데 **316장이 "마지막 자리만 틀림"** 으로 나온다. 두 자리로 짧게 답하는 게 아니라 자리를 만들어 채운다.

절제 곡선(holdout 1,122): 가림 0열 92.9% · 4열 92.3% · **8열 93.0%** · 16열 65.8% · 32열 78.6% · 48열 56.7% · 64열 29.9%. **끝 8열은 정보가 0** 이다(지워도 오히려 미세 상승).

### Analysis
- Why non-obvious: 정확도 92.9% 라는 집계는 이 행동을 숨긴다. 949 는 **지어낸 값이 우연히 맞아서 '정답'으로 집계**됐다. 사용자가 "박스에 9만 들어있는데 91이 나온다"고 짚지 않았으면 안 나왔다.
- 함께 성립하는 증거: holdout **전부(1042 정답 + 80 오답)** 가 마지막 글자를 40칸 중 t=38~39 에서 낸다. 다만 **BiLSTM 이라 타임스텝은 공간 위치가 아니다** — 처음에 "가장자리 조각을 읽었다"고 해석했으나 절제로 반증됐다(끝을 지워도 답이 같다). 위치가 아니라 **출력 습관**이다.
- Impact: **92.9% 는 실제 판독력을 과대평가한다.** 크롭이 조금이라도 잘리면 조용히 그럴듯한 값을 낸다 — 이 앱에서 가장 위험한 실패 모드다. 가로 화면 판독 14.3%(Case 6)가 "못 읽는다"가 아니라 "틀린 값을 자신 있게 낸다"인 이유.
- Action taken: `diag_edge_ablation.py` 추가. 임계값(G24)으로는 못 거른다 — 습관에 대한 확신이라 확신도가 높다.

## Case 5: 첫 자리 오독의 5/7 이 `1` — 학습 분포가 모델의 답을 정한다

### Grounding
- Git Context: `hash:ca177fd`
- Evidence: 자릿수 보존 오독 43건 중 첫 자리가 틀린 7건 → `1` 로 읽음 5건. 가장 확신 높은 오독 둘이 `444→144`(conf 0.996)·`219→119`(0.997). 학습·평가 3자리 첫 자리 분포 **`1`:802 `2`:75 `3`:17 `4`:3**
- Confidence: 5/5

### Discovery
모델이 픽셀이 아니라 **사전분포를 주장**한다. 그리고 방향이 **높은 값 → 정상 값**이다. `444`(중증 고혈당)를 `144`(정상)로, `219`를 `119`로.

자리별 정확도로도 같은 그림이 나온다 — 1번째 99.54%(엔트로피 0.58bit, 무조건 `1` 이라 찍어도 90%) · 2번째 99.31%(3.03bit) · 3번째 97.01%(3.31bit). **첫 자리 성적은 실력이 아니라 사전분포다.**

### Analysis
- Why non-obvious: 첫 자리 정확도가 가장 높아 보여서 "앞자리는 잘 읽는다"로 오해하기 쉽다. 엔트로피를 같이 봐야 드러난다.
- Impact: **모델이 가장 못 읽는 곳이 임상적으로 가장 중요한 곳이다.** 학습 데이터가 정상 범위(100~199) 위주라, 비정상 값일수록 사전분포가 정답을 이긴다. 확신도 임계값으로 못 거른다(G24: τ=0.99 에서 생존한 2건이 정확히 이 둘).
- Action taken: 기록만. 처방(첫 자리 분포 균형·클래스 가중치)은 사람 결정.

## Case 6: 가로 LCD — 검출·판독 양쪽의 사각지대

### Grounding
- Git Context: `hash:ca177fd`
- Evidence: 사용자 관찰("좌우가 긴 LCD 는 전혀 탐지 못한다")에서 출발. GM 검출 박스 중 w/h>1.5 는 **1.24%(31/2494)** 인데 사람 라벨은 **11.9%(35/294)**. 판독 정확도 w/h>1.5 **14.3%**(14장 중 12장 오답) · 1.1~1.5 62.5% · <1.1 94~95%. GM score 0.5~0.7 37.5% · >0.95 96.4%. 원본 해상도 눈검(`_diag/audit_wide/1593.png`): GM 박스가 큰 숫자 `100` 을 잘라내고 시간줄 블록을 담는다
- Confidence: 5/5

### Discovery
가로 화면에서 GM 은 화면을 못 찾거나(1046 score 0.35), 찾아도 **세로로 좁혀** 잡거나(1091: 사람 3.50 → GM 1.38), **엉뚱한 영역**(시간줄)을 잡는다. 미검출 18장 중 4장이 극단 가로(3.94·3.44·2.53·2.13).

**직관적인 처방은 틀렸다**: 사람이 그린 유리 전체 박스로 읽히면 가로 화면 **9.7%** 로 GM 박스(51.6%)보다 나쁘다. 3.5:1 화면을 2:1 캔버스에 넣으면 숫자가 폭의 일부만 차지한다. (교란: 리더가 GM 박스로 학습돼 사람 박스는 분포 밖)

### Analysis
- Why non-obvious: 전체 평균 92.9% 가 이 층을 완전히 가린다. 사람 라벨 vs GM 박스 전체 비교는 **+1.6pp(노이즈)** 였는데, 종횡비로 층화하니 **-41.9pp** 가 나왔다. 층화하지 않으면 42pp 효과가 1.6pp 로 뭉개진다.
- Impact: 학습셋에서 가로 화면은 약 4%(사람 라벨 55장/전체 1,570장). 실패 클래스가 학습에 거의 없다 — Case 5 의 첫 자리 편향과 **같은 모양의 클래스 불균형**.
- Action taken: `make_lcd_fix_queue.py` — 실측 기준(w/h>1.1 또는 score<0.85)으로 후보 165장을 뽑아 라벨링 큐 116 / **테스트 holdout 49** 로 층화 분할. holdout 은 큐에서 빼고 라벨러가 빨간 경고를 띄운다(전체 큐로 도달 가능하므로).

## Case 7: 416 입력의 박스 정밀도 한계 — "왜 박스가 숫자를 살짝 자르나"의 답

### Grounding
- Git Context: `hash:ca177fd`
- Evidence: `D:\tmp\YOLOX\gmscreen_ft2_exp.py` `input_size=(416,416)`. 원본 3024×4032. 어노테이션 정합 전수 검증(1,230장): cv2 기준 불일치 **0**, PIL 기준 불일치 **199**. `yolox/data/datasets/coco.py:148` 이 `cv2.imread`, `:116` 이 `r = min(...)` 로 이미지와 박스를 **같은 계수로** 축소(종횡비 보존)
- Confidence: 5/5

### Discovery
스케일링 **버그는 없다**(박스가 이미지와 같이 줄어들고 종횡비도 보존된다). 그러나 **정밀도 한계**가 있다: 3024→416 은 약 7.3배 축소라 **416 에서 1픽셀 = 원본 7.3픽셀**. 7-세그먼트 획 두께가 원본 30~60픽셀이므로 검출기는 **획 두께의 1/4~1/2 만큼** 경계를 어긋나게 놓을 수 있다. 숫자를 살짝 걸치며 자르는 현상의 물리적 하한이다.

동시에 **깨지기 쉬운 정합**을 발견했다: `build_gmft_dataset.py` 가 원본 파일을 `shutil.copy2` 로 **EXIF 미적용 상태 그대로 복사**하면서 어노테이션의 `width/height` 와 bbox 는 **표시 좌표계**로 적는다. 지금 맞는 이유는 오직 YOLOX 가 `cv2.imread`(EXIF 적용)를 쓰기 때문이다. 그 체인이 PIL 로 바뀌면 **1,230장 중 199장이 조용히 깨진다.**

### Analysis
- Why non-obvious: 사용자 질문("학습도 스케일링하는데 같은 문제가 있지 않을까")에서 출발했다. 버그를 찾으러 갔다가 버그는 없고 **물리적 한계**와 **잠복한 취약점**을 찾았다.
- Impact: 박스가 숫자를 살짝 자르는 것을 라벨·모델 품질 문제로 오해하고 쫓을 수 있다. 그 하한을 넘으려면 입력 해상도를 올려야 한다(비용은 추론 시간).
- Action taken: 기록만. 해상도 상향은 사람 결정.

## Case 8: 축소본으로 판단해 한 세션에 세 번 틀렸다

### Grounding
- Git Context: `hash:ca177fd`
- Evidence: (a) 620px 렌더로 `glucose_batch1/266` 을 "똑바로 서 있다" 판정 → 원본에서는 반시계 10~15° 기울어짐. (b) 같은 렌더로 "GM 박스가 `1` 을 자른다" 판정 → 원본 확대(`_diag/case266/right_edge_zoom.png`)에서 박스 경계가 `1` 의 **바깥**을 지난다. (c) 오독 43장 몽타주 8칸을 보고 "마지막 자리가 잘려서 틀린다" 가설 → 정량 반증 2회(끝 8열 잉크비율 오독 0.338 vs 정답 0.408; 끝 2열 획 연결 83.7% vs 79.1%)
- Confidence: 5/5

### Discovery
세 번 모두 **표본이나 해상도가 결론을 지탱하지 못하는데 단정**했다. (a)(b)는 축소본이라 몇 픽셀 차이가 안 보였고, (c)는 실패 사례만 보고 대조군을 안 봤다.

사용자가 (b)를 반박하며 던진 질문이 정확했다 — **"원본에서 안 잘린 숫자가 축소본에서 잘린다는 게 말이 되냐, 크롭박스는 스케일링 안 했냐"**. 스케일링 버그는 없었지만(박스를 원본에 그린 뒤 축소), 그 의심에서 출발한 감사가 Case 7 을 찾아냈다.

### Analysis
- Why non-obvious: 축소본은 **틀렸다는 신호를 주지 않는다.** 그냥 작을 뿐이라 판단이 가능해 보인다. 실패 사례만 모아 보는 것도 마찬가지로 — 공통 성질이 전부 원인처럼 보인다.
- Impact: (a)(b)는 사용자에게 잘못된 라벨링 지침을 줄 뻔했다. (c)는 하마터면 크롭 기하를 뜯는 작업으로 이어질 뻔했다.
- Action taken: 이미지 판단은 **원본 해상도로 확대해서**, 원인 주장은 **대조군과 함께**. Case 6 의 층화(+1.6pp → -41.9pp)도 같은 교훈의 정량판이다.

## Case 9: 가로 LCD 전수 조사 — 11%가 아니라 2.0%, 그리고 적합 실패

### Grounding
- Git Context: `hash:ca177fd` · GM ft3 `yolox_out/gmscreen_ft3/best_ckpt.pth`
- Evidence: 사용자가 2,512장 전수를 대지(`_diag/wide_all/`, 63장)로 눈검해 **51장**을 가로 LCD 로 표시(`wide_ids.json`). 무작위 200장 표본 사전 추정은 4장 = 2.0% [0.8~5.0] 로 전수와 일치. GM ft3 학습 여부 대조: `gmscreen_ft/annotations/instances_train2017.json`
- Confidence: 5/5

### Discovery
**세 가지가 한꺼번에 뒤집혔다.**

1. **비중이 2.0%(51/2512)다.** 앞서 근거로 삼은 11%는 라벨된 410장에서 나온 값인데, 그 410장은 **GM 실패 사례를 골라 라벨링한 것**이라 가로가 과대 표집돼 있었다. 실패를 모아 놓고 "가로가 11%나 된다"고 센 셈이다.

2. **비율 비교로는 GM 이 멀쩡해 보였다.** GM ft3 는 w/h>1.2 를 46장(1.8%) 내놓고 실제는 51장(2.0%)이라 거의 같다. 그런데 **목록으로 대조하니** 정밀도 67% · 재현율 61% — 오탐 15장과 미검출·접힘 20장이 **우연히 상쇄**돼 총량만 맞았던 것이다. 비율만 보면 영영 안 보인다.

3. **화면이 가로로 보이는 45장 중 GM 실패 16장, 그중 14장(88%)이 학습 데이터다.** `607`(사람 3.94)은 학습하고도 미검출, `1622`(2.05)는 학습하고도 0.77 로 접는다. 일반화가 아니라 **적합** 실패다.

부수 확인: 51장 중 사진이 회전돼 화면이 세로로 보이는 것은 **2장뿐**(번호 619·620 = `1564`·`1565`, 사람 라벨 0.37·0.38). 회전은 이 문제의 주 요인이 아니다.

### Analysis
- Why non-obvious: 층화까지는 옳게 했는데(가로에서 42pp 격차는 실측) **층의 크기를 곱하지 않았다.** 2%짜리 층을 38.6%에서 96.5%로 완벽히 고쳐도 전체 기여는 **+1.17pp** 다. "큰 격차"와 "큰 영향"은 다르다.
- Impact: 오버샘플링·추가 라벨링 계획이 **무효**다. 학습한 장을 못 맞히는 모델에게 같은 장을 더 자주 보여줄 이유가 없다. 남은 가설은 구조·해상도(416 에서 3.94:1 화면은 두께 40px 미만) 쪽이고, 그것도 상한이 +1.17pp 다.
- Action taken: `make_wide_survey.py`(표본·전수 대지) · `tally_wide_survey.py`(집계·신뢰구간) 추가. `DONE.md` 와 위키의 "11% · 사각지대" 서술 정정.
- **표기 실수로 한 번 혼선**: 보고서에 이미지 id(`glucose_batch1/1564`)를 썼는데 사용자는 시트 번호로 읽었다(번호 1564 는 다른 장이다). 번호 체계가 둘이면 **항상 둘 다 적어야 한다**.

## Case 10 (verification): 여유 + 흔들기 — 지어내기가 실제로 줄었다

### Grounding
- Git Context: `hash:77e5e82` (캐시 `BOX_MARGIN=0.10`, ft 증강 zoom 0.18 · translate 0.08)
- Evidence: 캐시 holdout 1,122장 재채점. 절제는 `diag_edge_ablation.py`, 동등조건 보정본은 여백폭 27px 을 더해 비교
- Confidence: 5/5

### Hypothesis
검출 박스의 오른쪽 오차가 넓게 퍼져 있고(p5 −6% ~ p95 +28%, σ 0.096 > 평균 0.072)
리더는 한 가지 프레이밍만 학습했다. 그래서 잘린 크롭이 오면 읽지 못하고 지어낸다.
→ **캐시에 여유를 주고 학습 증강이 그 안에서 프레이밍을 흔들면** 리더가 빡빡한
크롭과 헐거운 크롭 양쪽에 둔감해질 것이다.

### Results
| 지표 | 기준선 | 여유+흔들기 |
|---|---|---|
| 완전일치 | 92.87% | **94.83%** |
| **위험군(자릿수 보존 오독)** | **43 (3.83%)** | **18 (1.60%)** |
| 마지막 자리만 틀림 | 34 | **13** |
| 첫 자리를 `1` 로 읽음 | 7건 중 5건 | **2건 중 0건** |
| 고확신 위험군(≥0.99) | `444→144`(.996) · `219→119`(.997) | `155→159`(.991) 1건 |
| 확신도 중앙(정답/위험군) | 0.991 / 0.601 | 0.986 / **0.690** |
| 학습셋 참고 | 97.2% | 97.5% (격차 4.3 → 2.7pp) |

오류의 **성격이 옮겨갔다**: 위험 43→18, 안전(붕괴·blank) 37→40, 전체 80→58.
지어내는 대신 자릿수를 무너뜨린다 — 범위 검증기에 걸리는 실패다.

개별 확인(`949`, GT 91): 옛 모델은 박스 밖 `1` 을 0.993 으로 지어냈고 끝 32열을
덮어도 `'91'` 을 유지했다. 새 모델은 `'91'`(여유 덕에 `1` 이 크롭 안), **끝 32열을
덮으면 `'9'`** — 안 보이면 내지 않는다. `1196`(GT 104)도 같은 형태.

### Analysis
- Confirmed: 처방이 표적(마지막 자리·지어내기)을 직접 맞혔고, 부수적으로 첫 자리
  사전분포 편향(Case 5)까지 사라졌다. 프레이밍이 고정돼 있을 때 모델이 위치
  습관에 기대던 것이 원인이었다는 해석과 일관된다.
- **절제 곡선 비교에는 교란이 있다**: 여유 10% 때문에 같은 열 수를 가려도 지워지는
  화면 내용이 적다. 여백폭(27px)을 더해 동등조건으로 재보정하면 48열 기준
  56.7%/316건 → 37.7%/184건. **정확도가 더 떨어지는 것이 좋은 신호다** — 옛 모델의
  56.7% 는 안 보이는 것을 사전분포로 채워 얻은 점수였다.
- 실패했던 처방과의 대비: 추론 시 고정 패딩(+8% 오른쪽)은 마지막 자리 오류를
  34→23 으로 줄였지만 전체는 −0.62pp 순손실이었다. 편차가 평균보다 큰 분포에
  단일 값을 적용했기 때문이다. **분포를 보고 처방을 바꾼 것이 차이를 만들었다.**
- 남은 것: 위험군 1.60% 는 승격 게이트(≤0.2%)보다 여전히 8배 높다. τ=0.99 에서
  0.09% 로 내려가지만 미인식 55.7% 를 지불한다.
