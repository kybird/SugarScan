## Case 1: SPEC 을 하루 열었다가 같은 날 닫았다 — 임시 허용은 되돌림을 예고하고 시작한다

### Grounding
- Git Context: `hash:3d96c52`
- Evidence: `docs/SPEC.md` §5.3, `docs/BAND_EXP_PLAN.md` §25
- Confidence: 5/5

### Design Decision

7번 실험이 "특징맵 해상도가 병목"이라는 근거를 냈고 사람이 "스펙풀어서 다시
재보자"로 SPEC §5.3 의 stride /8 금지를 풀었다. 허용 문구에 **"채택 여부는
실험 8번이 정하며 기각되면 이 항목도 되돌린다"**를 못박고 사전 등록과 함께
**결과가 나오기 전에** 커밋했다(3d96c52). 결과가 기각이므로 같은 날 되돌렸다.

### Alternatives Considered
- 허용을 열어 두고 결과를 지켜본 뒤 판단 — 안 한다. "일단 열어 둔 문"은
  닫는 행위가 별도 결정이 되어야 해서 사실상 안 닫힌다.
- 코드에서 /8 을 아예 제거해 원천 차단 — 안 한다. 기각의 재현성이 필요하다.
  `--stride 8` 은 재현용으로 남기고 help 에 "SPEC 밖"이라고 적었다.

### Decision Code
```
SPEC §5.3: "채택 여부는 실험 8번(같은 문서 §25)이 정하며, 기각되면 이
항목도 되돌린다."  ->  결과 후: "허용했다가 같은 날 되돌렸다 (2026-09-21)"
```

### Analysis
- Context: CLAUDE.md 원칙 "조건부 허용 플래그를 만들지 말 것 — 플래그가
  있으면 언젠가 켜진다"가 설계 규칙 쪽에도 성립한다.
- **Trade-offs**: 임시 허용의 행정 비용(되돌림 커밋) vs 상시화 리스크.
  되돌림 커밋이 쌌다.
- Reversibility: High — 결정 기록 자체가 되돌림 절차를 담고 있었다.

## Case 2: "특징맵을 키워라"가 아니라 "입력을 키워라"였다 — 격자와 화소를 가른 3팔 비교

### Grounding
- Git Context: `hash:1e2146f`
- Artifact: `_diag/fix8/` (astride8 4시드), `report_cell_strata.py`
- Confidence: 5/5

### Hypothesis

7번(§24) 해석: 832 가 준 것은 52x52 특징맵이므로 같은 격자를 416 +
stride /8 로 얻으면 훨씬 싸게 같은 이득을 얻는다.

### Results

```
팔         입력 화소   격자      노린 층(2.5칸 미만) 게이트
asize512   512²        32x32     31.0
astride8   416²        52x52     31.0    <- 격자 2.7배, 화소 0.66배
abig       832²        52x52     62.2    <- 격자 같음,   화소 4배
```

격자를 촘촘히 해도(입력을 함께 줄이면) 노린 층이 전혀 안 움직이고(31.0 ->
31.0), 같은 격자에서 화소만 4배 올리면 62.2 다. 전체 게이트도 astride8
58.0% 로 abig 71.3% 에 전 층에서 못 미쳤다. 기각.

### Analysis
- Confirmed/Refuted: **가설 반박.** 병목은 격자 해상도가 아니라 **입력 화소
  (잉크의 정보량)** 이다. 416 으로 줄인 작은 밴드는 셀이 부족했던 게 아니라
  화소가 부족했다.
- Key metrics: 개발 586 게이트 -0.70pt [-4.27, +2.35](무개선) · 담음 -3.12pt
  [-5.46, -0.77](유의 하락) · 미검출 0.94%(abig 의 2.5배 대가는 안 옴).
- Implications: 작은 밴드를 올리는 확인된 지렛대는 입력 크기 하나뿐이고 그
  대가는 MACs 4배(110.5G)다 — 제품(단말 비용) 판단으로 사람에게 넘어갔다.
  부수 교훈: "격자가 같으면 4배 싸다"(§24.6)도 재보니 절약은 25%였다
  (83.2G/110.5G, count_macs.py) — /8 헤드가 백본 절약을 도로 먹는다.
  **구성 요소의 저렴함을 더해 총 비용을 말하지 않는다.**

## Case 4: 파일명에 공백이 있는 사진만 캔버스가 검게 나왔다

### Grounding
- Git Context: `hash:fe8ec80`
- Evidence: `webtool.py` /cache/ 라우트, 사람 보고 "와츠앱이미지는 검은색으로나와"
- Confidence: 5/5

### Error

사람 보고: livecmp 화면에서 Roboflow 의 "WhatsApp Image 2024-12-09 ..." 사진
123장만 캔버스가 검은색으로 뜬다. 서버 쪽 표시본 캐시는 정상이었다(휘도
평균 123 — 밝은 사진).

```
GET /cache/rf__train__WhatsApp%20Image%20..._640.jpg  ->  404
```

### Environment Context
- Packages: 표준 라이브러리 http.server
- Migration Issue: No

### Fix Code
```python
# 전: p = CACHE / Path(u.path).name          # %20 을 그대로 파일명으로 쓴다
# 후:
from urllib.parse import urlparse, parse_qs, unquote
p = CACHE / Path(unquote(u.path)).name
```

### Analysis
- Root cause: 브라우저는 파일명의 공백을 %20 으로 인코딩해 보낸다. 서버는
  그걸 디코딩하지 않고 경로 성분으로 썼다. 파일명에 공백이 있는 사진
  (WhatsApp 123장)만 404 — 이미지 로드가 실패하고 캔버스는 배경색(#000)
  그대로였다. **추론과 좌표는 전부 정상**이었다 — 깨진 것은 표시뿐.
- Why it failed: 코퍼스의 다른 파일명(IMG20241209...·glucose_batch1/1)에는
  공백이 없다. 공백이 있는 파일명이 들어온 날부터 숨어 있었고, 그 사진을
  큰 화면으로 보게 된 2026-09-21 에서야 사람 눈에 걸렸다. /arms 화면도
  같은 /api/image + meta.url 경로를 써서 WhatsApp 장은 줄곧 안 보였을
  것이다 — 성적표(jsonl 집계)에는 영향 없는 표시 결함이었다.
- How it was fixed: /cache/ 라우트에서 unquote. 프론트는 onerror 를 붙여
  로드 실패 시 검은 캔버스 대신 실패 문구를 내게 했다 — 실패가 침묵하지
  않게.
