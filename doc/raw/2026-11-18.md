## Case 1: GEN9 — 코드화면 학습 제거가 정답률을 복귀시키고 오답을 최저로

### Grounding
- Git Context: `hash:b2a1ace+`
- Artifact: docs/reports/dc238-judge-2026-11-16.md "GEN9" 절 ·
  band_out/ps9_det_neg25.pt · reader_out/ps9_rdr_neg/best.pt
- Confidence: 5/5

### Hypothesis
사람 가설(2026-11-18): "학습할수록 정답이 떨어지는 건 제품 이후 학습에
Code 화면이 들어갔기 때문" — GEN6~GEN8 의 정답 폭락(35~55%)은 코드화면
음성 프레임 탓이다. GEN9 = GEN5 설정 그대로(코드화면·원경 없음)로 굽고
검출기+리더 100에폭 체인을 돌려 확인.

### Results
DC238 (n=207 값 + 31 함정), 자 `eval_real_judge.py`:

| 세대 | 정답 확정 | 오답 확정 | 함정통과 |
|---|---|---|---|
| 제품 번들 | 68.1% | 13.6% | 68% |
| GEN5 | 62.8% | 15.9% | 58% |
| GEN6(+코드) | 35.3% | 20.8% | 12.9% |
| GEN7(코드 각도제한) | 54.6% | 14.5% | 35.5% |
| GEN8(+원경) | 39.6% | 11.6% | 16.1% |
| **GEN9(코드 제거)** | **60.4%** | **10.6%** | **58.1%** |

- 검출기 음성 오검출 크롭 724개 — GEN8(2297)의 1/3. obj- 0.0026.
- 리더 학습셋 완전일치 100.00% (n=4723). 총 체인 2925초.

### Analysis
- Confirmed: 코드화면 학습이 정답률 폭락의 원인이었다. GEN9 는 정답
  GEN5 수준 복귀 + 오답 전 세대 최저(제품보다 낮음)를 동시에 얻었다.
- Implications: 목표 "오답≤5% 안에서 정답 최대"에서 오답 축이 처음으로
  제품 아래로. 코드화면 방어는 검출기/리더 학습이 아니라 3층
  (값검증 → 유리 영역 단위 유무 게이트 → 사용자 확인)이 맡는다 —
  화면유형 분류기는 검출기와 별개의 작은 판정기로만.
- 코드화면을 음성으로 넣으면 검출기의 음성 혼동 자체가 커진다(오검출
  크롭 3배) — "거절 축을 하나 넣을 때마다 양성이 희생된다"는 GEN6~8 의
  패턴이 검출기 크롭 질에서도 재확인.

## Case 2: 리더 에폭 17.7초의 진짜 범인 — 매-접근 imread 와 매-에폭 로더 재생성

### Grounding
- Git Context: `hash:b2a1ace+`
- Evidence: reader_crnn.py "RAM 패딩 크롭 캐시(2026-11-18)" 주석 ·
  .claude/skills/synth-training/SKILL.md 리더 절 실측표
- Confidence: 5/5

### Discovery
사용자 관찰 "GPU 6GB 쓰는데 노는 시간이 있다"(utilization 23%)로 시작.
프로파일 결과 병목은 GPU 도 워커 수도 아닌 세 겹이었다:

1. `BandCrops.__getitem__` 이 크롭 하나마다 전체 프레임(896×516 PNG
   ≈462KB)을 `cv2.imread` — 100에폭 × 4723 = 47만 회 디스크 읽기.
2. 학습 루프가 **에폭마다 `loaders(ds, 64, False)` 로 새 평가 로더를
   만들었다** — `persistent_workers=True` 인데 로더가 매번 새로 생기면
   워커 8기가 에폭마다 재생성됐다.
3. 워커 스폰 시 데이터셋 전체가 피클로 전송된다(Windows spawn) —
   캐시 도입 후엔 92MB × 워커 수.

### Fix Code
- `__init__` 에서 지터 폭+2px 여유의 패딩 크롭을 한 번만 디코드해 RAM 보관
  (총 ~92MB). 프레임 밖 상자 87건만 전체 프레임 폴백으로 통째로 보관.
  좌표 계산은 구버전과 동일하게 프레임 좌표로 한 뒤 캐시 좌표로 이동.
- 평가 로더 루프 밖 1회 생성, `workers=0`(RAM 캐시 후 항목당 ~0.4ms 라
  싱글스레드로도 0.84초). 학습 로더 `workers=4`.

### Analysis
- 실측: 에폭 17.7초 → 2.8초(6.3배). 일회성 비용 사전디코드 8초 + 스폰
  11초. 100에폭 체인 ~29분 → ~5분.
- 동치 검증: jitter=0 에서 캐시 경로 vs 직접 imread 경로 52표본 불일치 0.
- Why non-obvious: "GPU 노는 걸 봐라"가 데이터 병목을 가리키는 건 맞지만,
  그 병목의 정체를 워커 수 부족으로 진단하면(2026-11-17 잘못된 결론)
  스폰 비용만 늘린다. 병목은 읽기 횟수와 로더 수명이었다.
- 함정: Windows spawn 은 워커마다 데이터셋 피클 전송 — 캐시를 넣으면
  워커 수가 비용이 된다. 캐시가 있으면 워커를 늘리지 말고 줄인다.
