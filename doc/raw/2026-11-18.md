## [2026-11-18 discovery] Case 2: 리더 에폭 17.7초의 진짜 범인 — 매-접근 imread 와 매-에폭 로더 재생성

### Grounding
- Git Context: `hash:b2a1ace+`
- Evidence: reader_crnn.py "RAM 패딩 크롭 캐시(2026-11-18)" 주석 ·
  .claude/skills/synth-training/SKILL.md 리더 절 실측표
- Confidence: 5/5

### Discovery
사용자 관찰 "GPU 6GB 쓰는데 노는 시간이 있다"(utilization 23%)로 시작.
프로파일 결과 병목은 GPU 도 워커 수도 아닌 세 겹이었다:

1. `BandCrops.__getitem__` 이 크롭 하나마다 전체 프레임(896×516 PNG
   ≈462KB)을 `cv2.imread` — 100에폭 × 4723 = 47만 회 디스크 읽기.
2. 학습 루프가 **에폭마다 `loaders(ds, 64, False)` 로 새 평가 로더를
   만들었다** — `persistent_workers=True` 인데 로더가 매번 새로 생기면
   워커 8기가 에폭마다 재생성됐다.
3. 워커 스폰 시 데이터셋 전체가 피클로 전송된다(Windows spawn) —
   캐시 도입 후엔 92MB × 워커 수.

### Fix Code
- `__init__` 에서 지터 폭+2px 여유의 패딩 크롭을 한 번만 디코드해 RAM 보관
  (총 ~92MB). 프레임 밖 상자 87건만 전체 프레임 폴백으로 통째로 보관.
  좌표 계산은 구버전과 동일하게 프레임 좌표로 한 뒤 캐시 좌표로 이동.
- 평가 로더 루프 밖 1회 생성, `workers=0`(RAM 캐시 후 항목당 ~0.4ms 라
  싱글스레드로도 0.84초). 학습 로더 `workers=4`.

### Analysis
- 실측: 에폭 17.7초 → 2.8초(6.3배). 일회성 비용 사전디코드 8초 + 스폰
  11초. 100에폭 체인 ~29분 → ~5분.
- 동치 검증: jitter=0 에서 캐시 경로 vs 직접 imread 경로 52표본 불일치 0.
- Why non-obvious: "GPU 노는 걸 봐라"가 데이터 병목을 가리키는 건 맞지만,
  그 병목의 정체를 워커 수 부족으로 진단하면(2026-11-17 잘못된 결론)
  스폰 비용만 늘린다. 병목은 읽기 횟수와 로더 수명이었다.
- 함정: Windows spawn 은 워커마다 데이터셋 피클 전송 — 캐시를 넣으면
  워커 수가 비용이 된다. 캐시가 있으면 워커를 늘리지 말고 줄인다.

## [2026-11-18 discovery] Case 3: "오답 확정 22"의 13건은 앱이 확정하지 않은 행이었다 — 집계 라벨 버그

### Grounding
- Git Context: `hash:c091269+`
- Evidence: _diag/judge_GEN9*.jsonl outcome×stage 교차집계 · eval_real_judge.py:77
- Confidence: 5/5

### Discovery
사용자 질문 "어딜 어떻게 봐야하냐"(오답 22건의 확신도 분포를 어디서 보는가)를
조사하다 발견. eval_real_judge 요약의 "정답 확정/오답 확정"이 **확신도 게이트
앞에서 `val` 을 대입**해, 0.85 에 막힌 행(앱이 확정하지 않음)까지 확정으로
샀다. GEN9 "정답 확정 125" 중 실제 확정 96, "오답 확정 22" 중 실제 확정 9.
"확정"이 두 의미(값통과 vs 앱확정)로 쓰였다.

### Analysis
- GEN9 앱 실제: 정닥 46.4% · **오답 4.3%(목표 ≤5% 달성)** · 함정 29.0%.
  제품 재집계(같은 자): 69.7% · 6.6% · 40.0% — 제품도 오답 5% 초과다.
- 확신도 문턱 스윕(재판 상세에서 재학습 없이 계산 가능 — 이게 "어떻게
  보는가"의 답): 0.80→48.3%/5.8%(초과) · 0.85→46.4%/4.3%(무릎) ·
  0.90→44.0%/2.4%. 현재 0.85 가 이미 무릎 — 문턱 조정 여지 없음.
- 남은 간극(제품 대비 -23pp)은 리콜: 미확정 102 = 검출게이트 21·판독 19·
  값검증 20·확신도차단 42.
- Why non-obvious: 요약 라벨이 "확정"이라 아무도 의심하지 않았다. 상세
  jsonl 에는 stage 가 늘 있었으니 — 명세를 stage 별로 교차집계하면 바로
  나온다. 채점 코드의 집계 축과 앱의 실제 행동 축이 어긋난 전형.

### Fix Code
eval_real_judge.py 요약 집계를 `stage=='확정'` 만 세도록 수정. 막힌 행은
"확신도차단(판독정답/오답)" 버킷으로 남김(문턱 조정의 교환 근거).

rot90 사망 14건을 회수한다"(2026-11-16 메모의 해법 후보).

### 판정
GEN9 검출기+리더에서 네 정책 전부 안전 제약(오답확정 ≤5%, DC238) 미달 또는 이득 0:

- rot90 태그 14건 중 5건(143·134·92·213·163)은 회전 후 정확 확정 — 축 자체는
  유효. 죽이는 것은 **방향 선택기**: 180° 프레임에서 검출기가 자신만만하게

  같은 값을 내는 일이 없다).

### 조치

방향을 판정하는 것 — 이는 코드화면 판별(단위 유무)과 같은 입력·같은 구조다.
