## Case 1: 한 상수가 그림과 라벨을 동시에 정해, 라벨을 넓히면 숫자가 작아졌다

### Grounding
- Git Context: `hash:998e474` (작업 트리)
- Evidence: `assets_dev/train/lcd_layout.py` BAND_MARGIN 주석 · `test_lcd_layout.py`
- Confidence: 5/5

### Error
사람 지시는 "정답 사각형을 키워라"였다. `BAND_MARGIN` 을 0.10 → 0.20 으로
올렸더니 게이트가 4.4% → 34.7% 로 올랐다. 원인을 재 보니 **밴드는 한 픽셀도
안 커졌고 숫자가 작아져 있었다.** 프로세스를 분리해 측정(프로파일 6종 × 6장,
유리 대비 중앙):

```
   m      밴드/유리   숫자/유리   밴드/숫자
 0.10      0.515      0.429      1.200
 0.20      0.514      0.367      1.400
 0.30      0.514      0.321      1.600
```

밴드는 0.514 로 붙박이다. 오른 점수는 "상자를 키워서"가 아니라 "숫자를 14%
줄여 상자 안 여백을 늘려서" 산 것이고, 리더가 받을 해상도를 그만큼 깎았다.

### Environment Context
- Packages: sugartrain(py3.10, opencv, torch)
- Migration Issue: No

### Fix Code
```python
BAND_MARGIN = 0.10    # 라벨 — band_quad 가 정답 쿼드를 그릴 때만
LAYOUT_MARGIN = 0.10  # 그림 — slot_field 가 숫자를 물릴 때. 고정.

# slot_field
m = LAYOUT_MARGIN if margin is None else margin
# band_top/band_bot(배치 기준선)도 그림 쪽이다
pad_x = max(2, int(round(LAYOUT_MARGIN * dh)))
```

분리 뒤 같은 측정:

```
BAND 0.10 → 0.30 :  밴드/유리 0.515 → 0.666,  숫자/유리 0.429 → 0.416
```

### Analysis
- Root cause: `band_quad` 는 "밴드 = 필드 + m·dh" 로 쓰고, `slot_field` 는
  "밴드가 영역을 꽉 채우도록" 숫자를 역산한다. 같은 m 이 두 식에 들어가
  정확히 상쇄한다.
- Why it failed: 한 상수가 **의도**(정답을 얼마나 넉넉히 적을까)와
  **사실**(기기가 어떻게 생겼나)을 겸했다. 둘은 독립적으로 정해져야 한다.
- How it was fixed: 역할별로 상수를 갈랐다. 계약 테스트도 바꿨다 — 정답 상자가
  mid 영역을 넘는 것은 이제 허용이고(밴드는 배치 요소가 아니라 크롭 영역),
  유리를 넘지 않는 것만 지킨다.

## Case 2: 캔버스를 넘으면 포즈를 줄이던 루프가, 라벨 크기에 촬영 각도를 종속시켰다

### Grounding
- Git Context: `hash:998e474` (작업 트리)
- Evidence: `assets_dev/train/synth_panel.py` 배율 루프 주석
- Confidence: 5/5

### Error
Case 1 을 고친 뒤에도 같은 시드 200장 중 **68장의 그림이 달랐다.** 요소는
하나도 안 움직였고(rects 동일) 난수 소비도 같았는데(78/81/75 로 양쪽 동일)
픽셀의 91%가 달랐다. 두 장을 나란히 보니 내용은 같고 **카메라 자세만** 달랐다.

구판:

```python
for shrink in (1.0, 0.5, 0.25, 0.0):
    Mk, Mr = _mats(shrink)
    quad = _warp_pts(quad0, Mk, Mr)
    if _in(quad):          # 라벨 쿼드가 캔버스 안인가
        img = _warp_img(pre, cv2.INTER_LINEAR, Mk, Mr)
        break
```

라벨을 키우면 쿼드가 더 쉽게 캔버스를 넘어 포즈가 깎인다. 실측(3k, 같은 시드):

```
BAND_MARGIN   |기울기| 중앙   p90     기울기 0 인 장
   0.10          3.84°      9.34°     39/300 (13.0%)
   0.22          2.15°      5.85°     51/300 (17.0%)
   0.30          1.72°      4.38°     68/300 (22.7%)
```

0.10 에서도 13%가 이미 반듯해져 있었다 — 전날 `cam_roll` 을 ±1.5 → ±15 로
넓힌 효과가 그만큼 무효화되고 있었다.

### Environment Context
- Packages: sugartrain
- Migration Issue: No

### Fix Code
```python
# 배율은 **유리**로 정한다 — 그림 쪽 값이다.
_glass0 = np.float32([[px0, py0], [px1, py0], [px1, py1], [px0, py1]])
for zoom in (1.0, 0.92, 0.84, 0.76, 0.68, 0.60):
    Mk, Mr = _mats(1.0, zoom)
    if _in(_warp_pts(_glass0, Mk, Mr)):
        img = _warp_img(pre, cv2.INTER_LINEAR, Mk, Mr)
        break
quad = _warp_pts(quad0, Mk, Mr)
# 라벨이 프레임을 넘으면 여백만 잘린다(유리가 안이고 숫자는 유리 안이다)
quad = np.stack([np.clip(quad[:, 0], 0, W - 1),
                 np.clip(quad[:, 1], 0, H - 1)], 1).astype(np.float32)
```

고친 뒤: 기울기 분포가 세 마진에서 동일(중앙 3.84 · p90 9.99 · 최대 15.33),
같은 시드 그림 **200/200 동일**, 쿼드 높이비 1.2000(이론값).

### Analysis
- Root cause: "프레임을 넘는다"의 판정을 **라벨**로 했고, 못 맞췄을 때의 처리로
  **촬영 변인**을 건드렸다. 판정 대상과 조정 대상이 다른 세계에 있었다.
- Why it failed: 포즈는 "어떻게 찍혔나"이고 라벨은 "무엇을 정답으로 적을까"다.
  후자가 전자를 바꾸면 A/B 에서 통제 안 된 변인이 같이 움직인다. 실촬에는
  뒤로 물러나 찍는 구도는 있어도 **각도를 펴서 찍는 구도는 없다.**
- How it was fixed: 판정을 유리(그림)로 옮기고, 조정을 배율(그림)로 바꿨다.
  라벨이 넘으면 여백만 자른다 — band_quad 의 clip 과 같은 규약이다.

## Case 3: 기본 인자가 모듈 적재 시 굳어, 없는 현상을 측정해 보고했다

### Grounding
- Git Context: `hash:998e474` (작업 트리)
- Evidence: `lcd_layout.band_quad` 시그니처
- Confidence: 5/5

### Error
"마진을 올리면 밴드가 12% 작아진다"고 보고했다. 그런 현상은 없었다.

```python
def band_quad(field, digit_h, clip=None, margin=BAND_MARGIN):   # 구판
```

기본값은 **모듈을 읽을 때 한 번** 평가된다. 실험 스크립트가
`lcd_layout.BAND_MARGIN` 만 바꾸고 모듈을 다시 읽지 않아, `slot_field` 는 새 값
(숫자가 줄어듦)을, `band_quad` 는 옛 값(밴드 그대로)을 쓰는 **어느 코드 경로에도
없는 상태**를 잰 것이다. 실제 굽기는 파일을 고쳐 새로 import 하므로 무사했다.

### Environment Context
- Packages: sugartrain
- Migration Issue: No

### Fix Code
```python
def band_quad(field, digit_h, clip=None, margin=None):
    m = (BAND_MARGIN if margin is None else margin) * digit_h
```

### Analysis
- Root cause: 파이썬 기본 인자의 조기 평가. 자가 잰 것은 제품이 아니라 자 자신의
  결함이었다.
- Why it failed: **자를 새로 만들고 검증하지 않았다.** 알려진 값이 나오는지
  기준선을 넣어 봤어야 했다 — 뒤에 부풀림 곡선을 낼 때는 0.20 줄이 실제 게이트
  94장(34.7%)과 일치하는지 먼저 확인했고, 그래서 그 표는 믿을 수 있었다.
- How it was fixed: 기본값을 호출 시점에 푼다. 측정은 마진별로 **프로세스를
  분리해** 다시 했다.

## Case 4: 게이트를 IoU 에서 포함률로 바꿨다

### Grounding
- Git Context: `hash:998e474` (작업 트리)
- Evidence: `assets_dev/train/eval_band_detector.py` CONTAIN_PASS 머리말
- Confidence: 5/5

### Design Decision
밴드 검출기 게이트의 1순위를 **포함률**(사람 밴드 라벨 중 예측 안에 든 넓이
비율)로 바꾸고, 2순위를 넓이비(예측/라벨), 진단을 변별 삐져나옴으로 두었다.
IoU 는 옛 판과 잇대어 보는 참고값으로 남기되 **합격을 정하지 않는다.**

사람 규칙: "게이트는 숫자를 전부 포함 여부이다. 넉넉하게 포함하든 타이트하게
포함하든 잘리지는 말아야지."

### Alternatives Considered
- Option A: IoU 유지 — 기각. 사람 라벨은 축정렬 직사각형이고 예측은 기울어진
  쿼드라 완벽히 맞춰도 1 이 안 된다. 천장이
  `r/((cos t + r sin t)(r cos t + sin t))` 이고 4° 0.864 · 8° 0.762 ·
  10° 0.715 다. 합성 기울기를 넓히면 검출이 좋아져도 내려간다 — 목표와 반대로
  움직이는 대리 지표.
- Option B: 포함률 단독 — 기각. 화면 전체를 찍으면 만점이다. 실제로 GM 박스
  폴백이 포함률 중앙 1.0000 · 넓이비 중앙 2.5배였다.
- Selected: 포함률(합격) + 넓이비(줄 세우기) + 변별 삐져나옴(진단).

### Decision Code
```python
CONTAIN_PASS = 0.999   # 부동소수 오차만 봐준다. 한 획이라도 밖이면 불합격.

def contain_ratio(pred, label):   # 교집합 넓이 / 라벨 넓이
def area_ratio(pred, label):      # 예측 넓이 / 라벨 넓이
def edge_shortfall(pred, label):  # 라벨 네 변이 예측 밖으로 나간 최대 깊이
```

### Analysis
- Context: IoU 0.838 로 "좋다"고 읽히던 모델(`band_det_r2_40k`)을 포함으로 재니
  **17/271 (6.3%)** 이었다. 네 변이 고르게 잘리고 있었다 — 사람이 처음 말한
  증상("좌우 위아래 상관없이 자른다")이 그대로 숫자로 나왔다.
- **Trade-offs**: 이 자는 엄격한 쪽으로 틀렸다. 사람 라벨은 숫자보다 크므로
  라벨을 담으면 숫자는 반드시 담긴다. 실촬에 숫자 다각형 정답이 없으니 라벨이
  가진 전부다. 느슨하게 하려면 숫자 범위를 지어내야 하고 그건 자가 아니다.
- Reversibility: High. 장별 값(contain/area/edges/iou)을 전부 jsonl 에 남긴다.

## Case 5: 모집단이 다른 두 수치를 나란히 놓고 순위를 매겼다

### Error
"SD CodeFree 실촬 60장 — 지금까지 본 기기 중 가장 많습니다(CareSens N 19장,
UltraMini 28장)". 틀렸다. CareSens N 은 **240장**이다.


"프로파일 없는 기기 중 표본이 가장 크다"도 틀렸다 — SD CHECK GOLD2 189,
오토-첵 156, HANDOK BAROZEN II 123 이 전부 프로파일 없이 더 크다.

### Environment Context

- Migration Issue: No

### Analysis
- Root cause: 수치를 낼 때 **어느 파일·어느 모집단·n** 을 적지 않았다.
- Why it failed: 같은 하루에 같은 모양이 넷이었다 — (a) 이 건, (b) 측정하지

- 사람 지적: "난 그저 숫자주의에 잡음을 무시하는 걸 가리키고 싶을 뿐이야."
- How it was fixed: 수치에 모집단과 n 을 함께 적는다. 두 수치를 비교하기 전에
  같은 모집단인지 먼저 확인한다. 상관을 인과로 말하기 전에 재고, 못 쟀으면
  "재지 않았다"고 말한다. n 이 작으면 순위가 아니라 "구별 안 된다"가 정답일 수
  있다.

## Case 6: [폐기] 밴드 쿼드 검출기 재학습 2차 — 재조준 합성으로 짝비교

### Grounding
- Evidence: doc\kanban\abandoned\밴드-쿼드-검출기-재학습-2차-—-재조준-합성으로-짝비교.md
- Confidence: 4/5

### Discovery
이 길은 아니었다 — 카드가 폐기됐다. 폐기 사유(안티패턴 원재료):

방향이 폐기됐다(사람 결정 2026-09-16). 이 카드는 기울어진 쿼드를 내는 밴드 검출기를 전제하는데, 검출기 출력을 축정렬 사각형으로 바꾸기로 했다. 근거 셋: (1) 실촬 라벨이 전부 축정렬이라 기울기 정답이 없다 — 사람 밴드 라벨 277장·화면 쿼드 410장 100% 직사각형이라 기울기를 채점할 방법이 없다. (2) IoU 는 기울어진 예측을 축정렬 라벨과 견주는 자라 천장이 있고, 합성 기울기를 넓히면 검출이 좋아져도 내려간다(8도 0.762). (3) 8좌표 자유 회귀는 카메라가 낼 수 없는 사각형을 내고, 사람이 화면에서 그 실패를 봤다 — 모서리 한 점만 끌려간 사다리꼴. 대신 마일스톤 '합성만으로 사진에서 값까지 한 번 통과시킨다' 가 축정렬 상자로 같은 질문에 답한다. 합성의 기울기 정답은 버리지 않는다 — 매니페스트에 남아 있으므로 필요하면 다시 꺼낸다.

### Analysis
- Why non-obvious: 다음 세션이 같은 벽에 다시 부딪히지 않게 하는 기록이다.
- Action taken: 주기 compile에서 안티패턴 승격 후보로 검토할 것.
