- Why it failed: "사람이 확인했다"와 "사람이 그렸다"를 같은 source 로 기록했다.

- How it was fixed: 좌표차 0.0 판정으로 수락장을 감별·소급 태그했고, 평가는
  두 축(파인튜닝 학습장·A키 수락장)을 다 빼고 재측정했다.
- 정정된 수치(순수 수동 라벨 134장): **ft_bandnet_v1 IoU 중앙 0.8981 vs
  atone_s0 0.8532** — 파인튜닝 효과는 실재한다. 과거 atone_s0 의 0.851(119장

  박스를 타이트하게 조인다(IoU는 이기지만 밴드 절단 위험은 커진다).
- 파인튜닝 학습 123장 중 12장도 A키 수락장이었다(atone_s0 예측 좌표를 학습).

- **사람 결정 2026-09-27: ft_bandnet_v1 은 폐기.** 실사진 파인튜닝이 사람

## Case 2: 평가 스크립트가 웹툴 오버레이 파일을 덮어썼다

### Grounding

- Confidence: 5/5

### Error

(웹툴 파란 예측 = atone_s0)이 ft_bandnet_v1 예측으로 통째로 교체됐다. 사용자가
A키로 검증 중인 예측이 조용히 다른 모델의 것이 되는 상태였다(웹툴 서버가 살아

### Environment Context
- Packages: eval_band_real.py OVERLAY 상수가 band_quads_pred.jsonl 에 하드코딩
- Migration Issue: No

### Fix Code
`predict_band_quads.py --ckpt band_out/tone/atone_s0.pt` 로 2,512장 재생성
(186초)해 복구. ft 예측은 `band_quads_pred_ft_bandnet_v1_20260927.jsonl` 로 보존.

### Analysis
- Root cause: 평가용 스크립트의 오버레이 출력이 운영 중인 웹툴의 입력 파일과
  같은 경로다. 개인 진단 출력을 정본 파일에 쓰는 구조 — 쓰는 주체가 둘인 파일이었다.

  덮어썼다. 첫 평가는 grep 으로 결과만 봐서 파일이 바뀐 것도 몰랐다.
- How it was fixed: 재생성으로 복구. 재발 방지책은 이번에 코드로 넣지 않았다 —
  eval 기본값을 끄기(off)로 바꾸는 게 합리적이지만 평가→오버레이 갱신 흐름을
  쓰는 다른 용도와 엮여 있어 사람 확인 후 결정한다.

## Case 3: atone_s0 실사진 오차의 병목은 높이 과대 — 단위 줄 흡수

### Grounding
- Git Context: `hash:d6a9451`
- Evidence: `assets_dev/train/band_scale_sweep.py`(자), `assets_dev/train/_diag/band_real/height_over_sheet_v1.png`(눈검판)
- Confidence: 4/5 (눈검 판정 1회, 모델 비전으로 관찰)

### Hypothesis
순수 수동 홀드아웃 134장 IoU 0.8532 의 손실이 스케일 오차인지, 위치 오차인지,
라벨 규약 차이인지 가른다 — 재학습 실험에 들어가기 전에 병목을 안다.

### Results
- 균일 스케일 보정 곡선: 최적 s=0.96 에 IoU 0.8830 (+0.030). 장마다 최적
  s(오라클) 상한 0.9080 — 스케일 보정만으로는 0.91 벽.
- 오차 분해(134장): 중심오차 중앙 0.032(대각선/2 기준, 작음) · 폭비 중앙
  1.023(정확) · **높이비 중앙 1.089, p90 1.223(세로 과대가 병목)**.
  세로형(122장) 높이비 중앙 1.100 vs 가로형(12장) 1.043 — 세로형에 집중.
- 높이만 보정(h_s=0.92): IoU 0.8828 — 균일 보정과 동급. 높이 축 하나가 손실의
  대부분.
- 눈검(height_over_sheet_v1.png, hr 상위 8+중앙 4+하위 4): 과대 장의 초록
  박스는 **아래쪽으로 편중해 나가며 그 자리에 mg/dL 단위 줄이 있다** — 모델이
  단위 줄을 밴드로 흡수. 위쪽(시계·아이콘) 흡수도 소수. 반대로 빨간(사람)
  박스가 숫자 하단을 살짝 자르는 장도 있고(1991·1653), hr=0.45 장(2317)은
  숫자 하단 절반을 놓친 국소 실패다.

### Analysis
- Confirmed/Refuted: 병목은 '계통적 스케일 오차'가 아니라 **세로형에서 단위
  줄을 밴드에 흡수하는 오인**. ~~중층(1.10)엔 위아래 여백 규약 차이 성분이
  섞여 있다~~ → **정정(사람 선언 2026-09-27)**: 라벨 규약은 처음부터
  '숫자줄만' 하나다. 단위가 라벨에 보이는 장은 포함 의도가 아니라 여백이
  넉넉해 가장자리에 걸친 것. 따라서 라벨 규약 불일치 성분은 없었고, 높이
  과대는 전부 모델 오인이다.
- Key metrics: IoU 0.8532 → 스케일 보정 상한 0.908(오라클). 후처리 h_s=0.92
  로 즉시 0.883 까지는 회복 가능하나 원인이 오인이므로 증상 치료다.
- Implications: 재학습 개선의 1순위는 합성에서 '밴드 아래 단위 줄' 경계를
  명시적으로 가르치는 것(단위 줄이 라벨 밖에 있는 훈련쌍). 기존 라벨 중
  단위가 걸친 장은 조여 없애는 감사 대상이다 — 걸침 의심 큐
  (make_unit_clip_queue.py, 라벨 하단 ≈ 예측 하단순 235장/351장).

### 사람 선언 2026-09-27 (peteroh)
밴드 라벨 규약은 **'숫자줄만' 하나다.** 단위(mg/dL)가 라벨에 보이는 장은
단위를 포함하려 한 것이 아니라 여백이 넉넉해 박스 가장자리에 단위가 잘려
걸친 것이다. 웹툴 U키(단위 포함 저장)는 이 선언 직후 제거했고, I키는
'숫자줄만 준수 확인' 마크로 용도를 바꿨다.

추가 선언(같은 날, 질문 답변으로 확정): 1픽셀까지 자르지 않는다. 단위
글자가 절반 이상 보일 때만 조여 배제하고 모서리 걸침은 방치 — 리더가
크롭을 96px(IN_H)로 리사이즈해 그 크기 걸침은 사라진다. 밴드가 기울어
축정렬 상자가 단위를 못 피하는 장은 숫자 온전 포함이 우선(허용 오차).
**밤 재확인: ~45도 등 크게 기울어진 사진에서는 단위가 전체 들어올 수
있다 — 그 장도 그대로 I 다(조이지 않는다).** 조임은 밴드가 거의 수직인데
단위가 절반 이상 들어온 경우만 한다.
