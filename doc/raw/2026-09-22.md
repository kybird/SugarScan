## Case 1: except Exception 이 SystemExit 를 못 잡아 백그라운드 초기화가 조용히 죽었다

### Grounding
- Git Context: `hash:22bcd08`
- Evidence: `assets_dev/train/webtool.py` `_atlas_ensure` · 아틀라스 in-process 흡수
  카드 Result(doc/kanban/done/아틀라스-검토-서버를-웹툴-프로세스로-흡수한다.md)
- Confidence: 5/5

### Error
웹툴(8777) 하나가 /atlas 를 in-process 로 서빙하도록 고친 뒤 첫 검증에서
/atlas 가 20분 넘게 "준비 중"(200 진행 안내)만 냈다. 서버 프로세스는 살아
있고 CPU 는 15초에 0.047초(사실상 정지).

### Environment Context
- Packages: 표준 라이브러리 http.server · make_failure_atlas.py(TF 적재)
- Migration Issue: No

### Wrong Code
```python
def run():
    global _ATLAS_STATE, _ATLAS_ERR
    try:
        import make_failure_atlas as mfa
        _ATLAS_STATE = mfa.init_serve_state(HERE, _AtlasArgs())
    except Exception as e:   # SystemExit 는 여기를 지나친다
        _ATLAS_ERR = f"{type(e).__name__}: {e}"
```

### Fix Code
```python
    except BaseException as e:  # SystemExit 포함 — build_cases 는 등가성
        # 검사에서 SystemExit 를 던진다. Exception 만 잡으면 초기화 스레드가
        # 조용히 죽고 /atlas 는 영원히 '준비 중'이 된다(2026-09-21 실제로 겪음).
        import traceback
        traceback.print_exc()
        _ATLAS_ERR = f"{type(e).__name__}: {e}"
```

### Analysis
- Root cause: `make_failure_atlas.build_cases` 는 등가성 검사 실패에서
  `raise SystemExit(...)` 로 종료한다. `SystemExit` 은 `BaseException` 의
  직계라 `except Exception` 에 잡히지 않는다. 백그라운드 스레드에서 잡히지
  못한 `SystemExit` 는 스레드만 죽인다 — 메인 스레프(서버 루프)는 멀쩡하고,
  상태 플래그도 에러도 기록되지 않아 요청은 영원히 "초기화 중" 분기를 탄다.
- Why it failed: 진행 상황을 관측 가능한 신호(산출물 mtime·로그 print)로 보지
  않고 상태 플래그 추측("아직 초기화 중이겠지")으로 읽어 20분을 낭비했다.
  포그라운드 재현 프로브(-u, unbuffered)가 7초 만에 진짜 원인을 드러냈다 —
  같은 초기화 경로라도 스레드가 아닌 메인에서 돌면 SystemExit 가 프로세스를
  죽여 로그에 즉시 보인다.
- How it was fixed: `except BaseException` 으로 바꿔 SystemExit 까지 안내(503,
  원인 명시)로 전이. 수정 후 진행 안내(200) → 20초 내 실패 안내(503) 전이
  확인. 이 실패 안내가 아틀라스 카드의 AC#3(미빌드 안내)을 그대로 채웠다.

### Related Knowledge
- Patterns: [[verify-symptom-before-hypothesis]]
- **Anti-Patterns**: 상태 플래그 추측으로 진행을 판단하는 것 — 스레드가 죽었는지는
  산출물·로그 같은 외부 신호로 본다

## Case 2: 아틀라스 등가성 실패의 정체 — 쿼드 정본 재생성이 캐시와 스택을 갈라놨다

### Grounding
- Git Context: `hash:ef5d6e7`
- Evidence: `data_cache_v2.npz`(9/5 03:46) · `gmscreen_quads.jsonl`(mtime 9/11 21:52,
  untracked) · `git show 3314eaf:assets_dev/train/eval_reader.py`(9/5 기하 복원) ·
  임시 진단 프로브(holdout 20개 크롭 diff)
- Confidence: 5/5

### Discovery

웹툴 /atlas 초기화가 "등가성 검사 실패: glucose_batch1/2411" 로 죽는 원인을 소거법으로
확정했다:

1. **기하·마진은 무죄** — 캐시 굽기 시점(9/5 02:36, 3314eaf)의 eval_reader 프레이밍은
   축정렬 외접 박스 + BOX_MARGIN(0.10 대칭) + warpPerspective 로, 현재
   build_cache_v2.frame_crop 과 알고리즘·값이 동일하다(904c266 은 정본 이동이지
   의미 변경이 아니었다).
2. **쿼드 값이 갈라졌다** — holdout 20개 전부에서 현재 쿼드로 만든 크롭이 캐시 크롭과
   불일치(diff 10~35, ±16px 시프트 탐색으로도 회복 불가 = 이동이 아니라 영역 자체가
   다르다). gmscreen_quads.jsonl 은 9/11 21:52(리더 스크래치 재구축)에 재생성됐고
   **untracked**이라 옛 값은 어디에도 없다. 지금 쿼드는 사람 LCD 라벨(screen_boxes)
   과도 일치하지 않는다(홀드아웃 라벨 보유 3개 중 0개 일치) — 재생성이 단순
   '사람 라벨 우선 병합'이 아니라 전체 재추론이었음을 시사한다.
3. **재결합은 세 방향 모두 막힌다** — (a) 옛 쿼드 부활: 없음(untracked). (b) 캐시
   재굽기(새 경로): 등가성 검사는 통과하지만 검사의 의미(옛 모델이 학습 때 본 크롭과
   같음 증명)가 깨진다 — 옛 preds(9/8)는 옛 쿼드로 추론된 것이라 재현·TTA 표와 공식
   예측이 어긋난다. (c) preds 재생성: 폐기 계보(2026-09-17) 복원이다.

### Analysis
- Why non-obvious: 어젯밤 첫 진단은 "기하가 바뀌어 캐시와 어긋난다"로 읽었는데,
  9/5 코드 복원 비교에서 기하가 같다는 게 드러났다 — **바뀐 건 정본 파일(쿼드)의 값**이었다.
  mtime 과 git 추적 여부(untracked = 복원 불가)를 먼저 봤어야 한 번에 나올 답이었다.
- Impact: /atlas 의 503 은 정확한 상태다. 부활 조건은 새 리더(reader_crnn.py)가 새
  preds 를 내는 것(마일스톤 '합성만으로 사진에서 값까지'). 웹툴 실패 안내 문구에 이
  진단을 명시했다.
- Action taken: 웹툴 503 안내 갱신 · 아틀라스 흡수 카드가 이미 못박은 "데이터 짝"
  사유의 정밀 버전을 이 Case 로 남김 — 아침 리뷰 카드 '리더 기본 캐시의 합성 팔을
  synth_panel 로 굽는다'(캐시 재굽기 허용 여부 판단)에도 이 근거가 쓰인다.
