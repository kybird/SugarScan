## Case 1: tf2onnx 설치가 훈련 환경의 TF 임포트를 죽였다 — numpy 2.x 가 진벽

### Grounding
- Git Context: `hash:ca4a49c`
- Evidence: `docs/reports/reader-onnx-parity-2026-09-10.md` §환경 사고·복구 기록 ·
  `assets_dev/train/reader_onnx_spec.md` 말미
- Confidence: 5/5 (재현·복구·검증을 이 밤에 전부 수행)

### Error
sugartrain(TF 2.10.1) 환경에서 `pip install tf2onnx`(최신) 후
`import tensorflow` 가 즉사:

```text
_np_bfloat16 = _pywrap_bfloat16.TF_bfloat16_type()
TypeError: Unable to convert function return value to a Python type!
The signature was () -> handle
```

### Environment Context
- Packages: tensorflow 2.10.1 · tf2onnx(최신 → 1.12.0) · protobuf 7.36.1 로 상승 ·
  **numpy 2.2.6 로 상승(원인)** · onnx 1.12.0 으로 하강(부수)
- Migration Issue: No (신규 패키지 도입의 부수효과)

### Fix Code
```text
복구 조합(전부 만족해야 함):
  numpy==1.23.5        # TF 2.10 은 numpy 2.x 에서 위 TypeError 로 죽는다
  protobuf==3.20.3     # 신·구 pb2 를 모두 지원하는 다리 버전(3.19 는 onnx 신스타일 거부, 4.x 는 TF 거부)
  onnx==1.13.0         # 1.22+ 는 numpy>=1.25 요구 → TF 2.10 과 양립 불가
  tf2onnx==1.12.0
  onnxruntime==1.23.2  # 기존 유지
검증: 네 모듈 임포트 + 미니 Keras fit(TRAIN OK)
```

### Analysis
- Root cause: **pip 의존성 해결기가 '요구를 만족하는 최신 조합'을 찾을 뿐 '기존
  워크로드가 돌아가는 조합'을 보존하지 않는다.** tf2onnx 최신은 protobuf>=3.20 을
  요구해 체인이 numpy 2.x 까지 끌어올렸다.
- Why it failed: `() -> handle` TypeError 는 pybind11 이 TF 의 올드 스타일 바인딩을
  numpy 2.x 타입 체계와 연결하지 못하는 시그니처다 — protobuf 를 먼저 의심해
  protobuf 만 내리면 소용없다(실제로 3차례 왕복했다). **TF 2.10 계열에서 이
  에러를 보면 numpy 부터 본다.**
- How it was fixed: numpy 복원이 핵심. protobuf 는 3.20.3(다리 버전), onnx 는
  TF 와 numpy 요건이 교차하는 유일 낮은 지점 1.13.0. 최종 조합은
  reader_onnx_spec.md 에 고정해 뒀다.

## Case 2: 코퍼스 전량이 정수 라벨 — dot·unit 지표는 측정 자체가 불가했다

### Grounding
- Git Context: `hash:3a66bfc`
- Artifact: `assets_dev/train/audit_dot_unit_coverage.py` 출력 · 칸반 done
  「dot·unit 지표 추가」
- Confidence: 5/5 (라벨 2,512장 전수 집계)

### Discovery
mmol/L 소수점 오독(10배 오류)을 완전일치율에서 분리해 보려 했더니 측정할
표본이 없다. `labels.jsonl` 2,512장 **전부 정수**(값 30~511, 자릿수 2~3),
소수점 표본 0건, 단위(unit) 필드 0건. 리더 charset 도 0~9 전용(NUM_CLASSES=11,
blank 포함)이라 소수점 클래스 자체가 없다.

### Analysis
- Why non-obvious: "완전일치 97%인데 소수점은?" 이라는 질문은 측정 가능성을
  전제하는데, 그 전제가 성립하지 않았다. 지표를 먼저 설계하지 말고 **측정할
  표본의 존재부터 센다.**
- Impact: mmol/L 판독은 측정도 학습도 현재 불가 — 앱의 규칙 엔진(소수점 채널
  직접 검출)만이 유일 경로. 데이터 확보가 모든 것의 선행 과제(칸반 handoff
  「mmol/L 실츬 데이터 확보」).
- Action taken: 카드를 "지표 추가"가 아니라 "측정 불가 종결"로 닫고 데이터
  확보 판정을 사람에게 넘겼다.

## Case 3: CTC 리더 ONNX 파리티 — 디코드 1122/1122 완전일치

### Grounding
- Git Context: `hash:ca4a49c`
- Artifact: `_diag/reader_onnx_parity.json` · `assets_dev/train/export_reader_onnx.py` ·
  `assets_dev/train/reader_onnx_spec.md`
- Confidence: 5/5

### Hypothesis
tflite 가 막힌 CTC 리더(BiLSTM, G28)가 ONNX(opset 13) 에서 TF 와 같은 판독을
내는가.

### Results
캐시 홀드아웃 1,122장 전량: greedy 디코드 **100% 완전일치**, logits 최대 절대차
0.006(float32 수준), 모델 2.4MB. 캐시 배열을 양쪽에 동일 투입해 전처리 동일성은
구조적으로 보장(§36). 중간 수정 1건: 입력 채널 축 누락(3 rank → 4 rank)은
모델이 아니라 호출측 인자 문제였다.

### Analysis
- Confirmed/Refuted: 확인 — 온디바이스 전환의 모델 측 준비는 끝났다.
- Key metrics: decode 100% · max|Δlogit|=0.006 · 2.4MB.
- Implications: 남은 것은 런타임 패키지 선택과 실기기 벤치마크(사람 판정 대기).
  파리티 검증 패턴(캐시 배열 재투입)은 tflite 때 작성해 둔 규약의 재사용이다.

## Case 4: 기종 태깅(G34) — 비전 브랜드 문구는 해상도가 내려가면 조건마다 다르게 읽힌다

### Hypothesis
장면 성분 710개의 대표 컨택트 시트(셀 400px)를 비전 모델로 읽으면 기종
1차 태그를 붙일 수 있다.

### Results
- 외형군(색·형태)은 두 독립 판독이 일치: 검정-타원형·흰색-소형·초록-패널·
  파랑·보라·은색 분포가 재현됨.
- 브랜드 문구는 같은 검정-타원형 기기가 판독마다 OneTouch Ultra /
  GlucoNeX plus / CUEDIO PAW / GLUCOCARD 로 갈림. 셀 캡션의 성분 id 도
  오독(c000↔c003 혼동) — 위치 기반 조인(k번째 셀 = c{k:03d})으로 회피.
- 원본 해상도(긴 변 1120px) 스트립에서는 CareSens II·N 이 사분위 8표본

- 채택 규칙: 구조는 믿고, 글자는 고해상도 교차검증된 것만 태그로.
  결과: c001=CareSens II(565장)·c003=CareSens N(723장)·OneTouch Ultra
  4성분(7장)만 확정, 704성분(1,199장·48.1%)은 미확인으로 사람 검토
  (웨툴 /devices, by:agent|human 규약)에 넘김.

### Analysis
- Confirmed/Refuted: 가설은 절반만 참 — 시트는 사람 검토용 대지로는
  유효하지만 브랜드 판독 소스로는 못 쓴다.
- Key metrics: 검증 6성분 1,288장(51.7%) · 미확인 704성분 1,199장(48.1%).
- Implications: "비전 판독은 구조 판단에만 쓰고 글자는 불신한다"(G32 교훈)이
  저해상도에서는 구조까지 일부 오염될 수 있음을 포함하도록 확장됐다.
  대규모 스크리닝 후 사람 확인 경로를 도구로 남기는 것이 측정 카드의

## Case 5: 장면 성분은 기기 그룹이 아니라 촬영 배경 그룹이다 — 거대 성분 판정이 반증됐다

### Grounding
- Git Context: `hash:60c7547`
- Evidence: `assets_dev/train/device_labels.jsonl` (사람 전량 라벨 723/723),
  `assets_dev/train/_diag/scene_components.json` (c003 구성원),
  `docs/reports/premerge-device-components.md`
- Confidence: 5/5

### Discovery
사람이 c003(723장, 코퍼스의 29%)을 사진 단위로 전량 라벨링하자 **기기가 21종**
나왔다. G34 는 이 성분을 `CareSens N` 하나로 단정했었다.

실측 분포(상위):

```
CareSens N                      215
오토-첵                          144
ACCU-CHEK Performa · 은색         63
ACCU-CHEK Performa · 빨강         45
CareSens Dual                    41
SD CodeFree                      35
ACCU-CHEK Active                 29
Gluco Navii GDH                  26
CareSens N Voice                 24
GC 녹십자 MS ONE                  22
CareSens N Premier               21
Auto-chek plus                   19
... 합계 21종 / 723장
```

사용자의 관찰이 원인을 정확히 짚었다: **dhash 는 사진 전체를 보고, 사진의
대부분은 배경(이불·책상·초록 매트)이다.** 혈당계는 프레임의 일부에 불과해
해시를 지배하지 못한다. 그래서 연결요소는 "같은 배경에서 찍은 여러 기기"를
한 덩어리로 만든다.

같은 사실의 다른 방향도 이미 측정돼 있었다 — 근접쌍(해밍 9~14)으로 성분을
이어 붙이면 임계 9 에서도 11%가 다른 기기를 섞었다
(`docs/reports/premerge-device-components.md`). 즉 dhash 거리는 기기 동일성과
상관이 약하다. 이번 건은 그 역방향으로, **성분 내부조차 기기가 균일하지 않다**는
것을 보인다.

또 하나: `ACCU-CHEK Performa` 30장이 **은색 각진버튼 / 빨강 둥근버튼 두 개체**
였다. 기기에 찍힌 모델명이 같아도 외형이 다르면 다른 개체다 — 라벨 스키마에
`variant` 를 추가했다(`81786d4`).

### Analysis
- Why non-obvious: G34 의 검증은 **거대 성분 연쇄를 의심해 사분위 4표본을
  뽑는** 절차였고, 그 표본이 전부 CareSens N 으로 나왔다. 723장 중 215장이
  CareSens N(29.7%)이므로 4표본이 모두 걸릴 확률은 낮지 않다(약 0.8%로
  보이지만 표본이 id 정렬 사분위라 촬영 순서와 상관돼 실제 확률은 훨씬 높다).
  보고서에 "4표본의 한계"를 명시했음에도, 그 한계가 실제로 결론을 뒤집었다.
  **표본으로 균일성을 확인하는 절차는 균일성의 증거가 아니다** — 반례를 못
  찾았다는 것뿐이다.
- Impact:
  1. `scene_components.json` 을 기기 그룹으로 쓰는 모든 추론이 무효다.
     기기 지도는 사진 단위 사람 라벨(`device_labels.jsonl`)로만 만들 수 있다.
  2. 기기 단절 평가(LODO)의 단위는 성분이 아니라 기기 라벨이어야 한다.
     성분 단위로 train/holdout 을 가르면 21종이 통째로 한쪽에 쌓인다.
  3. `scene-component-split` 패턴의 "세션 프록시" 해석은 좁혀야 한다.
     연결요소가 잡는 것은 **촬영 배경의 연속성**이지 기기도 세션도 아니다.
     누수 방지용 분할 기준으로는 여전히 보수적으로 유효하지만(같은 배경이
     양쪽에 걸치지 않게 한다), "같은 세션 = 같은 기기"로 읽으면 틀린다.
- Action taken: 웹툴 `/devices` 를 사진 단위 라벨링 도구로 다시 만들었고
  (`3674220`), 그룹은 "한 번에 여러 장을 고르는 묶음"으로만 쓴다. 사람이
  c003 전량(723장)을 끝냈다.
