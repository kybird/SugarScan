# 2026-09-15

## Case 1: devices.html 렌더가 drawPred 참조로 도중에 죽었다 — 히어로만 뜨고 스트립이 비었다

### Grounding
- Git Context: `hash:9586499` (수정은 미커밋)
- Evidence: 브라우저 콘솔 재현 — `ReferenceError: drawPred is not defined at renderStrip (devices.html:709) at render (devices.html:652) at toggleFlat (devices.html:752)` · 사용자 보고 "전체사진모드에서 기종을 누르면 하나도 표시되지 않고 메인에 딱 하나의 사진만 표시된다"
- Confidence: 5/5

### Error
기종 화면(/devices)에서 사진이 있는 범위(전체·기기 보기·전체사진 모드)를 여는 순마다
`render()` 가 `renderStrip()` 도중에 죽는다. 증상이 반쪽이라 헷갈렸다: `renderStrip` 은
`$('#heroImg').src = ...` 를 지정한 **다음 줄**에서 죽으므로 히어로에는 사진이 정확히
한 장 뜨고, 그 뒤의 스트립 썸네일 생성은 실행되지 않아 목록이 비어 있다.

### Environment Context
- Packages: devices.html 인라인 스크립트, 'use strict'
- Migration Issue: No

### Fix Code
```js
// 이 블록은 전역이어야 한다 — renderStrip·renderSugg 가 drawPred 를 부른다.
// boot() 안에 두면 스코프 밖이라 render 가 도중에 죽고, hero 에 사진 하나만
// 뜬 채 스트립이 비는 사고가 났다(2026-09-15).
const PRED = { quads: null, size: {} };
async function loadPred() { ... }
async function sizeOf(id) { ... }
async function drawPred(id) { ... }
$('#heroImg').addEventListener('load', () => drawPred(heroId));
// ... 청취자들 — 전부 boot() 밖 top-level 로 이동
```

### Analysis
- Root cause: 9586499 가 밴드 검출기 오버레이를 `boot()` **내부 함수**로 추가하면서
  호출부는 전역 함수 `renderStrip`(709행)·`renderSugg`(806행)에 달았다. 함수 선언은
  자기 함수 몸통 스코프에만 묶이므로 전역에서 보이지 않고, strict mode 에서는
  암묵 전역도 안 만들어져 즉시 `ReferenceError`.
- Why it failed: 기능 추가 커밋이 "좌표 계산·캔버스 겹침" 같은 어려운 부분에
  검증을 다 쓰고, **호출 그래프(누가 누구를 부르나)** 는 안 봤다. 커밋 메시지의
  "브라우저에서 확인"은 오버레이가 그려지는지만 봤을 때의 기록으로 추정 — 초기
  scope(todo)가 빈 상태에선 `render()` 가 `renderStrip` 전에 조기 반환해 페이지가
  정상으로 보인다. 빈 범위에서만 확인하면 이 버그는 안 잡힌다.
- How it was fixed: PRED 캐시·loadPred·sizeOf·drawPred·세 청취자를 boot() 밖
  top-level 로 옮기고, 같은 사고를 막는 이유를 주석으로 남겼다. 서버는
  devices.html 을 요청마다 디스크에서 읽으므로 F5 만으로 반영된다.
- 검증: 브라우저에서 ①전체 → ②f(전체사진 모드, 2494장 1–60 표시) → ③팔레트
  "보기"(CareSens N) → 스트립 "240장 중 1–60 (1/4)", 오류 0, 오버레이 캔버스
  180×240에 점선 393px 실제 그려짐.

## Case 2: 합성 목표와 사람 라벨이 다른 것을 가리켰다 — 게이트가 모델이 아니라 그 불일치를 쟀다

### Grounding
- Git Context: `hash:56d8e65`
- Evidence: `assets_dev/train/band_det_tilt_real.py` 출력 · `band_quads_pred.jsonl`(ckpt r2_40k) · `band_boxes.jsonl` 271장
- Confidence: 4/5

### Error

사람이 기종 화면에서 r2_40k 오버레이를 보고 보고했다:

> 오버레이결과가 사각형인데 비해 실촬은 각도가 삐뚤빼뚤이라 해당 검출결과가
> 숫자를 자르는 현상이 관찰된다 좌우 위아래 상관없이 발생한다.

그리는 쪽(`devices.html` `drawPred`)은 쿼드 네 점을 `moveTo/lineTo` 로 그대로
잇는다. 사각형으로 보이는 것은 **예측 자체가 축정렬**이라는 뜻이었다.

### Environment Context
- 검출기: `band_det_r2_40k.pt`, arch=fc, 256x256 레터박스 입력, 쿼드 4점 회귀
- 합성기: `synth_panel.py` 카메라 포즈(yaw/pitch/roll + 초점거리)
- Migration Issue: No

### 잰 값

```
                    |기울기| median    p90      max
합성 synth_r2_10000    0.63°        1.50°    2.73°
r2_40k 실사진 예측      0.36°        0.88°    2.61°
```

원인은 한 줄이었다 — `synth_panel.py:1849`

```python
cam_roll = rng.uniform(-1.5, 1.5)     # 손목 비틀림
```

yaw·pitch 는 ±9° 로 넉넉한데(그건 키스톤을 만든다) 화면 안에서 실제로 회전을
만드는 roll 만 ±1.5° 로 굶었다. 모델은 배운 범위를 정확히 재현하고 있었다.
용량도 구조도 아니었다.

여기까지 보고 게이트를 `bbox(예측)` 대 사람 라벨로 바꾸자고 제안했다.
전환 비용을 재니 0 이었다:

```
n=271   쿼드 median 0.8376   외접 축정렬상자 median 0.8370
```

**이 0.0006 을 "전환 비용이 없다"고만 읽은 것이 실수다.** 사람이 짚었다 —
「그러니까 니 자도 틀린거자나」.

### Root cause

실사진에는 기울기 정답이 아예 없다. `gmscreen_quads.jsonl`(사람)도
`gmscreen_quads_oriented.jsonl`(검출기)도 전 2,497장이 `0.00°` 다. 사람 밴드
라벨도 전부 축정렬이고, 기울어진 라벨을 사람에게 요구하는 안은 이미 기각됐다
(「라벨을 제대로된 기울기로 만드는건 불가능하다」).

그래서 **사람이 기운 숫자를 감싸려고 그린 상자는 그 밴드의 외접 상자**다.
그런데 합성의 학습 목표는 **딱 맞는 기운 밴드**였다. 둘은 다른 것이다:

```
IoU_max = r / ((cos t + r sin t)(r cos t + sin t))      r = h/w
```

| 기울기 | 전체 | 세로형 | 가로형 |
|---|---|---|---|
| 4° | 0.864 | 0.866 | 0.860 |
| 6° | 0.809 | 0.812 | 0.805 |
| 8° | 0.762 | 0.765 | 0.757 |
| 10° | 0.721 | 0.724 | 0.715 |

기울기까지 완벽히 맞힌 예측조차 축정렬 라벨과 이 값을 못 넘는다. 게이트는
검출 품질이 아니라 **목표 정의와 라벨 정의의 불일치**를 재고 있었다. 납작한
밴드일수록 세로로 크게 벌어지므로 가로형이 더 심하다.

`bbox(예측)` 으로 바꿔도 안 고쳐진다 — 예측이 이미 축정렬이라 bbox 가 자기
자신이다. 0.0006 이 바로 그 증거였는데 반대로 읽었다.

### Fix

고칠 자리는 자가 아니라 **목표**다.

- 합성의 밴드 학습 목표를 기운 쿼드가 아니라 **그 쿼드의 축정렬 외접 상자**로
  둔다. 기운 쿼드는 manifest 에 기록으로 남기고 학습에는 안 쓴다.
- 머리를 8 출력에서 **4 출력**(`x0,y0,x1,y1`)으로 줄인다. 네 점을 따로
  회귀하던 자유도가 하는 일이 없었다.
- `cam_roll` 을 실제 손에 맞게 넓힌다. 이제 이게 일을 한다 — 기울수록 목표
  상자가 커지므로 모델이 **기울기를 맞히는 게 아니라 여유를 배운다.** 네
  꼭지점과 달리 이건 실촬에서 가능하다.
- 게이트는 손대지 않는다. 예측·라벨·목표 셋이 같은 것을 가리키면 그때부터
  정직해진다. Case 진행 중 넣었던 `eval_band_detector.axis_box` 는 되돌린다.

펴기(unwarp)는 포기한다 — 사람 판단: 「펴기는 기대도안했어.. 실촬에서
네꼭지점 찾지도못한다」.

### 딸려 나오는 것

- 데이터 스케일 스윕 표(r2_10k 0.748 → r2_20k 0.800 → r2_40k 0.838 →
  r2_80k 0.838)는 **폐기**다. 다른 목표로 학습한 다른 모델의 수치라 새 수치와
  나란히 쓰면 안 된다.
- **40k 평탄화가 모델의 한계가 아니라 자의 천장일 수 있다.** 가로형이
  데이터를 아무리 넣어도 0.69~0.71 에서 안 움직인 것도 10° 천장 0.715 와
  붙어 있다.
- `wide_unknown` 의 좁은 라벨들(1091·1046·606·1094)을 「잘린 라벨」로 몰았는데
  일부는 덜 기운 사진이라 정상적으로 좁은 것일 수 있다 — 재검토 대상.
- 기종 화면 오버레이가 진짜 사각형이 되는데, 그때는 결함이 아니라 정답이다.

### Analysis

- Why it failed: 합성은 **내가 만드는 것**이라 목표를 내 편한 대로 정의할 수
  있었고, 라벨은 **사람이 만든 것**이라 정의가 이미 고정돼 있었다. 둘을 맞추는
  일을 아무도 안 했다. 자를 아무리 정교하게 만들어도 두 정의가 다르면 자는
  그 차이를 잰다.
- 목표는 「합성데이터로 실촬데이터를 정확하게 검출하는 것」이다(사람 선언).
  그러면 **무엇을 검출할 것인가는 실촬 라벨이 정하고, 합성이 따라가야 한다.**
  합성이 기준을 주는 것은 액정 **설계**(요소 자리·여백·hug)까지다 —
  [[no-real-photo-ruler-for-synth]] 는 거기서만 성립한다. 검출 **목표**의
  정의까지 합성이 정하면 배운 것과 채점하는 것이 갈린다.
- Reversibility: High — 목표 정의와 머리 크기만 바뀌고 라벨은 그대로다.
