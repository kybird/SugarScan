## Plan
1) 성분 배정을 파일로 뽑는다. build_grouped_split.py:27 의 components_of() 를 import 해서 쓴다 — 재구현·복사 금지(duplicated-geometry-implementation 과 같은 이유). **임계값은 반드시 8** 이다. 재분할이 8 로 갈랐으므로 다른 값을 쓰면 태그가 분할 그룹과 어긋나 이 카드의 목적이 사라진다. 산출 _diag/scene_components.json — {component_id: [image_id, ...]}. 성분 710개·최대 723장·2장 이상 99개가 재현되는지 먼저 확인하고, 안 되면 거기서 멈추고 보고할 것.

2) 성분마다 대표 1장을 고른다. 대표는 성분 안에서 id 사전순 첫 장으로 고정한다(무작위 금지 — 재실행마다 시트가 바뀌면 사람이 검토를 이어갈 수 없다).

3) 컨택트 시트를 만든다. _diag/device_tags/sheet_NNN.png 로 나눠 담고, 각 셀에 component_id · 대표 image_id · 성분 크기를 캡션으로. LCD 가 아니라 **기기 몸통과 브랜드 각인이 보이게** 원본 전체를 넣을 것 — 기종은 화면이 아니라 몸통에서 읽힌다.

4) 1차 태깅. 각 성분에 {brand, model, confidence, by: 'agent', note} 를 붙여 device_tags.jsonl 에 쓴다(assets_dev/train/ 루트, band_rotation.jsonl 과 같은 자리·같은 형식). 브랜드 각인이 안 읽히면 model 을 비우고 confidence 를 낮춰 남긴다 — 추측해서 채우지 말 것.

5) 검증과 집계. 거대 성분 전이 연쇄 점검(AC #3), 성분 수·장수 양쪽 집계(AC #4), 같은 기종의 성분 분산(AC #5), 저확신 목록(AC #6).

건드리지 말 것: labels.jsonl · gmscreen_quads.jsonl · band_boxes.jsonl · screen_boxes.jsonl · band_rotation.jsonl · data_cache*.npz · train_grouped 산출물 · reader_model* — 전부 읽기만 한다. build_grouped_split.py 와 audit_split_leakage.py 도 읽기만(임계값·성분 정의를 바꾸면 재분할이 흔들린다). lib/ 아래 0줄.

틀리기 쉬운 자리:
- 임계값을 8 이 아닌 값으로 쓰는 것. 감사 보고서에 ≤6 → 1,137개 라는 민감도 수치가 있어 그쪽을 쓰고 싶어지지만, 분할이 8 로 됐다.
- 성분 = 기기라고 **가정**하는 것. 연결요소는 전이 폐포라 A~B, B~C 로 A~C 가 묶인다. 723장 성분이 한 기기라는 보장이 없다 — 그래서 AC #3 이 있다.
- 장수로만 집계하는 것. 723장 성분 하나가 전체 2,494장의 29% 다(count-rows-not-entities · aggregate-hides-stratified-failure).
- 브랜드를 화면 모양으로 추정하는 것. 비전 판독은 구조 판단에만 쓰고 글자는 불신한다 — G32 에서 비전이 GT 171 을 '101' 로 읽었다.
- 태그를 확정으로 쓰는 것. 전부 by: agent 다. human 확인 전에는 다음 작업이 이 값을 근거로 삼지 않는다.
